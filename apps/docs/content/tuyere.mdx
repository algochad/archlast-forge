# Tuyere: the Rust HTTP engine

Tuyere is the HTTP server inside the engine image, written in Rust to take the place of `Bun.serve`. Sockets, TLS, HTTP/1.1, HTTP/2, WebSocket framing, server-sent events and pub/sub fan-out run on Rust threads (hyper, tokio, rustls, and uWebSockets' WebSocket protocol layer). Your functions, queries, mutations and pages still run in JavaScript on Bun's threads, so nothing about how you write an app changes.

Tuyere was called archlast-serve before it had a name of its own; `HTTP_ENGINE=archlast` still selects it, and its package is `@archlast/forge-tuyere` (`packages/tuyere`).

You do not install it or call it. The engine image has it, and `HTTP_ENGINE=auto` (the default) uses it in production on 4 or more CPU cores. Anywhere else (development, a one- or two-core machine, a platform it is not built for) the same app runs on `Bun.serve`.

## Why a second server

`Bun.serve` runs the HTTP stack and your handler on one thread. For a Forge app that thread also runs the function, so the more the server does per request (parsing, TLS, framing, headers, compression) the less is left for your code, and one core of a four-core machine does all of it. In Tuyere the Rust threads do that work and hand the JavaScript thread a batch of finished requests through shared buffers, one native call per batch, and take back the answers the same way. The JavaScript thread spends its time on your function.

## What it does for a Forge app

- **Faster everything around your code.** HTTP parsing, TLS, WebSocket framing and subscriptions' fan-out are off the JavaScript thread. A published query's update goes to every subscriber from Rust.
- **Pages printed by Rust** and **pages kept in memory.** The framework hands the engine a template and JSON, or asks it to keep a page for anonymous visitors, so a request is answered without running JavaScript at all: [Rust page rendering](rust-renderer.html).
- **A response type that skips Web `Response` objects** on `/rpc/<function>` and Forge RPC.
- **Everything else stays as it was.** CORS, rate limits, the firewall, security headers, telemetry and graceful shutdown run in the engine as before. The server logs which HTTP engine it chose at start.

## Choosing it

| `HTTP_ENGINE` | |
|---|---|
| `auto` (default) | The native engine in production on 4 or more cores when its library is there, `Bun.serve` otherwise. |
| `archlast` | The native engine. An error, not a fallback, where it cannot load. |
| `bun` | `Bun.serve`, always. |

`ARCHLAST_BACKEND` chooses how Bun loads the Rust core: `napi` (the default, a Node-API addon) or `bun-ffi` (a plain C ABI). Both run the same core and pass the same tests. The engine image ships the `napi` one. See [configuration](configuration.html#server).

## What the HTTP path does for a request

A request to `/http` (the routes of `forge/http.ts` and NestJS controllers) is answered from the engine's own request: the server reads the method, path, headers and body from it, runs the same checks, telemetry and rate limit as for any other request, and writes the answer as bytes. The pieces that took a Forge request from 33,000 to about 176,000 a second on four cores (a [minimal route](http.html#minimal-routes), which skips the Web objects and Nest, reaches about 336,000):

- **No Web objects on the way in for Nest.** A NestJS controller's request is handed to the adapter as the fields it reads, and the Web `Request` is made only if a handler asks for `req.raw`. The answer comes back as a status, headers and bytes, not a `Response` that is then read back.
- **Nest's interceptor machinery stays off HTTP routes.** The interceptor that records microservice and gateway messages goes on the handlers that take messages, so a controller's HTTP route is not run through an Observable and an async-context binding.
- **Security headers are encoded once.** The REST API's Helmet headers are written as one block of bytes, not encoded name by name for every answer.
- **Fewer hops, and no promise where none is needed.** A request that is not traced and has no cookie to resolve is answered from the engine's own batch without a promise when its handler's answer is ready; the handler's time limit is one list of deadlines with one timer instead of a timer per call; the headers a request needs are read from the raw bytes and the rest are decoded only if asked for; route matches, path names and the rollups telemetry counts into are remembered; and the Rust I/O threads default to one fewer than the cores (at most four), leaving one core for the JavaScript thread.

Telemetry, request ids, rate limits and every Nest feature work as before; anything the fast path would do differently (a WebSocket, a streamed body, the firewall, the API docs' paths) takes the old path.

## How much faster

Two measurements, both in containers limited to 4 CPU cores and 2 GiB of memory, loaded with oha ([method and machine](benchmarks.html)).

**A REST API with in-memory CRUD on the NestJS path**, the same controller on both servers: only `HTTP_ENGINE` changes.

{/* bench:engine */}

| | `Bun.serve` | Tuyere | |
|---|---:|---:|---:|
| Read one item (requests/s) | 37,971 | 175,874 | 4.6× |
| List 20 items (requests/s) | 32,708 | 133,301 | 4.1× |
| Update an item (requests/s) | 27,535 | 127,514 | 4.6× |
| Create an item (requests/s) | 26,192 | 113,262 | 4.3× |
| Read, 99th percentile | 3.22 ms | 1.22 ms | |

{/* /bench:engine */}

The engine gives the same Nest controller about 4.6 times the requests per second, and more than a Nest app costs on `Bun.serve` because of what the engine hands the framework (below).

**The engine on its own**, with no framework, serving the same API with its native `App` API (one JavaScript thread, three Rust I/O threads): about 456,000 reads a second, 3.2 times `Bun.serve`'s and level with Go and Axum and above .NET, whose servers are compiled; the handler is TypeScript. It is in the table on the [benchmarks](benchmarks.html) page. The `Bun.serve` server there is a single `fetch` handler, so a leaner one would narrow that gap.

**The same API in other stacks** (Go, Rust, .NET, Node, Bun) is on the [benchmarks](benchmarks.html) page. A Forge app is a framework with telemetry, security headers, authentication and a dashboard in the request path, and it runs your code in JavaScript, so it is not level with a hand-written Axum or fasthttp server (2.2 to 2.8 times behind on reads for a NestJS controller, 1.2 to 1.5 times for a [minimal route](http.html#minimal-routes)) and the numbers there say so.

**Forge RPC echo, a call that does almost nothing** (the engine's own harness, `bench/container/compare.sh`, same limits). The echo handler's cost is so small that this measures the server:

| | `Bun.serve` | Tuyere |
|---|---:|---:|
| HTTP, 64 connections (requests/s) | about 90,000 | about 105,000 |
| WebSocket, 16 connections (messages/s) | about 196,000 | about 307,000 |
| WebSocket, 512 connections, 32 in flight each | about 803,000 | about 911,000 |

**Where it loses.** With a single connection (a request, then wait for the answer) the Rust engine is behind: two thread hand-offs cost more than one thread doing everything (WebSocket echo at one connection: about 48,000 messages/s against 80,000; 75,000 with `spinMicros`, which spins instead of sleeping and costs CPU). It also uses more CPU per request than `Bun.serve` on the same load, about 1.4 to 1.6 times. The engine trades CPU for throughput and for keeping the JavaScript thread free; it is the right trade on a server with cores to spare and not on a single-core box, which is why `auto` leaves it off there.

## Limits worth knowing

- Linux only. Where its library is missing (macOS, Windows, a build without it) `auto` picks `Bun.serve`, and `archlast` is an error.
- A page the engine keeps skips rate limits, the firewall and telemetry on a hit, because the app is not run: [keeping a page](framework.html#keeping-a-page-for-visitors-who-are-not-signed-in).
- It is a workspace package (`packages/tuyere` in the repository) and is not published to npm on its own; the engine image builds its native library.

The package has its own README with the standalone API (`App`, `serve`, `serveCompat`), the options (`threads`, `workers`, `spinMicros`) and an architecture document with the buffers and the wire protocol.
