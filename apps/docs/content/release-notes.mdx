# Release notes

What each release changed, newest first. **Unreleased** is on the `staging` branch and goes out with the next version. Releases are made automatically when something is merged into `master` (a patch, or a minor when users get something new), and the release moves what was under Unreleased under its version number, here and on its [GitHub release](https://github.com/algochad/archlast-forge/releases). A version with nothing noted here lists its commits there.

## Unreleased

### Added

- **A native HTTP engine, `HTTP_ENGINE`.** The server can answer through archlast-serve instead of `Bun.serve`: sockets, TLS, HTTP/1.1 and HTTP/2, WebSocket framing and pub/sub fan-out run on Rust threads, and functions still run on Bun. `auto` (the default) picks it in production on 4 or more CPU cores and when its library is there (the engine image has it); development and one- or two-core machines keep `Bun.serve`. `bun` and `archlast` force one. Forge RPC's own server follows the same choice. See [configuration](configuration.html#server).

- **Islands for full-stack apps.** With `export const islands = true` in `app/root.tsx` (new apps have it), a page is server HTML and only the parts that need the browser load JavaScript, each hydrating on its own; links swap the next page in, so the document and its live connection survive. The starter's home page for a visitor who is not signed in has 1.3 kB of JavaScript instead of 126 kB. `FORGE_ISLANDS=0` or removing the line keeps whole-page hydration. Routes with an `action`, pages with errors and an interactive root stay whole. See [islands](framework.html#islands-pages-that-ship-only-the-javascript-they-need).
- **`@archlast/forge-runtime/pool`: threads for CPU-heavy work.** `computePool(tasks)` runs functions defined with `task({ f })` on worker threads ([knitting](https://js.knitting.run)) and an action awaits the result, so a long calculation no longer stalls the calls on its thread. Tasks can't use `ctx` or the database. See [functions](functions.html#cpu-heavy-work-in-an-action).

### Changed

- **Pages render faster on the server.** The Better Auth client a page's header gets from `useAuth()` is built when something uses it, not on every server render (the starter's home page: about 15% more requests per second). Nothing changes in the browser.
- **Faster calls on the native engine.** `/rpc/<function>` and Forge RPC answer with the engine's own response type, which skips the Web `Response` (a cached query on 4 cores: 88k req/s on `Bun.serve`, about 100k on the engine; Forge RPC's echo: 49k and 97k).

## 0.20.0

Better Auth's plugins built into the engine, an API docs site in the layout readers know, an engine image less than half the size, monorepos that deploy with `bun run up` in each app, commands for the agent skill, and security hardening across the server, GraphQL and the image.

### Security

- **Live queries hold bounded arguments.** A `subscribe` message is at most `MAX_SUBSCRIPTION_BYTES` (new, 64 KiB), and one WebSocket's live queries hold at most 16 times that; past either the subscription is refused with `PAYLOAD_TOO_LARGE`. A subscription whose arguments fail validation now ends with a `BAD_REQUEST` error message instead of an error update that stayed open: before, anyone could open subscriptions with large invalid arguments and make the server hold many times their size until the socket closed (20 messages of 4 MB held about 2 GB). See [limits](limits.html#subscriptions).
- **One client holds at most `MAX_CONNECTIONS_PER_IP` WebSockets** (new, 256 per server; `0` turns it off), so the per-connection bounds above can't be multiplied by opening more sockets. Behind a proxy this needs `TRUST_PROXY`, as the rate limit does.
- **A `_storage` row can't name an object outside the files.** Its `key` must have the shape `generateUploadUrl` makes, and S3 storage refuses to sign, read or delete any other key. An admin could write a row naming a backup under `_backups/` in the same bucket (owner-only everywhere else, and it holds the variables and settings), then download or delete it from the Files page. `ctx.storage.getUrl` and `delete` take only `_storage` ids.
- **`POST /rpc` compares the media type whole.** `text/plain; x=application/json`, which a cross-site page may send without a preflight, was accepted as JSON.
- **Webhooks connect to the addresses they checked.** The host is resolved once per attempt and the request goes to those addresses (the host still names TLS and `Host`), so a DNS answer that changes in between can't send it elsewhere; a host that can't be resolved isn't called (the attempt fails and is retried); `::` and NAT64 addresses of private or metadata IPv4 are blocked, and `fec0::/10` is private.
- **The firewall skips only what the engine or the app's files answer.** A static-looking path (`/posts/x.png?q=…`) that a loader or a route answers is inspected, and so are `/_dashboard`, `/_storage`, `/_csp` and `/_telemetry` where the engine doesn't serve them (dashboard off, S3 storage, a `GET`). App hosts can say which paths are their files (`AppHost.serves`; the framework does).
- **GraphQL through `nest()` no longer has graphql-yoga's open defaults.** Yoga answered any `Origin` with itself and `Access-Control-Allow-Credentials: true` (so any site could read a signed-in visitor's answers), ran mutations sent as a form (a cross-site `POST` that needs no preflight), and served GraphiQL and introspection in production. Now:
  - CORS covers only `TRUSTED_ORIGINS` and `BETTER_AUTH_URL`'s origin, and with `nest()`'s own `cors`, that configuration answers for GraphQL too.
  - Operations are accepted only as `application/json`; a form or multipart body gets `415`.
  - GraphiQL and introspection are on in development only.

  To restore the old behavior, use `yoga: { cors: true }`, `jsonOnly: false` (multipart uploads need it), `yoga: { graphiql: true }` and `introspection: true` in `GraphQLModule.forRoot()`. See [NestJS](nest.html).
- **The engine image runs as the `bun` user (uid 1000), not root.** `archlast-forge dev` and `start` hand the volumes an older image made over to it by themselves. A `compose.yaml` deployment's `/data` volume needs it once before the new image starts, or the engine stops at start and prints the command: `docker compose run --rm --user root --entrypoint chown app -R 1000:1000 /data`.
- **New projects' `compose.yaml` pins `rustfs/rustfs:1.0.4` and `amazon/aws-cli:2.39.3`** instead of `:latest` and an untagged image, and lets only the app's origin use the storage from a browser (`RUSTFS_CORS_ALLOWED_ORIGINS` was `*`). Existing projects can make the same edits ([backend](backend.html)).
- `ALLOW_CUSTOM_FUNCTIONS` can only be set in the environment, no longer from the dashboard.
- `ADMIN_KEY` must be at least 16 characters outside dev, and wrong `x-admin-key` guesses count against the sign-in rate limit. A dashboard session signed in with the key ends when the key changes, and setting an admin's password again signs that account out everywhere.
- Alert webhooks go only to public addresses, without following redirects, and **Send a test** no longer reports network errors.
- `/ready` no longer includes the load error outside dev.
- Rate limits count an IPv6 client by its `/64`, and on Redis a counter that lost its expiry gets one instead of locking the client out.
- MongoDB: an operator object in a pagination cursor or a `v.any()` argument is compared as a value instead of being part of the filter.
- The dashboard hides Better Auth plugin secrets (JWKS private keys, 2FA secrets, OAuth client secrets and tokens, API keys) and shows source lines only from `forge/` and `app/`; Nest's query objects count only their own keys; backup archives with oversized PAX headers are refused.
- The release workflows' actions are pinned to commit SHAs.

### Added

- **Better Auth's plugins come with the engine.** `@archlast/forge-runtime/auth` has everything `better-auth/plugins` exports (organization, two-factor, admin, JWT, bearer, magic link, email OTP, generic OAuth, username, phone number, …) and `oauthProvider`; Better Auth's separately published plugins are subpaths, loaded only when imported: `/auth/oauth-provider`, `/auth/api-key`, `/auth/passkey`, `/auth/sso`, `/auth/scim`, `/auth/i18n`. Nothing to install, all at the engine's Better Auth version, and none runs unless `plugins` lists it. Stripe, Expo and Electron, which need SDKs of yours, are still installed in `forge/`. See [Plugins](auth.html#plugins).
- **Better Auth plugins' tables are declared by the engine.** For every plugin in `defineAuth({ plugins })` the engine derives the tables it needs from the plugin itself (`members`, `organizations`, `jwkss`, `oauthClients`, …, following its options), and `archlast-forge codegen` writes their types to `forge/_generated/authTables.ts`, so `ctx.db.query("members")` is typed. Declare none of them in `schema.ts`, and drop the table-generator script; a table you already declared there under the same name is kept as you wrote it. See [Plugin tables](auth.html#plugin-tables).
- **The page can be made to look like another docs site without CSS** (#31). See [API docs](api-docs.html#look):
  - **Layout:** `page.layout` (the shell; pages per operation, per tag or one page; "On this page"; page actions; previous and next).
  - **Navigation:** `page.nav` (tabs, footer links, group case).
  - **Controls:** `page.controls` (where Authorize goes, an icon or text theme switch, the dev switch, the openapi.json link).
  - **Theme:** `page.theme` (a `minimal` or `dark` preset, every colour as a token for light and dark, light or dark code panels, tinted method labels, density, the sidebar width).
  - **Logo:** a dark variant, and the mark alone.
  - **CSS:** `page.css` (text or a file in `forge/docs`, in a layer after the page's).
  - **Stable selectors:** `data-part` attributes to target.
- **Guides have components:** `<Callout>` (and `<Note>`, `<Tip>`, `<Warning>`, …), `<Tabs>`, `<Steps>`, `<Cards>`, `<CodeGroup>`, `<Accordion>` and titled code blocks, with no imports. Your own components go in `forge/docs/_components/`.
- **Every docs page is also Markdown** (`<page>.md`, `index.md`), and `/docs/llms.txt` lists them.
- **A monorepo's stacks find each other in Docker.** Every app of a monorepo with services gets a `compose.override.yaml`, written by `init --monorepo`, `add`, `remove` and `workspace sync`. It puts the app on the Docker network `<monorepo>-apps` under its name and sets what the apps need to reach each other there: the services' addresses (`ORDERS_RPC_URL=http://orders:4001`, or the TCP host and port), `MICROSERVICES` and `DASHBOARD_URL` for the one dashboard, and the shared `FORGE_RPC_TOKEN` and `DASHBOARD_TOKEN` from `.env`. So `bun run up` in each app is a working deployment on one machine. Before, the apps' `compose.yaml` passed none of these, so the deployed main app couldn't call its services or show them on its dashboard. `.env` keeps the development addresses. `archlast-forge up`, `down` and the data commands read the override file, as `docker compose` does. Delete its first line to keep your own version. Existing monorepos get the file from `archlast-forge workspace sync`. See [Deploying a monorepo](monorepo.html#deploying).
- **The agent skill has commands**: twelve workflows that run a whole task through to its checks and a report. In Claude Code they are `/archlast-forge <command>`; in any agent, asking for the same in words runs them. Build: `feature`, `page`, `service`, `auth`, `webhooks`, `api-docs`. Quality: `review` (an audit against the house rules, as file:line findings with fixes), `adopt` (old code into the blueprint, the API unchanged), `test`. Operate: `deploy` (a production preflight, a backup, the deploy after a yes, live checks), `upgrade` (with the release notes in between applied), `doctor` (a diagnosis that stops at the cause). Update the skill with `npx skills update`. See [Agent skill](agent-skill.html#commands).

### Changed

- **The API docs page is a site of pages, in the layout readers know** (#31). With no configuration:
  - **Layout:** a navigation that runs the page's height, with the logo and search (`⌘K`) at its top, groups in sentence case that fold, and links and the light/dark icon at its foot.
  - **Pages:** a page per topic at its own address (`/docs/products/create-product`, `/docs/guides/quickstart`) instead of `#/products/CheckoutsController_create`.
  - **On each page:** "On this page" on wide screens, the section above the title, Copy page and View as Markdown, previous and next, and an endpoint bar with the method, the URL and Try it.
  - **Server rendering:** pages are rendered on the server, and the browser moves between them without reloading.
  - **Guides and the overview:** guides are pages of their own, and the overview is the description, the base URL and authentication.
  - **Operations:** "Scopes:" shows each scope's meaning on hover, and response headers start folded.
  - **Upgrading:** old `#/…` links move to their page. To keep the 0.19 page, set `page.layout: { pages: "single", shell: "header" }`, `nav: { groups: { case: "upper" } }` and `content: { responseHeaders: "open" }`.
- **Routes with a summary and no `operationId` get one from the summary** ("Create a product" is `createAProduct`, unique in the document). Before, the id was the controller and method (`CheckoutsController_create`) or `http_<METHOD>_<path>`. The page's addresses and generated clients' method names follow it.
  - **Upgrading:** set `operationId` on a route to keep an id you already publish.
- **The engine image is less than half the size**: about 300 MB on disk and a 75 MB download, down from 860 MB and 190 MB. It holds only the engine's packages and their runtime dependencies (no dev tools, type declarations or source maps) on Bun's distroless image, with BusyBox for the shell. Paths, the entry point, the healthcheck and `engine prepare` are unchanged.
  - **Upgrading:** the image no longer has `apt-get`. A project `Dockerfile` that installs system packages on top of it copies the program in from another image instead (see [What the image contains](deployment.html#the-image-on-its-own)).

### Fixed

- **A Nest handler got its `@Contract`'s query and path values as text.** `@Contract` converted them to check them (`?limit=2` against `v.number()`), then gave the handler the original strings, so the feature blueprint's `numItems: q.limit ?? 20` sent `"2"` to a paginated query, which refused it. The handler now gets the values as they were checked: numbers for `v.number()`, booleans for `v.boolean()`, a literal's value. Values the contract doesn't name, and routes without one, are unchanged.
  - **Upgrading:** a handler that compared or parsed them as text needs a change: `@Query("express") express === "true"` is now `express === true`; `Number(q.limit)` still works. See [Contract](nest.html#contract-validators-and-the-openapi-document).
- **A guide, slot or component that doesn't compile no longer takes the docs page down.** It is logged with its file and line, shown in its place in development and left out in production. It used to answer 500 with nothing in the log.
- **`archlast-forge build` on a fresh monorepo clone failed** with "Cannot find module '@archlast/forge-runtime/nest/rpc'" until `dev` had run once. `build` now installs `forge/package.json`'s dependencies first, as `up` and `codegen` do; a monorepo's root install doesn't include them.
- **A new monorepo said "To deploy: bun run up"** at a root that has no stack. It now names the command for each app.
- **An empty `BETTER_AUTH_URL` counts as unset** (the server's own address in development), as `KEY=` in an env file means. It was taken as the address itself, which the dashboard's origin check couldn't parse, so the dashboard's API refused calls from the browser.

### Documentation

- The docs now say that S3 uploads have no size limit from the engine (`MAX_UPLOAD_MB` is the built-in storage's): set one at the bucket.

## 0.19.0

The API docs as a public REST reference, validators that check and document more, an opt-in web application firewall, security headers on by default, and Postgres pools that size themselves.

### Security

- **Security headers (Helmet) are on by default**, with a preset for each kind of answer. A Nest app's REST API gets `Content-Security-Policy: default-src 'none'; frame-ancestors 'none'`, `X-Frame-Options: DENY`, `nosniff` and `no-referrer`. A full-stack app's pages get a Content-Security-Policy with a fresh nonce per page (inline scripts run only with it; your bundle, styles, images, fonts and https APIs and SDKs load), and `useNonce()` gives it to the inline scripts you render (the shadcn/ui starter's theme script uses it). The dashboard gets a strict policy (only its own files, no framing, `no-store` on its API). HSTS and `upgrade-insecure-requests` only in production over https. Change them in code with `http.helmet({ api, app, dashboard })` or `nest(http, { helmet })` (Helmet's own options, merged over the preset), or live on the dashboard's new **Security** page (saved as `HELMET` and `HELMET_CONFIG`), which also lists the CSP violations browsers report to `/_csp`. See [Security headers](security-headers.html).
  - **Upgrading:** an inline `<script>` in a page needs `nonce={useNonce()}`, or the page's policy blocks it; a third-party script, frame or image host goes in `http.helmet({ app })`. A header a handler sets is never replaced, and a proxy that already adds these headers should stop.

### Added

- **The API docs work as an app's public REST reference** (#18). Configure them in code with `http.docs({...})` in `forge/http.ts`: where they are (`path`, `openapi`, `explorer`, `basePath` for a proxy, `production: true` to serve them in production), who they are for (`include`/`exclude` prefixes, `functions: false` to leave `/rpc` out, `hidden` on a route or `@ApiHidden()`), and what the document says beyond the validators: `info`, `servers`, your `securitySchemes` and `security` (the engine's own describe `/rpc` only), your error shape (`errors: { schema, contentType, common }`), reusable `parameters`, response `headers`, `tags` and `tagGroups`, and the `webhooks` your app sends. Routes add `security`, `errors`, `parameters`, `headers`, `responseHeaders`, `status` and `codeSamples` on `http.route()` and `@Contract()`; `@ApiSecurity(scheme, scopes)` lets a scope guard document itself. `API_DOCS` and `API_DOCS_PATH` still win. See [API docs](api-docs.html).
- **Validators document and check more.** New `v.literal()`, `v.enum()`, `v.nullable()` and `v.describe()`. `v.string()`, `v.number()` and `v.array()` take checked options (`minLength`, `maxLength`, `pattern`, `format` such as `"email"` or `"date-time"`; `min`, `max`, `int`; `minItems`, `maxItems`, `unique`), enforced everywhere the validator is, and every builder takes documentation (`description`, `example`, `default`, `deprecated`, `name`). See [Constraints and documentation](schema.html#constraints-and-documentation).
  - **Upgrading:** the numbered `Shared1…` schemas are gone (unnamed shapes are written inline). Give a shape a `name` to make it a stable named schema in the OpenAPI document.
- **An opt-in web application firewall**: `WAF=on` inspects every request (function calls, sign-in, HTTP routes, pages, WebSocket handshakes) with the OWASP Core Rule Set before the engine handles it, and answers a flagged one with `403`. It is [Coraza](https://coraza.io/) running as WebAssembly on Bun, on its own thread (`WAF_WORKERS`), so the request thread isn't slowed; `WAF_MODE=detect` only logs what it would stop, `WAF_PARANOIA` sets the strictness, and `WAF_IGNORE_PATHS`, `WAF_DISABLED_RULES` and `WAF_MAX_BODY_KB` tune it. Blocked requests are logged with the matching rules and counted in `/metrics`. Off by default, and it costs about a millisecond a request and over 100 MB per thread. The dashboard's new **Firewall** page watches and runs it: counters, charts, the latest events, the rules, paths and clients that matched most, and each thread's health; owners switch it off, to detect or to block, change the paranoia level, ignored paths and switched-off rules without a restart (a change that can't load its rules leaves the firewall as it was), and open an event to switch off its rule or ignore its path; **Try a request** shows what the live rules make of a described request. `/metrics` also counts inspected requests and each rule's matches when on. The engine's own code for it is a Bun port of the Coraza adapter in [coraza-node](https://github.com/coraza-incubator/coraza-node) (Apache-2.0), which doesn't run on Bun as published. See [Web application firewall](limits.html#web-application-firewall-opt-in).

### Changed

- **One docs page, with Try it on every operation.** The page is laid out by resource, with an Authentication section, attribute tables, request and response examples, error codes, scopes, code samples (your own `codeSamples` first), Webhooks and Models; guides in `forge/docs/` take front matter (`title`, `group`, `order`), and `forge/docs/_slots/` fills the header, the sidebar footer and the space around each operation. "Try it" opens the request builder on that operation in the page, loaded only when pressed, with one credential store (bearer, API key, OAuth2 client credentials with renewal). `page` in `http.docs()` sets the title, logo, theme, code-sample languages, the builder's auth preset and every text. Full-stack apps can render the reference in their own layout with `ApiReference` from `@archlast/forge-dashboard/api-docs/react`.
  - **Upgrading:** the separate `/explorer` page is gone: that path now opens the docs page with the builder showing. The builder is the engine's fork of Scalar's request builder, kept in the repository as a pinned release and a patch series (no default proxy, no hosted features).
- **The dashboard's files are served under `/_dashboard/_assets/`** (they were at the root of the server), so a proxy that forwards only `/_dashboard` reaches all of it.

### Fixed

- **On a many-core machine, the engine used up a default Postgres's connections by itself** ("sorry, too many clients already", #17). A pool holds all its connections from its first query, so the old defaults (twice and four times the CPU cores) were 99 of 100 connections on 16 cores. Unless `DATABASE_POOL_SIZE` and `DATABASE_WRITE_POOL_SIZE` are set, the pools now take 60% of what Postgres allows (`max_connections`), shared by `REPLICAS` and `RUNTIME_WORKERS` and never more than before: 57 connections for one server on a default Postgres, and 4 + 8 in development. The telemetry store holds 3 connections instead of 9. The server logs its numbers at start and warns when it is close to the limit, and a refused connection logs which settings to change, once a minute, instead of the bare error every second.
- **An app page under the API docs' path answered a plain 404.** The docs now own only their page, `<path>/_docs/*`, the explorer path and the document; anything else under the path goes to the app. A page or root route at one of the docs' own paths is logged with both names (the app keeps it), and stops a production start.

### Documentation

- **The agent skill knows this release.** `SKILL.md` routes requests for API docs, security headers, a WAF and Postgres connection errors to the built-in features, lists what is new since 0.18.0, and adds them to its built-ins, mistakes and done checklist. The references follow: the feature blueprint puts bounds in validators (`v.string({ maxLength })`, `v.number({ int, min, max })`), the OAuth scope guard documents its scopes with `@ApiSecurity`, inbound webhooks are `@ApiHidden()` and outgoing events are listed in `http.docs({ webhooks })`, and operations covers Postgres pool sizing, the `WAF*` and `HELMET*` settings, the new startup messages and their fixes. It no longer tells agents to add security headers at the proxy.

## 0.18.0

Webhooks in and out, HTTP routes at the root, Better Auth client plugins in full-stack apps, MongoDB as a database for the whole engine, and SQLite that syncs every commit by default.

### Added

- **HTTP routes and NestJS controllers can be served at the root**: `httpRouter({ root: true })` serves each route at its own path (`/api/v1/tasks`, `/webhooks/stripe`) as well as under `/http`, and `nest(http, { prefix: "/api/v1/" })` puts controllers there. The engine's own paths win, a route inside one fails when the code loads, and in a full-stack app the pages keep every path no route matches (a route for every path stays under `/http`, with a warning). The OpenAPI document lists the root paths. See [Serving routes at the root](http.html#serving-routes-at-the-root).
- **Webhooks in and out, in the engine** (`@archlast/forge-runtime/nest/webhooks`), after `@nestjs/webhooks` but on your own database: `webhookTables` in the schema, `WebhooksModule.forRoot()`, `Webhooks.dispatch()` in a mutation (an outbox: sent only if the mutation commits), Standard Webhooks signatures, retries with backoff and an attempt log, endpoints per tenant that pause on 429/5xx and disable on 410 or after days of failures, secret rotation with an overlap, an SSRF guard; and `@VerifyWebhook()`/`@IncomingWebhook()` with `WebhookInbox.once()` to apply a received webhook exactly once. Works on SQLite, Postgres and MongoDB. See [Webhooks](webhooks.html).
- **Full-stack apps can use Better Auth client plugins**: export `authPlugins` from `app/root.tsx` and the framework gives them to the auth client on the server render and in the browser; `useAuth<typeof authPlugins>()` types their methods (`organization.create`, `oauth2.consent`, …), and `AuthClient<Plugins>` does the same for `client.auth` in a separate frontend.
- **OAuth discovery at the root addresses**: `/.well-known/oauth-authorization-server/api/auth` and `/.well-known/openid-configuration/api/auth` (where RFC 8414 and OpenID Connect clients look for an issuer at `/api/auth`) now answer with Better Auth's metadata instead of a 404, for apps that use the OAuth Provider plugin.
- **`v.any()`**: a validator for JSON whose shape is not yours, such as the fields Better Auth's plugins write.
- **MongoDB is a database for the engine**: `DATABASE_URL=mongodb://…` (or `mongodb+srv://…`) runs everything on it, as Postgres does: documents (a collection per table, the same indexes as the SQL databases, snapshot transactions on a replica set or sharded cluster, MongoDB 6.0 or newer), the scheduler (a scheduled job commits with the mutation that scheduled it, and a job is claimed by one server), the dashboard (data, admins, audit, environment, settings), migrations, full backups and restores, the CLI's data commands, Better Auth, live queries across servers (`REPLICAS`), and `RUNTIME_WORKERS`. Search is ranked (BM25 on the words of each document). The engine checks at startup that the server can do transactions and says how to fix it if it can't. Writes are snapshot isolation, not serializable (see [Database](concepts.html#database)). Mutations that touch one document avoid MongoDB's transactions: inserting one document went from 1,557 to 8,242 a second, and reading a document and writing it back from 789 to 1,374 (Postgres: 3,870 and 1,836); a mutation that needs more still runs in a transaction. `w=1&journal=false` in the URL trades durability for another 40% on writes. The telemetry store stays a SQLite file in `DATA_DIR`, one for each server. `backup` (a file copy) is for SQLite only: use `mongodump` or a full backup.

### Changed

- **`createTestBackend().withIdentity()` signs in with a real session**, and takes `session: { … }` for fields a plugin keeps there (`activeOrganizationId`), so code that reads the caller's session can be tested. `ctx.auth.getUserIdentity().sessionId` is that session's id instead of `"test"`.
- **SQLite now syncs every commit by default** (`SQLITE_SYNCHRONOUS=FULL`). It ran with `synchronous = NORMAL` until now, so a write the engine had answered could be lost if the machine lost power or the operating system crashed (a crash of the engine alone never lost one). The sync does not stop the function runtime and writes that arrive during one share the next; a write that arrives alone waits for its sync, and under load the speed follows how fast the disk syncs (the load benchmark has the numbers, from 1 ms to 6 ms disks). Set `SQLITE_SYNCHRONOUS=NORMAL` to get the old behavior back. Postgres and MongoDB are not affected, and telemetry stays on `NORMAL`.
- `sum()`, `avg()`, `min()` and `max()` on a query run in the database (SQLite, Postgres, MongoDB) instead of loading every document, when the answer is the same: no `filter()` or `skip()`, every value a number, and for the sum, integers small enough to add exactly. Over 50,000 documents they went from about 160–190 ms to about 19 ms, and a 2,000-document range from about 2.3 ms to about 1 ms. Anything else (reals for the sum, a value that isn't a number) reads the documents as before, so results and errors don't change.
- `include` with `take` on a reverse relation (`{ table, index, take }`) runs one direct statement per parent instead of building a query for each one, about 1.5–2× faster for 100 parents. `getMany()` builds each document's topic once instead of twice.
- Postgres is much faster, mostly under load. A read that makes one statement no longer opens a transaction (a `get` went from 0.44 ms to 0.18 ms, and 64 concurrent gets from 8,800 to about 40,000 a second on four cores), write transactions have a pool of their own (`DATABASE_WRITE_POOL_SIZE`, twice `DATABASE_POOL_SIZE`: concurrent patches 3,100 to 4,300 a second, inserts 4,250 to 5,700), `include` with `take` or `count` is one statement for any number of parents (19.2 to 2.6 ms and 10.4 to 2.9 ms for 100), `insertMany` and `updateMany` are one statement (100 updates 26 to about 2 ms), and `sum`, `avg`, `min` and `max` are worked out by the database when the answer is the same (10,000 documents 150 ms to 19 ms). The server warns at startup if the pools could open more connections than Postgres allows.
- Postgres ranks search results with the document's length taken into account (`ts_rank` with normalization 1), so a long text that mentions a word once no longer outranks a short one.
- `patch()`, `replace()` and `updateMany()` skip an update that leaves the document as it is stored: no SQL statement runs, no topics are published, and live queries don't re-run. On SQLite, a no-op `patch` went from about 100 µs to about 25 µs, and `updateMany` from about 60 µs to about 14 µs a document. An update that changes something publishes the same topics as before.
- Forge RPC is about 4× faster than Nest's TCP transport for small calls (137,000 to 146,000 calls a second against 33,000 to 34,000 in `benchmarks/forge-rpc`, answers checked; it was 3× slower before, at 14,600), and ahead of it for a caller that makes one call at a time (49,000 against 29,000). The client keeps a WebSocket open to the service and falls back to HTTP batches when the service can't take one (`websocket: false` always uses HTTP). The HTTP side is still tRPC's wire format, so a tRPC client can call a Forge RPC server. Its server and client are now `src/forge-rpc/`, written for Bun and shipped minified (`@archlast/forge-runtime/forge-rpc`; use `/nest/rpc`), and `@trpc/*` are no longer installed. A wrong token is refused before the procedure is looked up, so it no longer shows which procedures exist, and the dashboard records a Forge RPC call under the caller's trace over the WebSocket as it did over HTTP. `ForgeRpcClient.unwrap()` returns the caller instead of a tRPC client.

### Fixed

- **In development, a `where()` or `orderBy()` query could leave later reads stale.** The development-only check of the query plan left SQLite's `EXPLAIN` statement open, which kept the reader connection on the snapshot it had, so later queries on it (a `paginate()` after a write, for example) didn't see new writes until a restart. Production was not affected. `where()` is safe to use again.
- **`bun run typecheck` in a full-stack app failed with "Cannot find name 'process'"** when a page reached `forge/` code that reads `process.env` through `forge/_generated/api`. New apps' root `tsconfig.json` has `types: ["bun"]` and `@types/bun`; `archlast-forge upgrade` adds both to existing apps.
- **MongoDB mutations are serializable, as the docs always said.** They were snapshot isolation: forty concurrent "claim this name" mutations all succeeded, and two on-call doctors could both go off call. A mutation that scans, or reads a document it does not write, now also writes one shared guard document, so two of them conflict and the later is retried like a Postgres serialization failure; blind inserts and read-modify-write of the documents a mutation read never touch it, and the insert and toggle benchmarks did not change. Retried mutations run one at a time within a server on MongoDB. See [Transactions and ACID](transactions.html).
- **Sign-up and the other multi-step Better Auth flows are atomic.** The adapter had transactions turned off, so a failure between writing a user and writing its account left a user who could not sign in. Each flow is now one transaction.
- **`import` (and `import --replace`) is one transaction.** It cleared tables in one transaction and loaded rows in others, so a failure left the data empty or half loaded. On MongoDB a very large import is bounded by its 60-second transaction limit.

### Documentation

- The authentication docs and the agent skill cover being the client of another archlast-forge app: signing in with it through Better Auth's `genericOAuth`, calling its API with the user's token (refreshed) or as your app (`client_credentials`).
- The authentication docs cover being an [OAuth 2.1 and OpenID Connect provider](auth.html#being-an-oauth-21-and-openid-connect-provider) with Better Auth's OAuth Provider plugin (consent page, protecting your API with its tokens), [organizations for multi-tenant apps](auth.html#organizations-and-multi-tenant-apps), and a script that [declares a plugin's tables](auth.html#plugin-tables) for you. The agent skill follows them.
- **The agent skill states the conventions as rules and comes with a feature blueprint.** Agents built features as plain functions, put controllers outside `forge/_modules/<feature>/`, wrote their own pagination and wrapped the built-in hooks. `SKILL.md` now opens with the house rules, a table of the built-in systems to use instead of homemade ones, and the mistakes to avoid, and the new `references/feature-blueprint.md` is a complete feature (module, services, controller, thin functions, pagination from the query to the page and the REST route, a test) that was run in a fresh project. Run `npx skills update` to get it ([Agent skill](agent-skill.html)).
- Two new pages: [Transactions and ACID](transactions.html) (what is atomic, isolated and durable on each database, what is not, how it is tested) and [Compared with Convex](convex.html) (a benchmark of Convex's self-hosted backend against archlast-forge on one machine).

## 0.17.0

Two backends on one Redis no longer share a cache, and AI coding agents get a skill and docs they can read as Markdown.

### Added

- **An agent skill:** `npx skills add algochad/archlast-forge` teaches AI coding agents how to build on archlast-forge: project modes, what the scaffolder writes, the CLI, services and modules, Forge RPC, data and functions, clients, operations and observability, each reference pointing back to these pages. See [Agent skill](agent-skill.html).
- **The docs for agents:** `llms.txt` (also `/index.md`) has key facts, a start-here list by task and a line for every page. Every page is Markdown at `/<page>.md`, with its section and the previous and next page at the top, or at its own address with `Accept: text/markdown`. `/llms-<section>.txt` is one section in one file.

### Changed

- **Redis keys belong to a service.** Everything the engine keeps in Redis (the query cache, the topics that wake subscriptions, both rate limiters) now starts with a prefix, `archlast-forge:<service>:`, from [`OTEL_SERVICE_NAME`](configuration.html), or from `REDIS_PREFIX` when you set it. Before, every app used the fixed prefix `archlast-forge:`, so two backends on one Redis, such as the services of a monorepo, shared a query cache (a function with the same name and arguments in both was answered from the other's cached result) and woke each other's subscriptions. Servers of one service share their keys, and different services stay apart.
  - **Upgrading:** an app with no service name keeps its keys, so nothing moves. Naming a replicated app that had no name moves its keys, and its servers on different versions miss each other's writes until the last is upgraded (cached entries expire after `CACHE_TTL_MS`). Set `REDIS_PREFIX=archlast-forge:` on every server first to avoid that.
  - Two apps with one prefix on one Redis are reported at startup: `another app already uses the Redis prefix`.
- **The generated `compose.yaml` passes `OTEL_SERVICE_NAME` and `REDIS_PREFIX` on** from `.env` (empty means none). `archlast-forge stack` still recognizes a `compose.yaml` made before as generated, not as edited by you.
- **Every app of a monorepo gets its own `OTEL_SERVICE_NAME`** from `init`, `add app`, `add service` and `workspace sync`; one that is already set is kept.

### Documentation

- **A recommended `forge/` layout:** Nest code in `_modules/<feature>/`, with routers at the top level. See [Folder layout](nest.html#folder-layout).
- Corrections to the docs where they disagreed with the code: where `start --no-docker` keeps its data, SSE streaming, password reset, `--no-shadcn` with a backend, `--transport` implying a monorepo, hydration with `Date` values in loaders, and more.

## 0.15.0

The CLI adopts a monorepo made by hand, and upgrades a monorepo whole.

### Added

- The main app of a monorepo can have any name, and its packages any scope: `archlast-forge.workspace.json` has `main` (a folder) and `scope`. ### Changed

- A phone app is a client of any main app, a full-stack app or a backend (`init --mobile` and `add mobile` no longer need a backend).
- Shared packages and the phone app use the root's TypeScript pin and the main app's `@types/bun`, and package names are read from each app's `package.json`.
- The mobile and desktop templates name the main app and its typed API instead of `apps/api` and `apiApi`.
