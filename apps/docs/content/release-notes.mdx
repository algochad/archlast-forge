# Release notes

What each release changed, newest first. **Unreleased** is on the `staging` branch and goes out with the next version. Releases are made automatically when something is merged into `master` (a patch, or a minor when users get something new), and the release moves what was under Unreleased under its version number, here and on its [GitHub release](https://github.com/algochad/archlast-forge/releases). A version with nothing noted here lists its commits there.

## Unreleased

## 0.18.0

Webhooks in and out, HTTP routes at the root, Better Auth client plugins in full-stack apps, MongoDB as a database for the whole engine, and SQLite that syncs every commit by default.

### Changed

- **HTTP routes and NestJS controllers can be served at the root**: `httpRouter({ root: true })` serves each route at its own path (`/api/v1/tasks`, `/webhooks/stripe`) as well as under `/http`, and `nest(http, { prefix: "/api/v1/" })` puts controllers there. The engine's own paths win, a route inside one fails when the code loads, and in a full-stack app the pages keep every path no route matches (a route for every path stays under `/http`, with a warning). The OpenAPI document lists the root paths. See [Serving routes at the root](http.html#serving-routes-at-the-root).
- **Fixed: in development, a `where()` or `orderBy()` query could leave later reads stale.** The development-only check of the query plan left SQLite's `EXPLAIN` statement open, which kept the reader connection on the snapshot it had, so later queries on it (a `paginate()` after a write, for example) didn't see new writes until a restart. Production was not affected. `where()` is safe to use again.
- **Fixed: `bun run typecheck` in a full-stack app failed with "Cannot find name 'process'"** when a page reached `forge/` code that reads `process.env` through `forge/_generated/api`. New apps' root `tsconfig.json` has `types: ["bun"]` and `@types/bun`; `archlast-forge upgrade` adds both to existing apps.
- **Webhooks in and out, in the engine** (`@archlast/forge-runtime/nest/webhooks`), after `@nestjs/webhooks` but on your own database: `webhookTables` in the schema, `WebhooksModule.forRoot()`, `Webhooks.dispatch()` in a mutation (an outbox: sent only if the mutation commits), Standard Webhooks signatures, retries with backoff and an attempt log, endpoints per tenant that pause on 429/5xx and disable on 410 or after days of failures, secret rotation with an overlap, an SSRF guard; and `@VerifyWebhook()`/`@IncomingWebhook()` with `WebhookInbox.once()` to apply a received webhook exactly once. Works on SQLite, Postgres and MongoDB. See [Webhooks](webhooks.html).
- **Full-stack apps can use Better Auth client plugins**: export `authPlugins` from `app/root.tsx` and the framework gives them to the auth client on the server render and in the browser; `useAuth<typeof authPlugins>()` types their methods (`organization.create`, `oauth2.consent`, …), and `AuthClient<Plugins>` does the same for `client.auth` in a separate frontend.
- **OAuth discovery at the root addresses**: `/.well-known/oauth-authorization-server/api/auth` and `/.well-known/openid-configuration/api/auth` (where RFC 8414 and OpenID Connect clients look for an issuer at `/api/auth`) now answer with Better Auth's metadata instead of a 404, for apps that use the OAuth Provider plugin.
- The authentication docs and the agent skill cover being the client of another archlast-forge app: signing in with it through Better Auth's `genericOAuth`, calling its API with the user's token (refreshed) or as your app (`client_credentials`).
- **`v.any()`**: a validator for JSON whose shape is not yours, such as the fields Better Auth's plugins write.
- **`createTestBackend().withIdentity()` signs in with a real session**, and takes `session: { … }` for fields a plugin keeps there (`activeOrganizationId`), so code that reads the caller's session can be tested. `ctx.auth.getUserIdentity().sessionId` is that session's id instead of `"test"`.
- The authentication docs cover being an [OAuth 2.1 and OpenID Connect provider](auth.html#being-an-oauth-21-and-openid-connect-provider) with Better Auth's OAuth Provider plugin (consent page, protecting your API with its tokens), [organizations for multi-tenant apps](auth.html#organizations-and-multi-tenant-apps), and a script that [declares a plugin's tables](auth.html#declaring-a-plugins-tables) for you. The agent skill follows them.
- **The agent skill states the conventions as rules and comes with a feature blueprint.** Agents built features as plain functions, put controllers outside `forge/_modules/<feature>/`, wrote their own pagination and wrapped the built-in hooks. `SKILL.md` now opens with the house rules, a table of the built-in systems to use instead of homemade ones, and the mistakes to avoid, and the new `references/feature-blueprint.md` is a complete feature (module, services, controller, thin functions, pagination from the query to the page and the REST route, a test) that was run in a fresh project. Run `npx skills update` to get it ([Agent skill](agent-skill.html)).
- **MongoDB mutations are serializable, as the docs always said.** They were snapshot isolation: forty concurrent "claim this name" mutations all succeeded, and two on-call doctors could both go off call. A mutation that scans, or reads a document it does not write, now also writes one shared guard document, so two of them conflict and the later is retried like a Postgres serialization failure; blind inserts and read-modify-write of the documents a mutation read never touch it, and the insert and toggle benchmarks did not change. Retried mutations run one at a time within a server on MongoDB. See [Transactions and ACID](transactions.html).
- **Sign-up and the other multi-step Better Auth flows are atomic.** The adapter had transactions turned off, so a failure between writing a user and writing its account left a user who could not sign in. Each flow is now one transaction.
- **`import` (and `import --replace`) is one transaction.** It cleared tables in one transaction and loaded rows in others, so a failure left the data empty or half loaded. On MongoDB a very large import is bounded by its 60-second transaction limit.
- **SQLite now syncs every commit by default** (`SQLITE_SYNCHRONOUS=FULL`). It ran with `synchronous = NORMAL` until now, so a write the engine had answered could be lost if the machine lost power or the operating system crashed (a crash of the engine alone never lost one). The sync does not stop the function runtime and writes that arrive during one share the next; a write that arrives alone waits for its sync, and under load the speed follows how fast the disk syncs (the load benchmark has the numbers, from 1 ms to 6 ms disks). Set `SQLITE_SYNCHRONOUS=NORMAL` to get the old behavior back. Postgres and MongoDB are not affected, and telemetry stays on `NORMAL`.
- `sum()`, `avg()`, `min()` and `max()` on a query run in the database (SQLite, Postgres, MongoDB) instead of loading every document, when the answer is the same: no `filter()` or `skip()`, every value a number, and for the sum, integers small enough to add exactly. Over 50,000 documents they went from about 160–190 ms to about 19 ms, and a 2,000-document range from about 2.3 ms to about 1 ms. Anything else (reals for the sum, a value that isn't a number) reads the documents as before, so results and errors don't change.
- `include` with `take` on a reverse relation (`{ table, index, take }`) runs one direct statement per parent instead of building a query for each one, about 1.5–2× faster for 100 parents. `getMany()` builds each document's topic once instead of twice.
- Postgres is much faster, mostly under load. A read that makes one statement no longer opens a transaction (a `get` went from 0.44 ms to 0.18 ms, and 64 concurrent gets from 8,800 to about 40,000 a second on four cores), write transactions have a pool of their own (`DATABASE_WRITE_POOL_SIZE`, twice `DATABASE_POOL_SIZE`: concurrent patches 3,100 to 4,300 a second, inserts 4,250 to 5,700), `include` with `take` or `count` is one statement for any number of parents (19.2 to 2.6 ms and 10.4 to 2.9 ms for 100), `insertMany` and `updateMany` are one statement (100 updates 26 to about 2 ms), and `sum`, `avg`, `min` and `max` are worked out by the database when the answer is the same (10,000 documents 150 ms to 19 ms). The server warns at startup if the pools could open more connections than Postgres allows.
- **MongoDB is a database for the engine**: `DATABASE_URL=mongodb://…` (or `mongodb+srv://…`) runs everything on it, as Postgres does: documents (a collection per table, the same indexes as the SQL databases, snapshot transactions on a replica set or sharded cluster, MongoDB 6.0 or newer), the scheduler (a scheduled job commits with the mutation that scheduled it, and a job is claimed by one server), the dashboard (data, admins, audit, environment, settings), migrations, full backups and restores, the CLI's data commands, Better Auth, live queries across servers (`REPLICAS`), and `RUNTIME_WORKERS`. Search is ranked (BM25 on the words of each document). The engine checks at startup that the server can do transactions and says how to fix it if it can't. Writes are snapshot isolation, not serializable (see [Database](concepts.html#database)). Mutations that touch one document avoid MongoDB's transactions: inserting one document went from 1,557 to 8,242 a second, and reading a document and writing it back from 789 to 1,374 (Postgres: 3,870 and 1,836); a mutation that needs more still runs in a transaction. `w=1&journal=false` in the URL trades durability for another 40% on writes. The telemetry store stays a SQLite file in `DATA_DIR`, one for each server. `backup` (a file copy) is for SQLite only: use `mongodump` or a full backup.
- Postgres ranks search results with the document's length taken into account (`ts_rank` with normalization 1), so a long text that mentions a word once no longer outranks a short one.
- `patch()`, `replace()` and `updateMany()` skip an update that leaves the document as it is stored: no SQL statement runs, no topics are published, and live queries don't re-run. On SQLite, a no-op `patch` went from about 100 µs to about 25 µs, and `updateMany` from about 60 µs to about 14 µs a document. An update that changes something publishes the same topics as before.
- Forge RPC is about 4× faster than Nest's TCP transport for small calls (137,000 to 146,000 calls a second against 33,000 to 34,000 in `benchmarks/forge-rpc`, answers checked; it was 3× slower before, at 14,600), and ahead of it for a caller that makes one call at a time (49,000 against 29,000). The client keeps a WebSocket open to the service and falls back to HTTP batches when the service can't take one (`websocket: false` always uses HTTP). The HTTP side is still tRPC's wire format, so a tRPC client can call a Forge RPC server. Its server and client are now `src/forge-rpc/`, written for Bun and shipped minified (`@archlast/forge-runtime/forge-rpc`; use `/nest/rpc`), and `@trpc/*` are no longer installed. A wrong token is refused before the procedure is looked up, so it no longer shows which procedures exist, and the dashboard records a Forge RPC call under the caller's trace over the WebSocket as it did over HTTP. `ForgeRpcClient.unwrap()` returns the caller instead of a tRPC client.

### Documentation

- Two new pages: [Transactions and ACID](transactions.html) (what is atomic, isolated and durable on each database, what is not, how it is tested) and [Compared with Convex](convex.html) (a benchmark of Convex's self-hosted backend against archlast-forge on one machine).

## 0.17.0

Two backends on one Redis no longer share a cache, and AI coding agents get a skill and docs they can read as Markdown.

### Changed

- **Redis keys belong to a service.** Everything the engine keeps in Redis (the query cache, the topics that wake subscriptions, both rate limiters) now starts with a prefix, `archlast-forge:<service>:`, from [`OTEL_SERVICE_NAME`](configuration.html), or from `REDIS_PREFIX` when you set it. Before, every app used the fixed prefix `archlast-forge:`, so two backends on one Redis, such as the services of a monorepo, shared a query cache (a function with the same name and arguments in both was answered from the other's cached result) and woke each other's subscriptions. Servers of one service share their keys, and different services stay apart.
  - **Upgrading:** an app with no service name keeps its keys, so nothing moves. Naming a replicated app that had no name moves its keys, and its servers on different versions miss each other's writes until the last is upgraded (cached entries expire after `CACHE_TTL_MS`). Set `REDIS_PREFIX=archlast-forge:` on every server first to avoid that.
  - Two apps with one prefix on one Redis are reported at startup: `another app already uses the Redis prefix`.
- **The generated `compose.yaml` passes `OTEL_SERVICE_NAME` and `REDIS_PREFIX` on** from `.env` (empty means none). `archlast-forge stack` still recognizes a `compose.yaml` made before as generated, not as edited by you.
- **Every app of a monorepo gets its own `OTEL_SERVICE_NAME`** from `init`, `add app`, `add service` and `workspace sync`; one that is already set is kept.

### Added

- **An agent skill:** `npx skills add algochad/archlast-forge` teaches AI coding agents how to build on archlast-forge: project modes, what the scaffolder writes, the CLI, services and modules, Forge RPC, data and functions, clients, operations and observability, each reference pointing back to these pages. See [Agent skill](agent-skill.html).
- **The docs for agents:** `llms.txt` (also `/index.md`) has key facts, a start-here list by task and a line for every page. Every page is Markdown at `/<page>.md`, with its section and the previous and next page at the top, or at its own address with `Accept: text/markdown`. `/llms-<section>.txt` is one section in one file.
- **A recommended `forge/` layout:** Nest code in `_modules/<feature>/`, with routers at the top level. See [Folder layout](nest.html#folder-layout).

### Fixed

- Corrections to the docs where they disagreed with the code: where `start --no-docker` keeps its data, SSE streaming, password reset, `--no-shadcn` with a backend, `--transport` implying a monorepo, hydration with `Date` values in loaders, and more.

## 0.16.0

One dashboard for a main app and its microservices, Nodes, your Nest classes as Services, and the dashboard's slowdown fixed.

- **Fixed:** the Runtime and Cache pages over long ranges took up to minutes (a quadratic latest-sample query on the telemetry thread), holding up every other dashboard call, and a proxy in front answered 502. Live pages no longer poll while an answer is on the way.
- **Microservices** (was Services): with `DASHBOARD_URL`, `OTEL_SERVICE_NAME` and `DASHBOARD_TOKEN` a microservice sends its telemetry to the main app and serves no dashboard. The main app's `MICROSERVICES` lists them, and its backend picker shows a microservice's data, schema and functions.
- **Nodes:** each service's server processes and their function runtimes, as replicas start and stop, with a live-nodes alert.
- **Services:** your Nest classes by own time, method by method.
- Forge RPC calls and microservice messages are `rpc` requests (under the caller's trace), gateway messages `ws` requests.
- The CLI writes a monorepo's dashboard variables (`init`, `add`, `remove`, `workspace sync`).

## 0.15.0

The CLI adopts a monorepo made by hand, and upgrades a monorepo whole.

- The main app of a monorepo can have any name, and its packages any scope: `archlast-forge.workspace.json` has `main` (a folder) and `scope`. Without the file, the only app with an `archlast-forge.json` is the main app. `workspace sync` writes `packages/api` for it, so `add mobile`, `add desktop` and `workspace` work there.
- A phone app is a client of any main app, a full-stack app or a backend (`init --mobile` and `add mobile` no longer need a backend).
- `upgrade` in a monorepo moves every app and package: the projects, and the dependencies of the phone app, the desktop app and the shared packages.
- Shared packages and the phone app use the root's TypeScript pin and the main app's `@types/bun`, and package names are read from each app's `package.json`.
- The mobile and desktop templates name the main app and its typed API instead of `apps/api` and `apiApi`.

Earlier releases are in the repository's history: `git log --grep '^Version'`.
