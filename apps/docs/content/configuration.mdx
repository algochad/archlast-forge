# Configuration

The engine is configured with environment variables, read once at startup. Invalid or contradictory values stop it with a one-line message (see [Startup checks](#startup-checks)), so a bad setting never gets as far as serving traffic. A project also has one small file, [`archlast-forge.json`](#archlast-forgejson), which says what kind of project it is. Variables for your own functions are a separate thing: see [Variables for your functions](#variables-for-your-functions).

This page lists every variable the engine reads. [Limits and security](limits.html) explains what the limits do when they are reached, and [Deployment](deployment.html) and [Backends](backend.html) cover running the stack.

## How settings reach the engine

Where a variable comes from depends on how you start the engine.

| You run | Settings come from | Data lives in |
|---|---|---|
| `archlast-forge dev` (a full-stack app, or `--no-docker`) | the process environment, plus generated dev secrets | `forge/data/` |
| `archlast-forge dev` (a backend, with Docker) | `forge/.env` if it exists, plus values the CLI sets (`PORT`, `DATA_DIR`, the dev secrets, `BETTER_AUTH_URL`, `TRUSTED_ORIGINS`, and the URLs of services it started) | a Docker volume mounted at `/data` |
| `archlast-forge start --no-docker` | the process environment | `forge/data/` (next to `forge/`, as for `dev`), unless `DATA_DIR` is set |
| `archlast-forge up` | `.env` in the project root, through `compose.yaml` | the `app-data` volume, mounted at `/data` |
| `archlast-forge start --image <tag>` | `forge/.env`, or the file given with `--env-file` | a Docker volume mounted at `/data` |

In a project that has an `archlast-forge.json`, plain `archlast-forge start` with Docker available is the same as `up`. `--image` is what runs a single image on its own.

Four details are worth knowing before you debug a setting that "does nothing".

- **The process environment wins.** Whatever is already in the environment is never overwritten by the CLI's defaults, by `archlast-forge env set`, or by a value saved on the dashboard's Settings page (below).
- **Bun reads `.env` for you.** `bun` loads a `.env` file from the current directory into the environment before the CLI starts. So `archlast-forge start --no-docker` run in the project root sees the `.env` that `init` wrote, including `ALLOW_INSECURE_HTTP=1`. Move or delete it and the same command stops with `BETTER_AUTH_SECRET is required outside dev`.
- **`compose.yaml` passes only the variables it lists.** `up` uses `.env` to fill in `${...}` placeholders in `compose.yaml`; it does not hand the whole file to the app. The generated file passes `BETTER_AUTH_SECRET`, `ADMIN_KEY`, `BETTER_AUTH_URL`, `ALLOW_INSECURE_HTTP` and `DASHBOARD`, plus the service URLs and, with Caddy, `TRUST_PROXY` and `TRUSTED_ORIGINS`. To set anything else (`RATE_LIMIT_PER_MINUTE`, `TRUST_PROXY` without Caddy, `LOG_FORMAT`), add a line under `environment:` in `compose.yaml`. The file is yours to edit.
- **`dev` and `start --no-docker` share a database.** Both keep it in `forge/data/` unless `DATA_DIR` says otherwise, so what you create in development is there when you start the production bundles on the same machine. (Before `0.2.0`, `start --no-docker` used `./data` of the directory you ran it from, a different database.) Set `DATA_DIR` to keep them apart. In a container the database is on the volume at `/data`.

### Settings saved from the dashboard

Every variable on this page is on the dashboard's **Settings** page, grouped as here, with its current value, its default and where the value comes from. Owners can change most of them there. A value saved there is kept in the database (the `_settings` table) and used when the variable isn't set in the environment, so:

- **The environment still wins.** A variable set in `.env`, `compose.yaml` or the shell shows as "set in the environment" and can't be changed from the page.
- **Most settings apply when the server restarts.** The page lists the ones waiting and has a **Restart now** button: the CLI (`dev`, `start`, the engine image) stops the server and starts it again in the same process, which takes a few seconds; clients reconnect by themselves. A server embedded with `startServer` without a `restart` option says to restart its process instead. The backup settings (`BACKUP_*`) apply at once.
- **Some can only come from the environment:** `DATA_DIR` and `DATABASE_URL` (the engine reads them to find the database the settings are in), `PORT` and `HOST` (the container's port mapping depends on them), `REDIS_URL` and `REDIS_PREFIX` (connected before anything is served), `REPLICAS`, `BETTER_AUTH_URL`, `BETTER_AUTH_SECRET`, `ADMIN_KEY` and `DASHBOARD` (a wrong value could lock you out of the dashboard), and `FORGE_RPC_TOKEN` (every app needs the same one). They are listed, read-only, with the reason.
- **A value is checked before it is saved:** its type, and whether the engine would still start with it (`RUNTIME_MODE=inline` is refused in dev, `STORAGE=s3` without an endpoint, and so on). If a saved value stops making a valid configuration later (the same database opened in dev), the engine starts without the saved values and the Settings page says why.
- **Secrets are write-only.** `S3_SECRET_ACCESS_KEY`, `METRICS_TOKEN` and the like show as "set (hidden)"; typing a new value replaces it. Changes are in the audit log without their values.
- **Where it applies:** on the server that restarts. With several servers, each picks up the saved values when it restarts. CLI data commands that open the database themselves use them too.

### Development secrets

In development the CLI generates `BETTER_AUTH_SECRET` and `ADMIN_KEY` the first time and saves them in `.dev-secrets.json` inside the data directory (`forge/data/.dev-secrets.json`, file mode `0600`), so sessions and the dashboard key survive restarts. They are used only when the variable is not already set. Delete the file to get new ones; everyone is signed out. `dev` also trusts `http://localhost:<port>` as an origin and, when it runs behind a code-server port proxy (`VSCODE_PROXY_URI` is set to something like `https://{{port}}.host/`), the proxy's address for the same port. Outside development nothing is generated: you set the secrets.

### Value formats

- **Integers** (`PORT`, `*_MS`, `*_BYTES`, counts) must be whole numbers at or above the stated minimum. `"10s"` and `"1.5"` are rejected; `"1e3"` is read as 1000. An empty value means "use the default".
- **Booleans** (`DASHBOARD`, `TRUST_PROXY`, `SCHEMA_CHECK`, `ALLOW_CUSTOM_FUNCTIONS`, `ALLOW_INSECURE_HTTP`) are true for `1`, `true`, `on` or `yes` in any case. Every other non-empty value is false, so `DASHBOARD=enabled` turns the dashboard off. Write `on` or `off`.
- **Lists** (`TRUSTED_ORIGINS`) are comma separated; spaces around items are ignored.

"Dev" in the tables below means `archlast-forge dev`. Everything else, including `start` and `up`, is production.

## Server

| Variable | Default | Accepted | What it does |
|---|---|---|---|
| `PORT` | `3000` | integer ≥ 0 | The port to listen on. `0` picks a free one. The CLI's `--port` overrides it. In the engine image keep it at `3000` and map the port with Docker: the image's health check calls `localhost:3000`. |
| `HOST` | `0.0.0.0` | an address | The interface to bind. Set `127.0.0.1` when a proxy on the same machine is the only client. |
| `IDLE_TIMEOUT_SECONDS` | `75` | integer 1 to 255 (higher values are capped at 255) | How long an idle keep-alive connection stays open. Proxies and load balancers reuse upstream connections for 60 to 75 seconds, so closing sooner makes them send a request down a socket that was just closed. Keep it above your proxy's upstream keep-alive. Responses that must stay open (server-sent events) opt out of it on their own. |
| `DATA_DIR` | `./data` (`/data` in the image) | a path | Where the SQLite database (`app.db`), its WAL files and the dev secrets live. Created if missing. Ignored when `DATABASE_URL` is set. |

## Authentication and origins

| Variable | Default | Accepted | What it does |
|---|---|---|---|
| `BETTER_AUTH_SECRET` | generated in dev | any string; use 32 or more random characters | Signs session cookies. **Required outside dev.** Changing it signs everybody out. Better Auth logs a warning at startup for a secret shorter than 32 characters or one that looks low-entropy; generate one with `openssl rand -hex 32`. |
| `BETTER_AUTH_URL` | `http://localhost:<port>` | a URL | The public address of the app, as browsers see it. Sign-in cookies and redirects are built from it. **Outside dev it must start with `https://`** unless `ALLOW_INSECURE_HTTP` is on. Its origin is trusted automatically. |
| `ALLOW_INSECURE_HTTP` | off | boolean | Lets production start with an `http://` `BETTER_AUTH_URL`. Over http the session cookie is not marked `Secure`, so use it for trying things out on one machine, not for real users. |
| `TRUSTED_ORIGINS` | none | comma-separated origins | Browser origins other than `BETTER_AUTH_URL` that may call the engine: Better Auth accepts their sign-in requests (`Invalid origin` otherwise) and `/rpc` and `/api/auth` answer them with CORS headers and credentials. Write origins exactly as the browser sends them: scheme, host and port, no path, no trailing slash. An origin listed only in `trustedOrigins` in `forge/auth.ts` passes Better Auth's check but gets no CORS headers and is not accepted on the WebSocket: use this variable. |

If you serve a frontend from another origin, list it in `TRUSTED_ORIGINS` and create the client with `{ url }`. If the frontend is proxied through the same origin, you need no entry. See [Authentication](auth.html).

## Database

| Variable | Default | Accepted | What it does |
|---|---|---|---|
| `DATABASE_URL` | unset: SQLite at `DATA_DIR/app.db` | `postgres://…`, `postgresql://…`, `mongodb://…` or `mongodb+srv://…` | Use Postgres or MongoDB instead of the SQLite file. Any other scheme fails at startup. Required when `REPLICAS` is above 1. MongoDB must be a replica set (a single node is one) or a sharded cluster, version 6.0 or newer, because documents are written in transactions; the engine checks this at startup and says what is missing. The database in the URL's path (`forge` when there is none) holds a collection per table and the engine's own collections. Options of the URL apply: writes are acknowledged by a majority of the replica set and journaled unless it says otherwise, and `w=1&journal=false` is faster (about 40% on writes) and can lose the last writes if the primary fails. See [Database](concepts.html#database). |
| `DATABASE_POOL_SIZE` | sized from Postgres (below) | integer ≥ 1 | Postgres connections (MongoDB: the driver's pool is this plus the write pool, shared by reads and writes; twice the CPU cores when unset) each function-runtime process holds for reads. |
| `DATABASE_WRITE_POOL_SIZE` | sized from Postgres (below); twice `DATABASE_POOL_SIZE` when only that is set | integer ≥ 1 | Postgres connections each function-runtime process holds for write transactions. A write waits for its commit and the round trips of its statements, which more connections hide (6,100 patches a second on 32 connections against 4,200 on 8, with the reads' pool unchanged). |
| `SQLITE_SYNCHRONOUS` | `FULL` | `FULL` or `NORMAL` | Whether a write is on disk when the engine answers it. `FULL`: yes, so it survives a power cut or an operating-system crash. The write-ahead log is fsynced asynchronously, so the function runtime is not stopped meanwhile, and writes that arrive during a sync share the next one. A write that arrives alone waits for its own sync, so throughput under load depends on how fast the disk syncs (the benchmark disk took 1–6 ms; see the load benchmark report). `NORMAL`: the answer does not wait for the disk, so a power cut can lose the last few answered writes (the database stays consistent; a crash of the engine alone loses nothing). Applies to the app database only; telemetry is always `NORMAL`. Ignored with Postgres or MongoDB, which have their own settings. |
| `SCHEMA_CHECK` | on outside dev, off in dev | boolean | At startup, validate every stored document against the schema and refuse to start if some do not match. `SCHEMA_CHECK=off` skips the scan, which can take a while on big tables. [Migrations](migrations.html) shows how to fix mismatches. |
| `REPLICAS` | `1` | integer ≥ 1 | The number of servers you run. It does not start any; it declares your intent so that a multi-server setup missing its shared pieces fails at startup. Above 1 it requires `REDIS_URL` and a Postgres or MongoDB `DATABASE_URL`. |

**How many Postgres connections the engine holds.** A pool opens all of its connections at its first query and keeps them, so a server holds `RUNTIME_WORKERS × (DATABASE_POOL_SIZE + DATABASE_WRITE_POOL_SIZE) + 3` (the 3 are the telemetry store's) from the moment it starts, busy or not, and `REPLICAS` servers hold that many times over. When the two pool sizes aren't set, the engine reads Postgres's `max_connections` at start and gives this app's servers 60% of what an ordinary role may open (`max_connections` minus the reserved slots), split between `REPLICAS` and `RUNTIME_WORKERS`, a third for reads and the rest for writes, never more than twice the cores for reads and four times for writes. On a default Postgres (100) that is 18 + 36 + 3 = 57 for one server with one process; the rest is left for a reload, `psql` and other clients. In development the pools are 4 and 8. The server logs the numbers at start (`Postgres connections: …`) and warns when what it holds, with what was already open, is over 80% of the limit. If Postgres refuses a connection (`sorry, too many clients already`), the log says once a minute which settings to change. Set both sizes to choose them yourself, for example when other apps share the database. See [Tuning](deployment.html#tuning).

SQLite runs in WAL mode with one serialized writer, and it belongs to one engine process. Its memory is sized to the server's RAM (the container's memory limit when there is one, else the machine's), split across `RUNTIME_WORKERS`: reads are memory-mapped up to a quarter of it (64 MiB to the 2 GiB SQLite allows), so pages come straight from the OS's file cache without a copy, and the page caches of the writer and the four readers share a sixteenth of it (8 MiB to 1 GiB in all, against SQLite's 2 MiB a connection); sorts and temporary indexes stay in memory. On 50,000 random reads by id of a 116 MiB database that the OS had cached, that made reads about 1.5× faster, range reads about 1.2×. There is nothing to set. Postgres is the choice for several servers. The engine does not pool or tune Postgres connections through variables; put those options in the URL.

## Redis

| Variable | Default | Accepted | What it does |
|---|---|---|---|
| `REDIS_URL` | unset: in-memory | `redis://…` | Turns on cross-server behavior: the bus that carries write notifications between servers, a shared query cache, and rate limits (also Better Auth's) that count across servers. With one server you can leave it unset. If it is set and Redis is not reachable, startup fails rather than hanging. |
| `REDIS_PREFIX` | from `OTEL_SERVICE_NAME`; `archlast-forge:` without one | `letters, digits . _ - :`, up to 64 | What every Redis key and channel of this service starts with: the cache (`<prefix>cache:`), the topics (`<prefix>t:`) and the rate limits (`<prefix>rl:`). Every server of one service uses the same prefix, and services that share a Redis use different ones, or one would serve another's cached results and wake its subscriptions. You rarely set it: the default is `archlast-forge:<service>:` from [`OTEL_SERVICE_NAME`](observability.html#exporting-to-your-own-collector), which is the same on every server of a service (that is how the dashboard tells services apart too), and `init` gives every app of a monorepo its own. An app with no service name keeps `archlast-forge:`, the keys the engine always used, so upgrading it moves nothing. A secret has no part in it, so rotating `BETTER_AUTH_SECRET` changes no keys. A trailing `:` is added if missing. If another app has already used the prefix (it notes who in Redis, by a hash of `BETTER_AUTH_SECRET`), startup logs a warning. |

## Storage

| Variable | Default | Accepted | What it does |
|---|---|---|---|
| `STORAGE` | `s3` with `S3_ENDPOINT`; otherwise `local` in dev and `off` elsewhere | `s3`, `local`, `off` | Where files live. `local` keeps them in `DATA_DIR/storage` and serves them at `/_storage` (see [built-in storage](storage.html#built-in-storage)); it refuses `REPLICAS` above 1. |
| `STORAGE_PUBLIC_URL` | the value of `BETTER_AUTH_URL` | a URL | With `STORAGE=local`: the address browsers reach the engine at, which upload and download URLs start with. |
| `MAX_UPLOAD_MB` | `5120` | integer ≥ 1 | The largest file the built-in storage accepts, and the largest backup the dashboard takes as an upload. Other requests keep `MAX_REQUEST_BYTES`. |
| `S3_ENDPOINT` | unset | a URL | The S3-compatible service, as the engine reaches it. |
| `S3_BUCKET` | unset | a bucket name | The bucket for uploads. It must already exist. Set together with `S3_ENDPOINT`, or neither. |
| `S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY` | unset | strings | Credentials for the bucket. |
| `S3_REGION` | unset | a region, e.g. `us-east-1` | Needed by some providers when signing. |
| `S3_PUBLIC_ENDPOINT` | the value of `S3_ENDPOINT` | a URL | The address browsers use for uploads and downloads. Presigned URLs are signed for this host, so it must be reachable from the browser and must be the host that will be called. Set it whenever the engine reaches storage by an internal name (a Docker network, a private IP). |

Without storage, `ctx.storage.generateUploadUrl()` fails with `Storage is not configured: set S3_ENDPOINT and S3_BUCKET, or STORAGE=local to keep files on this server`. See [File storage](storage.html).

## Backups

Read again for every backup, so a change applies without a restart. See [Backups](backups.html).

| Variable | Default | Accepted | What it does |
|---|---|---|---|
| `BACKUP_SCHEDULE` | none | a cron expression (UTC) | When to back up: `0 3 * * *` is 03:00 every day. Empty: no scheduled backups. |
| `BACKUP_KEEP` | `7` | integer ≥ 1 | Scheduled backups kept; older ones are deleted. |
| `BACKUP_FILES` | `on` | boolean | Whether scheduled backups include the files in storage. |
| `BACKUP_DIR` | unset | a path | Keep backups in this directory. |
| `BACKUP_S3_ENDPOINT`, `BACKUP_S3_BUCKET` | unset | a URL, a bucket | A bucket of their own for backups (wins over `BACKUP_DIR`). Set both, or neither. |
| `BACKUP_S3_ACCESS_KEY_ID`, `BACKUP_S3_SECRET_ACCESS_KEY`, `BACKUP_S3_REGION`, `BACKUP_S3_PUBLIC_ENDPOINT` | unset | strings | Its credentials, region, and the address browsers download from. |
| `BACKUP_S3_PREFIX` | `_backups/` in the files' bucket, none in a bucket of their own | a key prefix | Where in the bucket backups go. |

Without `BACKUP_S3_*` or `BACKUP_DIR`, backups go to the files' bucket under `_backups/` with `STORAGE=s3`, and to `DATA_DIR/backups` otherwise.

## Limits

These are explained one by one, with what happens when each is hit, in [Limits and security](limits.html#limits-and-what-happens-when-you-hit-them).

| Variable | Default | Minimum | What it limits |
|---|---|---|---|
| `FUNCTION_TIMEOUT_MS` | `10000` | 1 | Time for a query or mutation (and the basis of the hard timeout). |
| `ACTION_TIMEOUT_MS` | `600000` | 1 | Time for an action or an HTTP endpoint handler. |
| `MAX_RESULT_BYTES` | `8388608` (8 MiB) | 1 | The JSON size of a function's return value. |
| `MAX_DOCUMENT_BYTES` | `1048576` (1 MiB) | 1 | The JSON size of one stored document. |
| `MAX_REQUEST_BYTES` | `8388608` (8 MiB) | 1 | An HTTP request body and a WebSocket message. |
| `RATE_LIMIT_PER_MINUTE` | `1200` (off in dev) | 0 | Requests per client IP per minute. `0` turns rate limiting off. |
| `MAX_SUBSCRIPTIONS_PER_CONNECTION` | `200` | 1 | Live queries one WebSocket may hold. |
| `MAX_SUBSCRIPTION_BYTES` | `65536` (64 KiB) | 1 | The JSON size of one `subscribe` message, its arguments included. The live queries of one WebSocket may hold 16 times this together. |
| `MAX_PENDING_CALLS` | `1000` | 1 | Calls waiting for the function runtime before new ones get `503`. Queries are also refused earlier, once their estimated wait passes `FUNCTION_TIMEOUT_MS` (see [limits](limits.html#overload)). |
| `TRUST_PROXY` | off | | Take the client IP from `X-Forwarded-For` for rate limiting. Only behind a proxy that overwrites that header. |

Raise limits only when you have a reason. A larger `MAX_REQUEST_BYTES` lets a single client hold more memory, and a larger `FUNCTION_TIMEOUT_MS` lets one slow query occupy the runtime for longer. Keep work that needs more than ten seconds in an action.

| `WAF_IGNORE_PATHS` | none | comma-separated path prefixes | Requests under these aren't inspected. |
| `WAF_DISABLED_RULES` | none | comma-separated CRS rule ids | Rules switched off, for one that stops something legitimate. |

## Logging and observability

| Variable | Default | Accepted | What it does |
|---|---|---|---|
| `LOG_FORMAT` | `pretty` in dev, `json` otherwise | `pretty`, `json` | Server log lines: readable text, or one JSON object per line with `time`, `level`, `msg` and fields such as `requestId` and `function`. |
| `TELEMETRY` | `on` | `on`, `off` | Record [telemetry](observability.html): requests, traces, errors, logs, runtime samples and metrics, in `DATA_DIR/telemetry.db` (SQLite, also with MongoDB: each server keeps its own) or `_otel_*` tables (Postgres), and serve it to the dashboard and the `/otlp` endpoints. |
| `TELEMETRY_DETAIL_PER_SECOND` | `200` | integer ≥ 1 | Requests a second recorded with all their spans. Past it, a share that keeps to this rate is; the rest are only counted. See [sampling](observability.html#sampling). |
| `TELEMETRY_TRACES_PER_SECOND` | `25` | integer ≥ 1 | Traces kept a second for ordinary requests, and as many again for errors and slow requests. |
| `LOG_RETENTION_DAYS` | `7` | integer ≥ 1 | How long requests, traces and logs stay in the telemetry store. Its statistics, metrics and runtime samples are kept 30 days (or this long, if longer). Finished scheduled jobs are deleted after it too. The audit log is not pruned. |
| `FORGE_RELEASE` | unset | a string | The [release](observability.html#releases) this server runs, when the platform doesn't set a commit variable the engine reads (`GIT_COMMIT`, `GITHUB_SHA`, …). Without either, a hash of `forge/`. |
| `METRICS_TOKEN` | the value of `ADMIN_KEY` | a string | The bearer token for `GET /metrics` (Prometheus text format). With neither set, `/metrics` answers `404` outside dev. |
| `OTEL_EXPORTER_OTLP_ENDPOINT` | unset | a base URL | Also export every request, with its spans, as OTLP/HTTP JSON to `<endpoint>/v1/traces` (a collector, not this app's own `/otlp`). Works with `TELEMETRY=off`. An incoming W3C `traceparent` header is continued either way. |
| `OTEL_EXPORTER_OTLP_TRACES_ENDPOINT` | unset | a full URL | The same, with the full traces URL. Wins over the variable above. |
| `OTEL_EXPORTER_OTLP_HEADERS` | unset | `key=value,…` | Headers for the export (values URL-encoded), such as the collector's API key. `OTEL_EXPORTER_OTLP_TRACES_HEADERS` wins over it. |
| `OTEL_SERVICE_NAME` | `archlast-forge` | a string | The engine's name on the dashboard and on exported spans. A microservice's (with `DASHBOARD_URL`) is required, and is its name in the main app's `MICROSERVICES`. |
| `MICROSERVICES` | unset | `name=url,…` | On a main app: its microservices, at the addresses it reaches them at. Its dashboard shows their telemetry and, picked in the top bar, their data, schema and functions. Needs `DASHBOARD_TOKEN`. Environment only. See [one dashboard](observability.html#one-dashboard-for-a-main-app-and-its-microservices). |
| `DASHBOARD_URL` | unset | a base URL | On a microservice: the main app's address. Its telemetry goes there (it keeps no store of its own), its admin API answers that app's dashboard, and its `/_dashboard` redirects there. Needs `DASHBOARD_TOKEN` and `OTEL_SERVICE_NAME`. Environment only. |
| `DASHBOARD_TOKEN` | unset | 16 characters or more | The secret a main app and its microservices share for the two above. Environment only. |
| `NO_COLOR`, `FORCE_COLOR` | unset | any value | CLI output: no colors, or colors even when output is not a terminal. |

Every response carries an `x-request-id` header. A request id sent in by the caller is kept if it is 1 to 64 letters, digits, `_`, `.` or `-`; otherwise the server makes one. Logs, errors and spans all carry it. `GET /health` is liveness and `GET /ready` is readiness (`503` while starting, shutting down, or after a failed load, with the error in the body).

## Dashboard and admin

| Variable | Default | Accepted | What it does |
|---|---|---|---|
| `DASHBOARD` | on in dev, off otherwise | boolean | Serve `/_dashboard` and its API under `/_admin`. When off, `/_admin/*` answers `404`. The generated `compose.yaml` turns it on (`DASHBOARD: ${DASHBOARD:-on}`); set `DASHBOARD=off` in `.env` to hide it. |
| `FORGE_RPC_TOKEN` | unset: Forge RPC refuses to start | 16 characters or more | The bearer token [Forge RPC](forge-rpc.html) servers check and clients send. Every app that serves or calls Forge RPC needs the same value. Environment only. |
| `ADMIN_KEY` | generated in dev | any string; use 24 or more random bytes | An owner credential. It signs in to the dashboard and authorizes the CLI's data commands over `POST /_cli`. Without it, key sign-in is refused and the CLI cannot reach a running production server (it answers `Invalid admin key`). Prefer named admin accounts (`archlast-forge admin add`) for people, and keep the key for scripts. |
| `ALLOW_CUSTOM_FUNCTIONS` | on in dev, off otherwise | boolean | Lets owners run code typed into the dashboard. That code runs with the function runtime's privileges, so leave it off unless you need it. See [Dashboard](dashboard.html#running-your-own-code). |

## Runtime and process model

| Variable | Default | Accepted | What it does |
|---|---|---|---|
| `RUNTIME_MODE` | `inline` outside dev; `process` in dev or when `RUNTIME_WORKERS` is above 1 | `process`, `inline` | `inline` runs your functions inside the server process: no message passing per call, about twice the throughput on one core. A function that blocks the event loop for longer than its timeout plus 5 seconds makes a watchdog kill the whole process, so run it under something that restarts it (the engine container does). `process` runs functions in child processes that are restarted alone on a code change or a hang. |
| `RUNTIME_WORKERS` | `1` | integer ≥ 1, or `auto` | Function runtime processes per server. `auto` is the CPU cores (the container's CPU quota when it has one) times `RUNTIME_WORKERS_RATIO`, rounded down, at least 1: 2 on 4 cores, 4 on 8. A call goes to the process with the fewest calls waiting, so one slow call holds up only what is queued behind it. Needs `process` mode (more than 1 selects it). Only the first runs the scheduler, migrations and the schema check. Helps CPU-heavy functions more than write-heavy ones, because SQLite writes share one lock. In `process` mode a change from the dashboard applies without a restart ([below](#changing-the-worker-count-while-running)). |
| `API_DOCS` | the code decides: on in dev, and in production with `http.docs({ production: true })` | `on`, `off` | Serve the OpenAPI document and the API docs page ([API docs](api-docs.html)). Set, it wins over the code either way. |
| `API_DOCS_PATH` | `http.docs({ path })`, else `/_api` | a path | Where the docs page is (the document and the explorer move with it unless `http.docs()` places them); not under a path the engine owns. |
| `RUNTIME_WORKERS_RATIO` | `0.5` | number above 0, up to 4 | For `RUNTIME_WORKERS=auto`: processes per core. Half the cores leaves room for the server process, the database and anything else on the machine. |

`RUNTIME_MODE=inline` is refused in dev (it could not reload code), and refused together with `RUNTIME_WORKERS` above 1.

### Changing the worker count while running

On the dashboard's Settings page, `RUNTIME_WORKERS` shows what is in effect: `2 running (auto: 4 cores × 0.5) · 4 CPU cores detected`. Saving a new value (or `RUNTIME_WORKERS_RATIO`) while the server runs in `process` mode resizes the pool at once, with no restart:

- **Growing**, the new processes start beside the others and take calls once they are ready.
- **Shrinking**, the last processes get no new calls, finish the ones they have (up to `ACTION_TIMEOUT_MS`), and then stop. The first process, which holds the scheduler, backups and gateway sockets, always stays.
- **Nothing in flight fails, and subscriptions carry on**: they live in the server, and their re-runs go to whichever processes are in the pool. A process that crashes is started again, as before.
- The value is saved, so a restart keeps it. A value set in the environment still wins: the dashboard then shows it read-only and changes nothing.
- Going between one inline runtime and several processes changes `RUNTIME_MODE`, which needs a restart (the page says so).

Measured with 16 clients calling a query that spends 4 ms of CPU (`benchmarks/workers`, 4 cores): 185 calls a second inline, 221 with one process, 348 with two, 599 with four; resizing 1 → 3 → 1 under that load failed no call.

## Startup checks

The engine checks its configuration before it opens the database. These are the messages, exactly as printed, and what to change.

| Message | Cause and fix |
|---|---|
| `BETTER_AUTH_SECRET is required outside dev` | Set it in the environment or `.env`. |
| `BETTER_AUTH_URL must be https:// outside dev (got "http://localhost:3000"). Set ALLOW_INSECURE_HTTP=1 only for local testing.` | Set `BETTER_AUTH_URL` to your public `https://` address, or `ALLOW_INSECURE_HTTP=1` for a local trial. |
| `REPLICAS > 1 requires REDIS_URL, or mutations won't reach subscribers on other servers` | Add `REDIS_URL`. |
| `REPLICAS > 1 requires a Postgres or MongoDB DATABASE_URL; bun:sqlite is single-server` | Add a Postgres or MongoDB `DATABASE_URL`. |
| `Set both S3_ENDPOINT and S3_BUCKET, or neither` | Storage needs both. |
| `DATABASE_URL must be a postgres:// or mongodb:// URL (unset it to use bun:sqlite), got "mysql:"` | Only Postgres and MongoDB are supported besides SQLite. |
| `This MongoDB is a standalone server, and the engine needs transactions…` | Start `mongod` with `--replSet rs0` and run `rs.initiate()` once (a single node is a replica set), or use a managed replica set such as Atlas. |
| `MongoDB 5.0.x is too old: the engine needs 6.0 or newer` | Upgrade MongoDB. |
| `RUNTIME_MODE must be "process" or "inline", got "thread"` | Fix the spelling. |
| `RUNTIME_MODE=inline can't reload code when it changes; use it outside dev` | Remove `RUNTIME_MODE` in dev. |
| `RUNTIME_MODE=inline runs one function runtime, in the server process; unset RUNTIME_WORKERS` | Choose `process`, or unset `RUNTIME_WORKERS`. |
| `LOG_FORMAT must be "pretty" or "json"` | Fix the value. |
| `DASHBOARD_URL needs DASHBOARD_TOKEN: the secret the main app and its microservices share` | Set the same `DASHBOARD_TOKEN` on the main app and the microservice (`MICROSERVICES` says the same). |
| `DASHBOARD_URL needs OTEL_SERVICE_NAME: this microservice's name, as the main app's MICROSERVICES lists it` | Name the service. |
| `MICROSERVICES is a list of name=url, like orders=http://orders:3000,billing=http://billing:3000; got "orders"` | Give each service its address. |
| `FUNCTION_TIMEOUT_MS must be an integer ≥ 1, got "0"` | The same shape for every integer variable: `<NAME> must be an integer ≥ <min>, got "<value>"`. |
| `REDIS_URL is set but Redis is unreachable: Connection closed` | Check the host, port and that Redis is up. |

Failures after these checks come from the database itself: a Postgres URL with the wrong password prints `password authentication failed for user "forge"`, a missing database `database "nosuchdb" does not exist`, and an unresolvable host just `Failed to connect`. A schema mismatch prints `Stored documents don't match the schema (fix them with a migration, or set SCHEMA_CHECK=off):` followed by up to ten documents. [Troubleshooting](troubleshooting.html) walks through each.

## archlast-forge.json

This file in the project root says how the project is built and run. `archlast-forge init` writes it; the CLI and the scaffolder both read it.

```json
{
  "mode": "framework",
  "services": ["postgres", "redis"]
}
```

| Key | Values | Meaning |
|---|---|---|
| `mode` | `"framework"` or `"backend"` | A full-stack app (React pages, server rendering and the backend in one engine) or a backend only. |
| `services` | a list of `"postgres"`, `"redis"`, `"s3"`, `"caddy"`; default `[]` | What `dev` starts in Docker (`caddy` is for production only) and what `compose.yaml` and `.env` were generated for. |

`init` gives a full-stack app `postgres`, `redis`, `s3` and `caddy`, and a backend `postgres`, `redis` and `s3`; pass `--services none` for SQLite with an in-memory bus and cache. A file without `services` means none. Changing `services` afterwards changes what `dev` starts but does not rewrite `compose.yaml`, which is yours to edit. `dev --with postgres,redis` overrides the list for one run.

The file is validated, and a mistake says what to change:

```
archlast-forge.json: "mode" must be "framework" or "backend" (got "fullstack")
archlast-forge.json: unknown service "mysql"; choose from postgres, redis, s3, caddy
archlast-forge.json isn't valid JSON: …
```

A project without the file behaves as a backend with no services.

## Variables for your functions

Your functions read configuration from `process.env`, like any Bun program:

```ts
const key = process.env.EMAIL_API_KEY;
if (!key) throw new Error("EMAIL_API_KEY is not set"); // a bug: callers see "Server error (request …)"
```

There are two places to define them.

- **The engine's environment.** The same variables as everything above: your shell, `.env`, `compose.yaml`, your platform's secret store. Every variable of the process is visible to your functions, including `BETTER_AUTH_SECRET` and `DATABASE_URL`.
- **The `_env` table**, managed with the CLI. Values are stored in the database, so they travel with it (a backup includes them) and can be changed without rebuilding the image.

```bash
archlast-forge env set EMAIL_API_KEY re_12345       # create or change
archlast-forge env list                              # NAME=value, one per line
archlast-forge env get EMAIL_API_KEY
archlast-forge env rm EMAIL_API_KEY
```

Names must match `[A-Za-z_][A-Za-z0-9_]*`. The commands talk to the running server (so `ADMIN_KEY` must match; in dev the saved dev key is used), and open the database themselves when none is running. Setting or removing a value is written to the audit log, never its value.

Know these rules:

- **The process environment wins.** At startup the function runtime copies each `_env` row into `process.env` only if that name is not already set. A variable in `.env` or `compose.yaml` therefore overrides `env set` for the same name.
- **Applying a change.** `env set` and `env rm` ask the running engine to reload its function runtime (the CLI sends `SIGHUP` to the container, or calls the admin reload endpoint of a local server), and the reload applies the change: a changed value is replaced, a removed one is unset. A variable that was in the process environment before the engine started (set in `compose.yaml`, a shell or `.env`) always wins and is never touched. On `0.1.0` a reload in production only picked up variables that were new, so restart after changing or removing one. With `DASHBOARD` off, a local `start --no-docker` server has no reload endpoint at all, and the CLI says `(no running server picked it up; it applies on next start)`.
- **Values are not hidden from the dashboard's owner.** The Settings page lists names only, but `env list` prints values to anyone who has the admin key. Treat `_env` as being as sensitive as the database.
- **Keep engine settings out of `_env`.** The engine reads `PORT`, `BETTER_AUTH_SECRET` and the rest before the database is open, so a value stored here never reaches them.

Reading variables inside a query is fine, but remember the [query cache](caching.html): a result that depends on `process.env` is cached for up to `CACHE_TTL_MS`. A reload empties the cache.

## Examples

### A small deployment

One server, SQLite on a volume, Caddy or another proxy for HTTPS. This is the shape `init --services caddy` produces. Put it in `.env` next to `compose.yaml`:

```bash
BETTER_AUTH_SECRET=3f1c0e…                 # openssl rand -hex 32
ADMIN_KEY=9a47d2…                          # openssl rand -hex 24
BETTER_AUTH_URL=https://app.example.com
DOMAIN=app.example.com
```

With Caddy in the stack, `compose.yaml` already sets `TRUST_PROXY=1` and `TRUSTED_ORIGINS=https://${DOMAIN}`. The data is in the `app-data` volume; take a copy with `archlast-forge backup app.db`. Leave `DASHBOARD` at its default only if you want the dashboard reachable behind the admin key; otherwise add `DASHBOARD=off`.

Without compose, the same server as a plain environment file for `start --image`:

```bash
BETTER_AUTH_SECRET=3f1c0e…
ADMIN_KEY=9a47d2…
BETTER_AUTH_URL=https://app.example.com
TRUST_PROXY=1
DASHBOARD=off
LOG_FORMAT=json
```

### A scaled deployment

Three servers behind a load balancer, with Postgres and Redis shared. Every server gets the same file:

```bash
BETTER_AUTH_SECRET=3f1c0e…                      # the same on every server
ADMIN_KEY=9a47d2…
BETTER_AUTH_URL=https://app.example.com
TRUSTED_ORIGINS=https://www.example.com         # only if another origin calls the API

DATABASE_URL=postgres://forge:…@db.internal:5432/forge
REDIS_URL=redis://redis.internal:6379
REPLICAS=3                                      # fails at startup if the two lines above are missing

S3_ENDPOINT=http://rustfs.internal:9000
S3_PUBLIC_ENDPOINT=https://files.example.com
S3_BUCKET=forge
S3_ACCESS_KEY_ID=…
S3_SECRET_ACCESS_KEY=…
S3_REGION=us-east-1

TRUST_PROXY=1                                   # the load balancer overwrites X-Forwarded-For
RATE_LIMIT_PER_MINUTE=1200                      # counted across all servers through Redis
IDLE_TIMEOUT_SECONDS=90                         # above the load balancer's upstream keep-alive
DASHBOARD=off
OTEL_EXPORTER_OTLP_ENDPOINT=http://otel-collector.internal:4318
```

Points that matter at this size:

- The load balancer must pass WebSocket upgrades on `/rpc`. Sticky sessions are not needed.
- `/ready` is the readiness probe; `SIGTERM` drains a server and closes its sockets with code 1012, so clients reconnect to another one.
- Only the first runtime process of each server runs the scheduler. Cron runs are inserted once across servers, because every server computes the same id for a run.
- `REPLICAS` starts nothing. It only makes the engine refuse to start without Redis and Postgres.
- Scrape `/metrics` with the `METRICS_TOKEN` bearer token on each server.
