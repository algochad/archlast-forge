# Monorepos and microservices

`init` can lay a project out as a [Turborepo](https://turborepo.com) monorepo: the app in `apps/`, backends beside it that serve as microservices, and the main app's typed API shared from `packages/api`. A project that exists becomes one with [`archlast-forge monorepo`](#turn-a-project-into-a-monorepo), and services and apps are [added and removed](#add-and-remove) later.

```bash
bun create archlast-forge acme --monorepo
bun create archlast-forge acme --microservices orders,billing   # implies --monorepo; the services talk Forge RPC
```

```
acme/
  package.json        workspaces apps/* and packages/*; scripts dev, build, typecheck (turbo run …), upgrade, workspace, format
  turbo.json          dev (persistent, no cache), build, typecheck (after the packages it depends on)
  apps/
    web/              the main app, as init makes it (--mode framework; apps/api with --mode backend)
    orders/           a backend: the orders microservice
    billing/          a backend: the billing microservice
  packages/
    api/              @acme/api: the main app's api object and data model types (each other app's: @acme/api/<app>)
    contracts/        @acme/contracts: the services' Forge RPC types, for the backends that call them (--transport forge-rpc, the default)
```

Every app is a whole archlast-forge project with its own `forge/`, `compose.yaml`, `Dockerfile` and `.env`. Each can be [deployed independently](#deploying). A backend main app's package is `@acme/backend`, because `@acme/api` is `packages/api`.

## Develop from the workspace root

`bun run dev` starts the apps through Turbo and each Forge engine watches its own source. Forge RPC workspaces run native engines and default to SQLite. Set `mainPort`, app `port` and service `rpcPort` in [the workspace file](#the-workspace-file). Turbo starts declared dependencies even in a filtered run such as `bun run dev --filter=@acme/web`. Forge waits for their readiness, and reports which app is unavailable or which port is occupied.

Development configuration comes from each app's private `.env.development.local`. It does not inherit stack `.env` files or application settings exported at the root. Set `DATABASE_URL`, `REDIS_URL` or `S3_…` there to use development infrastructure you run yourself. To have Forge start and stop development containers, set `FORGE_DEV_SERVICES` to a comma-separated selection of `postgres,redis,s3` in that app's profile. Forge uses the selected containers' connection settings and keeps their volumes on shutdown. `bun run up` in an app still uses its deployment stack.

Each app keeps its database and development signing and admin keys under `forge/data`, or the `DATA_DIR` in its development profile. Use separate data locations and external databases for each app. Local RPC credentials are stable and scoped to the receiving service. Forge supplies each declared caller with `<SERVICE>_RPC_URL` and `<SERVICE>_RPC_TOKEN`. The dashboard uses its own credential. Deployment credentials stay in the deployment environment.

To run an application-owned startup task, add a `forge:seed` script to that app's `package.json`. Forge runs it once per development start after the app and its dependencies are ready, with `FORGE_DEV_URL` and the app's development configuration available. Make the script idempotent. Keep it out of deployment scripts. Use `bun run workspace status` to see addresses, readiness, database mode, data locations and the state of generated contracts.

From the root, `bun run typecheck` and `bun run build` run producer codegen before consumers use its output. `bun run upgrade [version]` uses the root's project-local CLI to update the workspace, regenerate contracts and refresh the lockfile. For an older workspace, use a recent Forge CLI to run `archlast-forge workspace sync` once. Move existing development settings you still need to the app's private development profile. Dev sessions previously signed with deployment keys may require signing in again.

## Shared types

`packages/api` (named `@<project>/api`) re-exports the main app's generated `api` and data model, so whatever is the main app's client, such as its pages, a [mobile](mobile.html) or a [desktop](desktop.html) app, calls it typed:

```ts
import { webApi, type Web } from "@acme/api";

const client = new ArchlastForgeClient({ url: "http://localhost:3000" });
await client.query(webApi.messages.list, { paginationOpts: { numItems: 20, cursor: null } });
```

- **Services aren't in it.** Clients call the main app, and the main app calls its services over a transport, with [their own types](forge-rpc.html#its-types-forgegeneratedrpcts).
- **Another app has a file of its own:** `import { adminApi } from "@acme/api/admin"`.
- **A TypeScript project imports the types of one backend.** The types each backend generates declare the global `Register` with its schema, so two backends' types in one project collide (`TS2717`). Each app already has its own project, and so does a mobile or a desktop app: it imports `@acme/api`, the main app's, and no other.

## Turn a project into a monorepo

```bash
cd my-app
archlast-forge monorepo --microservices orders --yes
```

`archlast-forge monorepo` makes the project in the current folder the main app of a monorepo, in place. Its files move to `apps/web` (or `apps/api` for a backend), the monorepo's own files are written around them, and the services you name are added as `init --microservices` adds them. `.env`, the data, `compose.yaml` (with the Docker project name it already has, so a running stack keeps its volumes), the lockfile and the Git history all come along, and your code isn't reformatted. `--dry-run` shows the plan first. [The CLI reference](cli.html#monorepo) has the details.

## Add and remove

From any folder of the monorepo:

```bash
archlast-forge add service billing      # apps/billing, and a class in the main app that calls it
archlast-forge add app admin            # another full-stack app (--mode backend for a backend)
archlast-forge add mobile               # an Expo app, a client of the main app
archlast-forge add desktop client       # a Tauri app: full, or client
archlast-forge remove billing           # a service or app, or mobile or desktop
archlast-forge workspace                # what is here, and on which ports
```

Each takes the next free ports, runs `bun install` and codegen, and says what is left for you. A service is made exactly as `init` makes one: the main app gets `forge/<service>.service.ts` (the class that calls it), `forge/<service>.controller.ts` and `forge/<service>.ts` (the action), and `forge/_services.ts`, which lists them for the one `nest()` call in `forge/http.ts`. `_services.ts` is written by the commands, so adding a third service doesn't touch `http.ts`. If `http.ts` already has a `nest()` call of its own, the command tells you which two lists to add to it.

`add` stops before writing anything when a name is taken, or when a file in the main app would be overwritten. [The CLI reference](cli.html#add) lists what each writes.

## The workspace file

`archlast-forge.workspace.json` at the root records what the commands need:

```json
{
  "main": "web",
  "transport": "forge-rpc",
  "apps": {
    "orders": { "kind": "service", "port": 3001, "rpcPort": 4001 },
    "admin": { "kind": "app", "port": 3002 }
  },
  "mobile": true
}
```

`main` is the folder of the main app: `web` or `api` in a monorepo `init` made, any name in one made by hand. `scope`, when it is there, is what the packages are scoped with (`@<scope>/api`) in place of the root package's name. A service is called by the main app over `transport`; an app is a project of its own. `port` is where `dev` serves it on this machine, and `rpcPort` the service's port for the transport. A monorepo made before this file existed has it worked out from its folders, and the first change writes it. `archlast-forge workspace sync` rewrites the shared packages after changes you made by hand.

`mainPort` defaults to 3000. In a Forge RPC workspace, `dependsOn` maps an app name to the services it calls. The main app calls all services by default. Other apps have no dependencies until declared. For example, `"dependsOn": { "web": ["orders"], "orders": ["billing"] }` starts Billing with Orders and Orders with Web, including filtered runs. It supplies the corresponding development addresses and tokens. Add the typed client in each caller's backend code as shown in [Forge RPC](forge-rpc.html#a-service-class-that-makes-the-calls). Run `bun run workspace sync` after editing the workspace file to refresh the Turbo tasks and shared contracts.

## A monorepo made by hand

A monorepo that was set up without these commands, with a main app called `medico` or `ward`, joins them with its record:

```json
{ "main": "ward", "scope": "hospital", "transport": "forge-rpc", "apps": {} }
```

Save that as `archlast-forge.workspace.json` at the root and run `archlast-forge workspace sync`. It writes `packages/api` (`@hospital/api`, with `wardApi`), naming each app's package as its own `package.json` does. After that `add mobile`, `add desktop`, `add service` and `workspace` work as they do in a monorepo `init` made. Without the file, a lone app with an `archlast-forge.json` is taken for the main app, and with several the command asks you to say which.

## One Redis for several apps

The apps of a monorepo may share a Redis (and a Postgres server): the engine puts everything it keeps in Redis (the query cache, the topics that wake subscriptions, the rate limits) under a prefix from the app's name, so `orders` and `billing` don't see each other's cached `messages:list` or wake each other's live queries. `init`, `add app`, `add service` and `workspace sync` give every app its own `OTEL_SERVICE_NAME` (its folder's name), and that name is the prefix, `archlast-forge:orders:`. Nothing needs configuring, and it holds when you scale: every server of `orders` has the same name, so they share their keys, while `billing`, a different service, has its own. Set `REDIS_PREFIX` on an app to name the prefix yourself. Each app still has its own database, because the data of a service is private to it. Each app's `compose.yaml` passes `OTEL_SERVICE_NAME` and `REDIS_PREFIX` on from its `.env` (a `compose.yaml` from before that doesn't: add them under `environment:`), so a shared Redis in production needs nothing more than the `.env` the commands wrote.

## One dashboard

The main app's dashboard is the monorepo's: each service sends its telemetry there and serves no dashboard of its own, so requests, traces, errors, logs, [nodes](observability.html#nodes) and Nest classes of every app are on one set of pages, and with a service picked in the top bar its data, schema and functions are too. `init`, `add service`, `remove` and `workspace sync` keep the apps' `.env` in step: `MICROSERVICES` in the main app, `DASHBOARD_URL` and `OTEL_SERVICE_NAME` in each service, and the `DASHBOARD_TOKEN` they share. A monorepo made with 0.15.0 or before gets them from `archlast-forge workspace sync`. Deployed with Docker on one machine, each app's `compose.override.yaml` gives them the addresses on the monorepo's network ([Deploying](#deploying)); see also [one dashboard](observability.html#one-dashboard-for-a-main-app-and-its-microservices).

## Services calling services

By default (`--transport forge-rpc`) each service serves a [Forge RPC](forge-rpc.html) router: typed calls between forge apps. The service declares it with decorators:

```ts
// apps/orders/forge/orders.router.ts
@Router({ alias: "orders" })
export class OrdersRouter {
  @Mutation({ input: z.object({ from: z.string() }), output: z.object({ service: z.string(), greeting: z.string(), calls: z.number() }) })
  async hello(@Input("from") from: string, @Ctx() ctx: ActionCtx) {
    const calls = await ctx.runMutation(internal.calls.record, { from });
    return { service: "orders", greeting: `Hello, ${from}`, calls };
  }
}
```

The service serves the router in its `forge/http.ts`, with `new ForgeRpcServer({ port: Number(process.env.ORDERS_RPC_PORT ?? 4001) })` in `nest()`'s `microservices`. Its codegen writes the router's types to `forge/_generated/rpc.ts`, and `packages/contracts` re-exports them.

The main app calls each service from a class: a Nest service that holds the typed client and makes the calls. A controller and an action both use it:

```ts
// apps/web/forge/orders.service.ts
@Injectable()
export class OrdersService {
  private readonly orders = createForgeRpcClient<OrdersRpc>({ url: process.env.ORDERS_RPC_URL ?? "http://127.0.0.1:4001" });

  hello(from: string) {
    return this.orders.orders.hello.mutate({ from });
  }
}

// apps/web/forge/orders.controller.ts: POST /http/orders/hello
@Controller("orders")
export class OrdersController {
  constructor(private readonly orders: OrdersService) {}

  @Post("hello")
  hello(@Body() body: { from: string }) {
    return this.orders.hello(body.from);
  }
}

// apps/web/forge/orders.ts: api.orders.hello, for pages and other functions
export const hello = action({
  args: { from: v.string() },
  handler: async (ctx, { from }) => (await inject(ctx, OrdersService)).hello(from),
});
```

`forge/http.ts` mounts them with `nest(http, { controllers: [OrdersController], providers: [OrdersService] })`. [Calling it](forge-rpc.html#calling-it) covers the class in detail, along with `ClientsModule` and other providers that use it.

The backends share `FORGE_RPC_TOKEN`, which the scaffold writes to each one's `.env`.

Forge RPC is backend to backend only. The pages of `apps/web`, `apps/mobile` and `apps/desktop` call the main app (`api.orders.hello` or `POST /http/orders/hello` here), and the main app's `OrdersService` calls the service. They never import `@acme/contracts` or a service's address, and they never hold the token. See [Forge RPC](forge-rpc.html#backend-to-backend-only) for the checks that enforce it.

With `--transport tcp`, `redis` or `nats`, each service instead listens with that [NestJS transport](nest.html#microservices), in its `forge/http.ts`, and answers a message pattern with a controller that uses its own database:

```ts
// apps/orders/forge/orders.controller.ts
@Controller()
export class OrdersController {
  @MessagePattern("orders.hello")
  async hello(@Payload() data: { from: string }, @Ctx() ctx: ActionCtx) {
    const calls = await ctx.runMutation(internal.calls.record, { from: data.from });
    return { service: "orders", greeting: `Hello, ${data.from}`, calls };
  }
}
```

The main app has the same three files. Only the service class differs: it sends a message through a Nest client that connects on first use:

```ts
// apps/web/forge/orders.service.ts
@Injectable()
export class OrdersService {
  private readonly client = ClientProxyFactory.create({ transport: Transport.TCP, options: { host: process.env.ORDERS_HOST ?? "127.0.0.1", port: Number(process.env.ORDERS_PORT ?? 4001) } });

  hello(from: string) {
    return rxjs.firstValueFrom(this.client.send<{ service: string; greeting: string; calls: number }>("orders.hello", { from }));
  }
}
```

With any transport, the main app answers both ways:

```bash
curl -X POST localhost:3000/rpc/orders:hello -H 'content-type: application/json' -d '{"from":"web"}'   # the action
# {"result":{"service":"orders","greeting":"Hello, web","calls":1}}
curl -X POST localhost:3000/http/orders/hello -H 'content-type: application/json' -d '{"from":"web"}'  # the controller
# {"service":"orders","greeting":"Hello, web","calls":2}
```

| Transport | Service listens on | Callers set | Needs |
|---|---|---|---|
| `forge-rpc` | `<SERVICE>_RPC_PORT` (4001, 4002, … in dev) on every interface | `<SERVICE>_RPC_URL`; the same `FORGE_RPC_TOKEN` in every app | nothing |
| `tcp` | `<SERVICE>_PORT` (4001, 4002, … in dev) on every interface | `<SERVICE>_HOST`, `<SERVICE>_PORT` | nothing |
| `redis` | the Redis at `MICROSERVICES_REDIS_URL` (default `redis://127.0.0.1:6379`) | the same URL | a Redis server; `ioredis` (added to each backend's `forge/package.json`) |
| `nats` | the NATS server at `MICROSERVICES_NATS_URL` (default `nats://127.0.0.1:4222`) | the same URL | a NATS server; `nats` (added to each backend) |

A service listens in the first function runtime process of its server, so a message is handled once per server. Deployed, every app is its own stack, and [Deploying](#deploying) puts the stacks on one network with the callers' addresses; for Redis or NATS, every app also needs `MICROSERVICES_REDIS_URL` or `MICROSERVICES_NATS_URL` pointing at the same broker.

## Deploying

Each app has its own stack, and `bun run up` (`archlast-forge up`) in its folder builds its image and starts it. Nothing runs at the monorepo's root:

```bash
(cd apps/orders && bun run up)
(cd apps/web && bun run up)
```

On one machine the stacks find each other. `init --monorepo`, `add`, `remove` and `workspace sync` write a `compose.override.yaml` beside each app's `compose.yaml` when the monorepo has services. Docker Compose merges that file in (so does `archlast-forge`, for `up`, `down`, `logs` and the data commands). It puts the app on the Docker network `<monorepo>-apps` under the app's name, so `orders` is `http://orders:3000` to the others, and gives each app what it needs to reach the others there:

| App | What `compose.override.yaml` sets |
|---|---|
| the main app | `<SERVICE>_RPC_URL=http://<service>:<rpc port>` (Forge RPC; `.env` can still set another), or `<SERVICE>_HOST` and `<SERVICE>_PORT` (TCP); `MICROSERVICES=<service>=http://<service>:3000,…` |
| each service | `DASHBOARD_URL=http://<main app>:3000` |
| every app | `FORGE_RPC_TOKEN` (Forge RPC) and `DASHBOARD_TOKEN` from its `.env`; `MICROSERVICES_REDIS_URL` or `MICROSERVICES_NATS_URL` from its `.env` for those transports, which `up` refuses to start without |

`.env` keeps the development addresses (`localhost`), which `bun run dev` uses. The file's values win over `compose.yaml`'s, and the commands write it again whenever the apps change. To change it, delete its first line (`# Written by archlast-forge…`), which makes the file yours, and the commands leave it alone. For apps on several machines, make it yours and put in the addresses the apps reach each other at, and expose each service's transport port to its callers only. On another orchestrator, set the same variables there.
