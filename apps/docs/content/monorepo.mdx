# Monorepos and microservices

`init` can lay a project out as a [Turborepo](https://turborepo.com) monorepo: the app in `apps/`, backends beside it that serve as microservices, and the main app's typed API shared from `packages/api`. A project that exists becomes one with [`archlast-forge monorepo`](#turn-a-project-into-a-monorepo), and services and apps are [added and removed](#add-and-remove) later.

```bash
bun create archlast-forge acme --monorepo
bun create archlast-forge acme --microservices orders,billing   # implies --monorepo; the services talk Forge RPC
```

```
acme/
  package.json        workspaces apps/* and packages/*; scripts dev, build, typecheck (turbo run …), format
  turbo.json          dev (persistent, no cache), build, typecheck (after the packages it depends on)
  apps/
    web/              the main app, as init makes it (--mode framework; apps/api with --mode backend)
    orders/           a backend: the orders microservice
    billing/          a backend: the billing microservice
  packages/
    api/              @acme/api: the main app's api object and data model types (each other app's: @acme/api/<app>)
    contracts/        @acme/contracts: the services' Forge RPC types, for the backends that call them (--transport forge-rpc, the default)
```

Every app is a whole archlast-forge project, made as `init` makes one: its own `forge/`, `compose.yaml`, `Dockerfile` and `.env`, deployed on its own. `bun run dev` at the root starts them all (`turbo run dev`): the main app on port 3000, the services on 3001, 3002 and so on, on this machine (`--no-docker`) so they reach each other's transports. `bun run typecheck` runs each app's codegen and `tsc`, then `packages/api`'s. A backend main app's package is `@acme/backend`, because `@acme/api` is `packages/api`.

## Shared types

`packages/api` (named `@<project>/api`) re-exports the main app's generated `api` and data model, so whatever is the main app's client, such as its pages, a [mobile](mobile.html) or a [desktop](desktop.html) app, calls it typed:

```ts
import { webApi, type Web } from "@acme/api";

const client = new ArchlastForgeClient({ url: "http://localhost:3000" });
await client.query(webApi.messages.list, { paginationOpts: { numItems: 20, cursor: null } });
```

- **Services aren't in it.** Clients call the main app, and the main app calls its services over a transport, with [their own types](forge-rpc.html#its-types-forgegeneratedrpcts).
- **Another app has a file of its own:** `import { adminApi } from "@acme/api/admin"`.
- **A TypeScript project imports the types of one backend.** The types each backend generates declare the global `Register` with its schema, so two backends' types in one project collide (`TS2717`). Each app already has its own project, and so does a mobile or a desktop app: it imports `@acme/api`, the main app's, and no other.

## Turn a project into a monorepo

```bash
cd my-app
archlast-forge monorepo --microservices orders --yes
```

`archlast-forge monorepo` makes the project in the current folder the main app of a monorepo, in place. Its files move to `apps/web` (or `apps/api` for a backend), the monorepo's own files are written around them, and the services you name are added as `init --microservices` adds them. `.env`, the data, `compose.yaml` (with the Docker project name it already has, so a running stack keeps its volumes), the lockfile and the Git history all come along, and your code isn't reformatted. `--dry-run` shows the plan first. [The CLI reference](cli.html#monorepo) has the details.

## Add and remove

From any folder of the monorepo:

```bash
archlast-forge add service billing      # apps/billing, and a class in the main app that calls it
archlast-forge add app admin            # another full-stack app (--mode backend for a backend)
archlast-forge add mobile               # an Expo app (a backend main app)
archlast-forge add desktop client       # a Tauri app: full, or client
archlast-forge remove billing           # a service or app, or mobile or desktop
archlast-forge workspace                # what is here, and on which ports
```

Each takes the next free ports, runs `bun install` and codegen, and says what is left for you. A service is made exactly as `init` makes one: the main app gets `forge/<service>.service.ts` (the class that calls it), `forge/<service>.controller.ts` and `forge/<service>.ts` (the action), and `forge/_services.ts`, which lists them for the one `nest()` call in `forge/http.ts`. `_services.ts` is written by the commands, so adding a third service doesn't touch `http.ts`. If `http.ts` already has a `nest()` call of its own, the command tells you which two lists to add to it.

`add` stops before writing anything when a name is taken, or when a file in the main app would be overwritten. [The CLI reference](cli.html#add) lists what each writes.

## The workspace file

`archlast-forge.workspace.json` at the root records what the commands need:

```json
{
  "main": "web",
  "transport": "forge-rpc",
  "apps": {
    "orders": { "kind": "service", "port": 3001, "rpcPort": 4001 },
    "admin": { "kind": "app", "port": 3002 }
  },
  "mobile": true
}
```

`main` is `web` or `api`. A service is called by the main app over `transport`; an app is a project of its own. `port` is where `dev` serves it on this machine, and `rpcPort` the service's port for the transport. A monorepo made before this file existed has it worked out from its folders, and the first change writes it. `archlast-forge workspace sync` rewrites the shared packages after changes you made by hand.

## Services calling services

By default (`--transport forge-rpc`) each service serves a [Forge RPC](forge-rpc.html) router: typed calls between forge apps. The service declares it with decorators:

```ts
// apps/orders/forge/orders.router.ts
@Router({ alias: "orders" })
export class OrdersRouter {
  @Mutation({ input: z.object({ from: z.string() }), output: z.object({ service: z.string(), greeting: z.string(), calls: z.number() }) })
  async hello(@Input("from") from: string, @Ctx() ctx: ActionCtx) {
    const calls = await ctx.runMutation(internal.calls.record, { from });
    return { service: "orders", greeting: `Hello, ${from}`, calls };
  }
}
```

The service serves the router in its `forge/http.ts`, with `new ForgeRpcServer({ port: Number(process.env.ORDERS_RPC_PORT ?? 4001) })` in `nest()`'s `microservices`. Its codegen writes the router's types to `forge/_generated/rpc.ts`, and `packages/contracts` re-exports them.

The main app calls each service from a class: a Nest service that holds the typed client and makes the calls. A controller and an action both use it:

```ts
// apps/web/forge/orders.service.ts
@Injectable()
export class OrdersService {
  private readonly orders = createForgeRpcClient<OrdersRpc>({ url: process.env.ORDERS_RPC_URL ?? "http://127.0.0.1:4001" });

  hello(from: string) {
    return this.orders.orders.hello.mutate({ from });
  }
}

// apps/web/forge/orders.controller.ts: POST /http/orders/hello
@Controller("orders")
export class OrdersController {
  constructor(private readonly orders: OrdersService) {}

  @Post("hello")
  hello(@Body() body: { from: string }) {
    return this.orders.hello(body.from);
  }
}

// apps/web/forge/orders.ts: api.orders.hello, for pages and other functions
export const hello = action({
  args: { from: v.string() },
  handler: async (ctx, { from }) => (await inject(ctx, OrdersService)).hello(from),
});
```

`forge/http.ts` mounts them with `nest(http, { controllers: [OrdersController], providers: [OrdersService] })`. [Calling it](forge-rpc.html#calling-it) covers the class in detail, along with `ClientsModule` and other providers that use it.

The backends share `FORGE_RPC_TOKEN`, which the scaffold writes to each one's `.env`.

Forge RPC is backend to backend only. The pages of `apps/web`, `apps/mobile` and `apps/desktop` call the main app (`api.orders.hello` or `POST /http/orders/hello` here), and the main app's `OrdersService` calls the service. They never import `@acme/contracts` or a service's address, and they never hold the token. See [Forge RPC](forge-rpc.html#backend-to-backend-only) for the checks that enforce it.

With `--transport tcp`, `redis` or `nats`, each service instead listens with that [NestJS transport](nest.html#microservices), in its `forge/http.ts`, and answers a message pattern with a controller that uses its own database:

```ts
// apps/orders/forge/orders.controller.ts
@Controller()
export class OrdersController {
  @MessagePattern("orders.hello")
  async hello(@Payload() data: { from: string }, @Ctx() ctx: ActionCtx) {
    const calls = await ctx.runMutation(internal.calls.record, { from: data.from });
    return { service: "orders", greeting: `Hello, ${data.from}`, calls };
  }
}
```

The main app has the same three files. Only the service class differs: it sends a message through a Nest client that connects on first use:

```ts
// apps/web/forge/orders.service.ts
@Injectable()
export class OrdersService {
  private readonly client = ClientProxyFactory.create({ transport: Transport.TCP, options: { host: process.env.ORDERS_HOST ?? "127.0.0.1", port: Number(process.env.ORDERS_PORT ?? 4001) } });

  hello(from: string) {
    return rxjs.firstValueFrom(this.client.send<{ service: string; greeting: string; calls: number }>("orders.hello", { from }));
  }
}
```

With any transport, the main app answers both ways:

```bash
curl -X POST localhost:3000/rpc/orders:hello -H 'content-type: application/json' -d '{"from":"web"}'   # the action
# {"result":{"service":"orders","greeting":"Hello, web","calls":1}}
curl -X POST localhost:3000/http/orders/hello -H 'content-type: application/json' -d '{"from":"web"}'  # the controller
# {"service":"orders","greeting":"Hello, web","calls":2}
```

| Transport | Service listens on | Callers set | Needs |
|---|---|---|---|
| `forge-rpc` | `<SERVICE>_RPC_PORT` (4001, 4002, … in dev) on every interface | `<SERVICE>_RPC_URL`; the same `FORGE_RPC_TOKEN` in every app | nothing |
| `tcp` | `<SERVICE>_PORT` (4001, 4002, … in dev) on every interface | `<SERVICE>_HOST`, `<SERVICE>_PORT` | nothing |
| `redis` | the Redis at `MICROSERVICES_REDIS_URL` (default `redis://127.0.0.1:6379`) | the same URL | a Redis server; `ioredis` (added to each backend's `forge/package.json`) |
| `nats` | the NATS server at `MICROSERVICES_NATS_URL` (default `nats://127.0.0.1:4222`) | the same URL | a NATS server; `nats` (added to each backend) |

A service listens in the first function runtime process of its server, so a message is handled once per server. In production every app is its own stack: for Forge RPC or TCP, put the stacks on one network and give callers the services' hosts and ports; for Redis or NATS, point every app at the same broker.
