# Mobile apps

`init --mobile` adds a React Native app made with [Expo](https://expo.dev) to a backend or a full-stack app: a client that calls its functions and keeps queries live, typed from its generated API. Both serve the same `/rpc` and sign-in, so the app doesn't care which it talks to, and `add mobile` ([CLI](cli.html#add)) adds it later. It never runs the engine: the pages and functions stay in the main app, so `--mobile` goes with either `--mode backend` or `--mode framework` and the app is a client of whichever you made.

```bash
bun create archlast-forge acme --mode backend --mobile        # implies --monorepo
cd acme && bun install && bun run dev                          # start the backend and Expo
```

```
acme/
  apps/api/           the backend (apps/web/ for a full-stack app), with Better Auth's Expo plugin in forge/auth.ts
  apps/mobile/        the Expo app: App.tsx (sign-in, a live chat), src/client.ts, app.json, .env
  packages/api/       the backend's typed API, which the app imports types from
```

## Run on Android

From the workspace root:

```bash
bun run archlast-forge mobile doctor
bun run archlast-forge mobile setup
bun run archlast-forge dev --mobile
```

Connect and unlock a USB phone with USB debugging enabled. Accept its authorization prompt. Forge prefers a ready USB phone, then an already-running Waydroid session on Linux Wayland, then a managed Android Emulator. If several USB phones are ready, pick one with `--device <serial>`. Use `--target device`, `--target waydroid`, or `--target emulator` to choose explicitly. The same target flags apply to `mobile setup`. `mobile doctor` reports host tools, devices, app delivery, port use and emulator acceleration without starting an ADB server or runtime.

`mobile setup --target device` can install ADB when it is missing. `mobile setup --target emulator` also installs Google's emulator and system image. Forge supports its portable SDK on Linux x64, Windows x64, and Intel or Apple silicon macOS. Linux needs KVM access, Windows needs firmware virtualization and Windows Hypervisor Platform, and macOS uses Hypervisor.Framework. A compatible ADB already on your PATH can also drive a physical device. Forge uses a running Waydroid installation and its reported network address. If Waydroid cannot report an address, connect with its documented [ADB workflow](https://docs.waydro.id/faq/using-adb-with-waydroid), then pass its serial. ARM-only APKs need a compatible ABI on Waydroid.

Setup prints the packages and a disk-space estimate. Forge pins the command-line tools and portable Temurin 17 with SHA-256 checksums. Google's SDK Manager checks its own package downloads. Forge keeps the tools, verified archives, and temporary emulator profiles under its per-user data directory. Set `FORGE_HOME` to choose a different directory. License prompts are interactive unless you supply both `--yes --accept-licenses` after reviewing the [Android SDK terms](https://developer.android.com/studio/terms). Java and SDK paths are supplied to the tools that need them.

### Ports and app delivery

`dev --mobile` starts the main Forge app and its declared services through Turbo. It selects a Metro port, keeps the workspace's main HTTP port by default, and maps both ports on the selected device with ADB reverse. The device reaches Forge at its forwarded `127.0.0.1` address. Expo receives that value as `EXPO_PUBLIC_API_URL` for the session. Forge uses direct HTTP for this session, including when the normal desktop workflow uses a local reverse proxy. Browser development remains available through the ordinary `bun run dev` command.

The command opens Expo Go and installs a verified SDK 58 APK when Expo Go is missing. If a device has Expo Go for a different SDK, install the matching version from [Expo](https://expo.dev/go). Use `--client dev-client --apk <path>` with an Android development build that contains `expo-dev-client`. The app's Android package and scheme come from `apps/mobile/app.json`. For local HTTP, enable cleartext loopback access in the development build. A preinstalled matching development client can be used without the APK flag.

Ctrl-C stops the Forge tasks, Metro, and any emulator Forge started for that session. ADB mappings created by the session are removed. Shared ADB servers and existing Waydroid sessions keep running. Forge leaves the project's `.env` files alone.

### Project defaults

Existing workspaces keep `"mobile": true`. An optional `mobileDev` object in `archlast-forge.workspace.json` can set the target, system image API and ABI, AVD profile, client and ports.

```json
{
  "target": "auto",
  "api": 36,
  "profile": "pixel_7",
  "client": "go",
  "backendPort": 3000
}
```

The example is the value of `mobileDev`. The emulator uses the host-compatible ABI by default. Set `abi` to `x86_64` or `arm64-v8a`, and `metroPort` to pin Metro. CLI overrides include `--android-api`, `--android-abi`, `--avd-profile`, `--backend-port` and `--metro-port`. Pass device serials and APK paths when starting a session so workspace configuration stays portable.

iOS Simulator orchestration is a follow-up. On macOS, start Expo in `apps/mobile` and open it from Xcode Simulator. For a device outside a managed session, set `EXPO_PUBLIC_API_URL` to a device-reachable backend. A production build uses the deployed HTTPS API.

## Expo and React Native Reusables

Both `init --mobile` and `add mobile` use the Expo SDK 58 blank TypeScript baseline generated with `create-expo-app`. The starter has NativeWind, Metro and Tailwind configuration, theme tokens, the `@/` alias, `components.json`, and `PortalHost`. The sign-in and chat screens use the generated React Native Reusables button, card, input, and text components.

From `apps/mobile`, use `bunx @react-native-reusables/cli@0.7.1 add <component>` to add a component. Use `bunx expo install <package>` for Expo native modules, `bun run doctor` to check the project, and `bun run export:android` to smoke-test the Android bundle.

## Signing in

Browsers carry the session in a cookie; a native app keeps it in the device's **secure storage** (Keychain on iOS, Keystore on Android) with [Better Auth's Expo plugin](https://www.better-auth.com/docs/integrations/expo), and sends it with every call:

```ts
// apps/mobile/src/client.ts
export const client: ArchlastForgeClient = new ArchlastForgeClient({
  url: process.env.EXPO_PUBLIC_API_URL ?? "http://localhost:3000",
  authPlugins: [expoClient({ scheme: "acme", storagePrefix: "acme", storage: SecureStore })],
  headers: () => {
    const cookie = (client.auth as unknown as { getCookie(): string }).getCookie();
    return cookie ? { cookie } : undefined;
  },
});
```

```ts
// apps/api/forge/auth.ts
export default defineAuth({ emailAndPassword: { enabled: true }, plugins: [expo()], trustedOrigins: ["acme://"] });
```

- `client.auth.signIn.email(...)`, `signUp.email(...)` and `signOut()` work as in a browser; the plugin stores the session and sends it to `/api/auth`.
- [`headers`](clients.html#constructor) adds the session to every function call and to the live socket's handshake (React Native's WebSocket takes headers; a browser's can't), so `ctx.auth` sees the user in queries, mutations and live queries.
- A Better Auth plugin turns off the engine's faster session check (see [Authentication](auth.html#customizing-with-forgeauthts)): about a millisecond per signed-in call instead of a few hundredths.

## Live queries and the background

Live queries share one WebSocket, as on the web, and reconnect with backoff when it drops. When the app comes back to the foreground the template opens a fresh socket (`AppState` → `client.reconnect()`), because the system may have closed the old one while the app slept; every live query subscribes again and refetches, so the screen catches up.

## Offline

Nothing is stored on the device, and there is no offline store in the client:

- While the connection is down, screens keep the last data their queries had (live queries come back with fresh data when it returns).
- Calls fail while offline: `useMutation` and `client.query` reject, and nothing is queued for later. Retry when the connection is back, or keep your own queue.

## Types

`src/client.ts` types `api` from the backend with a type-only import (`import type { apiApi } from "@acme/api"`) over `anyApi`, so the app never bundles the backend's code, and its types follow the backend's codegen.

## What was checked

The client side (headers on every call and on the socket, sign-in by cookie header, live updates arriving after a mutation) is tested against a real engine, with a WebSocket that takes headers the way React Native's does. The Expo app itself wasn't built or run on a device or simulator here.
