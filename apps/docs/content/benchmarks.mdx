# Benchmarks

Everything here was measured on one machine, in containers with fixed limits, with the same load generator, and the harness is in the repository so you can run it. This page says what was run and where the numbers come from; the pages for [archlast-serve](archlast-serve.html), [Rust page rendering](rust-renderer.html) and [Anvil, the thread pool](thread-pool.html) say what they show. How archlast-forge compares with Convex is [its own page](convex.html).

{/* bench:versions */}

Express 5.1.0 on Node 24.22.2; Bun 1.4.4; Go 1.24.13 with fasthttp 1.62.0; .NET 10.0.14 (Minimal APIs); Rust 1.90.0 with Axum 0.8. The full-stack apps ran on Node 26.8.2: React Router 7.9.4, Next.js 16.0.0, brust 2.0.0-alpha.38.

{/* /bench:versions */}

- **REST API servers** ran in Docker containers with those limits (`--network host`, so no bridge sits in the path). The Go, Rust and .NET servers were built in a multi-stage image from the language's official SDK image; Node and Bun run the code as it is.
- **Full-stack apps** (React Router, Next.js, brust, archlast-forge) ran on the host under a systemd scope with the same limits (`MemoryMax=2G`, no swap, `taskset` to cores 0–3). The memory in the tables is the scope's peak (`memory.peak`), children included.
- The server uses four cores and the load generator eight threads on different cores, so the client does not compete with the server. The fastest servers here (compiled languages at 400,000 to 550,000 requests a second) are close to what one client of that size can send, so their numbers are a floor on what they can do.
- One run is 5 seconds after 2 seconds of warm-up; the table shows the median of 3.

## A REST API with in-memory CRUD

A small `items` API, built the same way in nine setups. An item is `{ id, name, quantity }`.

| | |
|---|---|
| `GET /items/:id` | the item, or `404` |
| `GET /items?limit=N` | the existing items among ids `1…N` (default 20, at most 100) |
| `POST /items` | creates an item (`201`), or `400` for an invalid body |
| `PUT /items/:id` | replaces an item (`200`), `404` or `400` |
| `DELETE /items/:id` | `204` or `404` |

The store is a map in memory, seeded with 1,000 items, safe for concurrent use, and capped at 100,000 items (creating item *n* removes item *n − 100,000*, so a long create run does not fill the memory). Every body is validated: a non-empty `name` of at most 100 characters and a whole `quantity` of 0 or more. A script (`conformance.ts`) checks all of this against each server before it is measured, and the benchmark does not run a server that fails it.

| Stack | How it is served |
|---|---|
| archlast-forge | a NestJS controller on the Nest path (`forge/http.ts`), served by archlast-serve, under `/http`; also with `HTTP_ENGINE=bun` and with telemetry off. Rate limiting is off (it is on by default in production and would refuse the load); everything else is as shipped, including telemetry. |
| archlast-serve | the engine on its own, with no framework: its native `App` API (`packages/serve`), one JavaScript thread and 3 Rust I/O threads |
| NestJS on archlast-serve | the same controller on archlast-serve with no Forge around it: a basic Nest HTTP adapter (about 150 lines, `benchmarks/rest/servers/nest-serve/adapter.ts`) over the engine's native `App` API, one JavaScript thread and 3 Rust I/O threads. It does JSON bodies, params, the query string, status codes and Nest's own guards, pipes and exception filter; no middleware, CORS, static files, views or streaming |
| NestJS on Node.js | the same controller as Forge's, as a plain NestJS app on Nest's Express adapter (`@nestjs/platform-express`), Node 24, one process |
| NestJS on Bun | the same NestJS app on Bun 1.4 (still Nest's Express adapter), one process |
| Node.js | Express 5, one process |
| Bun | `Bun.serve`, one process |
| Go | fasthttp with `fasthttp/router`, one goroutine per connection |
| .NET | Minimal APIs on Kestrel, source-generated JSON |
| Rust | Axum on Tokio, multi-threaded |

The JavaScript servers (Forge, archlast-serve, NestJS, Express, Bun) use the same store module, so they differ only in what serves HTTP. Each case is one request type at 64 connections: read a random seeded item, list 20, update a random item, create an item.

How to read this:

- **The compiled servers are 2.6 to 3.7 times as fast as a Forge NestJS controller on reads, and 1.3 to 1.8 times as fast as a Forge light route.** A Forge request goes through the engine's routing, telemetry, security headers and the JavaScript runtime, and your code runs on one JavaScript thread: a NestJS controller used about 1.9 of the four cores, a light route about 2.6, the Rust I/O threads taking the rest. Axum, Go and .NET spread the work over all four. If a route needs more than a light route gives, write it in one of them.
- **archlast-serve on its own is level with the compiled servers.** Its handler is TypeScript on one JavaScript thread, and the engine's Rust threads do the sockets and HTTP around it: it answers about 3.5 times as many reads as `Bun.serve` and sits between Axum and Go. This is the engine's native API, which hands the handler a light context and takes a `Reply` back; the `Bun.serve` server here is one `fetch` handler with Web `Request` and `Response` objects, and a leaner `Bun.serve` (its `routes` option) would be faster than the row shown. The gap between this row and Forge's is what a framework costs: a NestJS controller, routing, validation, telemetry and the runtime between the socket and your code.
- **Forge on the Nest path is about 7 times Express and a little above a bare `Bun.serve`** on reads, with a NestJS controller, telemetry and security headers that neither of those has. A [light route](http.html#light-routes) on the same engine is about twice a bare `Bun.serve`. On `Bun.serve` the same NestJS controller runs at about a quarter of the Nest figure: the engine's own request reaches the Nest adapter without a Web `Request` or `Response` in between (see [archlast-serve](archlast-serve.html#what-the-http-path-does-for-a-request)).
- **The same NestJS controller on archlast-serve alone, with no Forge, does 264,000 reads a second**: 7 times NestJS on Bun, 12 times NestJS on Node, 1.7 times the Forge Nest path (152,000) and 1.9 times a bare `Bun.serve`. Nest's own pipeline (guards, pipes, exception filter) costs little once the Web `Request`, Express's request and response objects and their event emitters are gone. The gap to Forge's 152,000 is what the framework adds around every `/http` request: telemetry, rate limiting, security headers, the request id, the caller's identity, the action's time limit, the async context for logs, and an Express-compatible `req` and `res` for the middleware, CORS and streaming that real apps use and this basic adapter leaves out. It is a measure of the ceiling, not a replacement for Forge's adapter.
- **Telemetry costs about 12%** here, and it is on by default (every request is counted and a share of them are traced, kept in your own database). `TELEMETRY=off` turns it off; the first row shows what that gains.
- The state is in memory and in one process, which is why the benchmark runs one function worker. A real Forge app keeps it in the database, which adds the database's time to each of these.

## The same API on SQLite

The same API, scenarios and limits, with the items in a SQLite database instead of in memory. Each server uses its own driver in the setup you would use: `rusqlite` in Rust, `go-sqlite3` in Go, `Microsoft.Data.Sqlite` in .NET, `bun:sqlite` on Bun and `node:sqlite` on Node. archlast-forge uses what it ships: the items are documents in the engine's database, read and written with `ctx.db` directly from the route, in a transaction of its own (`ctx.read` and `ctx.write` in the light routes, a `DbService` with `@Read()` and `@Write()` methods in the NestJS controller). No function of the reactive system is called in between.

Every server has the same table, WAL mode and `synchronous = NORMAL` (Forge: `SQLITE_SYNCHRONOUS=NORMAL`; its default, `FULL`, is stronger), and the same rules: ids count up from 1001 and a trigger removes item *n − 100,000* when item *n* is inserted. The multi-threaded servers (Rust, Go, .NET) read through a few connections and write through one, as SQLite wants, and the JavaScript servers have one connection because they have one thread. The database is a file on the machine's NVMe disk (a new directory per server, bind-mounted), not tmpfs.

{/* bench:sqlite-versions */}

SQLite 3.53.4 is the version in Bun 1.4 (which `bun:sqlite` and the engine use); `rusqlite` and `go-sqlite3` compile their own copy, Node's `node:sqlite` and .NET's `Microsoft.Data.Sqlite` bring theirs.

How to read this:

- **Reads are the engine, and the database is in its way.** With in-memory data archlast-serve alone is level with the compiled servers; here it answers about as many reads as Axum and twice as many as .NET or Go, because `bun:sqlite` runs a prepared statement without leaving the thread, while the others take a lock or a pooled connection per request. This is one fast statement on a table the cache holds, so it measures the driver more than SQLite.
- **archlast-forge on its own database does about 70,000 reads a second on the Nest path and 90,000 on a light route.** Compare the in-memory rows (152,000 and 328,000): the database costs the Nest path about 54% of its reads and a light route about 73%. What is left is the database layer itself: a transaction, an index lookup, a stored JSON document parsed and a result, plus schema checks on writes and topics published after every write, where `bun:sqlite` called directly runs one prepared statement. A `Bun.serve` server on `bun:sqlite` does about 102,000, so a light route here is a little under it and the Nest path about two thirds. The first version of these rows called the database through `ctx.runQuery` and `ctx.runMutation` (60,000 and 74,000 reads); calling it directly gained 17% and 22%, which is what the lookup, validation, cache and span of a call by name cost.
- **The same Forge routes on `bun:sqlite` do 119,000 (Nest path) and 214,000 (light route) reads a second.** These two rows keep the engine and the route code and replace only the storage: the store is the one Express, `Bun.serve` and archlast-serve use, a prepared statement on a connection of the app's own, outside Forge's database. A light route with it answers about twice as many reads as `Bun.serve` on the same store and more than .NET, so the framework around the route is not what limits the `ctx.db` rows; the database layer is. The cost of `ctx.db` over a bare `bun:sqlite` call here is about 40% of the Nest path's reads and 58% of the light route's, and it buys what a raw connection does not: documents checked against a schema, indexes the engine maintains, transactions that retry, and live queries that update after a write. Creates show it most (8,000 against 25,000 a second), because Forge's write path validates each document against the schema, maintains its indexes and publishes its topics.
- **NestJS on archlast-serve with `bun:sqlite`, no Forge, does 202,000 reads a second**: 6.5 times NestJS on Bun on the same store (31,000), and above both Forge variants (119,000 on `bun:sqlite`, 66,000 on `ctx.db`).
- **Writes are limited by the disk and by SQLite's single writer.** Create and update are one transaction each. Every server's create is below its update, because an insert also changes the index and the file grows; the figures for create also depend on what the disk does while the log is checkpointed (the p99 in the full table), so read them as an order of magnitude.
- **Forge's write-ahead log is bounded under writes that never pause.** The benchmark found that it was not: the engine copied the log into the database from its own thread, but the log restarts only when a write finds nothing left to copy, and 64 connections inserting at once leave no such moment, so the file grew to several gigabytes in a 17-second create run (about 6 KB per insert) and, on a 256 MB tmpfs, every create failed. The checkpointer now holds the writer for the length of one checkpoint when the log passes 64 MiB, so the log restarts and stays near that size ([SQLite durability](https://github.com/algochad/archlast-forge/blob/staging/docs/decisions.md#sqlite-durability) has the details). The suite still keeps the databases on the disk, as measured before the fix, so that the rows stay comparable.
- Memory is the largest anonymous memory sampled during the run (the page cache is left out, because the log fills it).

## What these numbers do not show

- **One machine, one run of three medians.** A different CPU, kernel or container runtime moves every number. Compare the rows within a table, not against someone else's table.
- **No database, no TLS, no authentication in the REST and page cases.** They measure the server and the framework, not the app around them.
- **Closed-loop load.** 64 connections each send the next request when the last is answered, which measures capacity. It is not a model of a user, and latency at saturation is mostly queueing.
- **Latest versions at the time of writing.** brust is an alpha release; Next.js and React Router are used the way their documentation says to ship them (`next start`, `react-router-serve`), as one process each.

## Run them yourself

```sh
# the REST API: builds ten images, checks each server, loads each one (about 15 minutes)
cd benchmarks/rest && ./run.sh && bun report.ts

# the thread pool
cd benchmarks/pool && ./run.sh

# the full-stack pages (React Router, Next.js, brust and Forge)
cd benchmarks/fullstack && ./run.sh && bun report.ts

# put the numbers on the docs pages
bun benchmarks/collect.ts && bun benchmarks/docs.ts
```

Each folder has a README with the details. You need Docker (the REST and thread pool servers), [oha](https://github.com/hatoo/oha) and Bun; the full-stack benchmark also needs Node.
