# Dashboard

The dashboard is a web console served by the engine itself. It shows how your app is running (every request, its trace, errors, logs and releases: see [observability](observability.html)), shows and edits your data, runs your functions and manages users, and everything on it is a call to the engine's admin API. There is nothing extra to install or deploy.

- **URL:** `/_dashboard` (for example `http://localhost:3000/_dashboard`). `archlast-forge dashboard` prints it, and `dev` prints it on startup.
- **API:** `/_admin/<op>`, used by the page itself (see [the admin API](#the-admin-api)).
- **Enabled:** on in dev; **off in production** until you set `DASHBOARD=on`. When it's off, `/_dashboard` and every `/_admin/*` path answer 404, even with the admin key. The backend stack (`archlast-forge up`) turns it on, behind the admin key; set `DASHBOARD=off` in `.env` to hide it.

## Signing in

There are two ways in, chosen on the sign-in screen.

| Method | What it gives you |
|---|---|
| **Admin account** | An email and password with a role: `owner`, `admin` or `viewer`. Create one with `archlast-forge admin add you@example.com --role admin` (`--password` to choose it; otherwise one is generated and printed). Passwords need at least 12 characters. `admin list` and `admin remove` manage the rest. The default role is `admin`. |
| **`ADMIN_KEY`** | The deployment's admin key, as an `owner`. In dev it is generated once and printed by `archlast-forge dev` (it's kept in `DATA_DIR/.dev-secrets.json`). In production, set it in the environment; if `ADMIN_KEY` isn't set, key sign-in is off. Actions are logged under the name `admin-key`. |

Dashboard accounts are their own thing. They are not the users of your app (those are Better Auth's `users`), and an app user can't sign in here. See [authentication](auth.html#dashboard-accounts-are-separate).

A successful sign-in sets an `afx_admin` cookie: `HttpOnly`, `SameSite=Strict`, valid for 12 hours, and `Secure` when `BETTER_AUTH_URL` is `https://`. The server keeps only a hash of the token. When the session ends or is revoked the page returns to the sign-in screen. Sign-in attempts, and requests with a wrong `x-admin-key`, are rate limited per IP, with their own counter next to the one for normal calls (`RATE_LIMIT_PER_MINUTE`). Setting an account's password again (`archlast-forge admin add` with its email) signs it out everywhere, and a session signed in with `ADMIN_KEY` ends when the key changes.

## Roles

| Role | Can |
|---|---|
| **viewer** | Open every page and read everything: telemetry, documents, users, sessions, schema, the audit log. Cannot change anything (but can mark notifications read). |
| **admin** | Everything a viewer can, and also: insert, patch, replace and delete documents; run functions (including internal ones) as any user; cancel and retry scheduled jobs; delete files; revoke sessions; ban and unban users; clear the cache; reload the function runtime; resolve and ignore issues; manage SLOs, alert rules and ingest keys; make a backup. |
| **owner** | Everything, plus [run your own code](#running-your-own-code) (when `ALLOW_CUSTOM_FUNCTIONS` allows it); download, upload, restore and delete backups and set their schedule; change engine settings and restart the server; set and remove the functions' environment variables. Backups hold credentials and settings hold secrets, so these are the owner's. |

Buttons a role can't use are hidden, and the server enforces the same rules: a viewer's write answers 403 `Requires the admin role`.

**A viewer can read every table** in the Data page except the credentials in them: `accounts.password` and OAuth tokens, `sessions.token` and `verifications.value` show as `[hidden]` to every role, the owner included. Everything else in your data is visible, so give the role only to people you would trust with it. On `0.1.0` those fields were readable; upgrade if viewers are not fully trusted.

## The pages

The sidebar groups them as Observe, Performance, Infrastructure, Backend and Admin, and its foot says whether the function runtime is up, with its functions, tables and the release it runs (a runtime that failed to load shows its error on every page). The top bar has the search, the alert notifications, the theme switch and who you are, and, on a main app with [microservices](observability.html#one-dashboard-for-a-main-app-and-its-microservices), the backend the Backend and Admin pages show: the main app, or one of its microservices.

### Observe, Performance and Infrastructure

**Overview**, **Requests**, **Errors**, **Logs**, **Users**, **Jobs**, **Spans**, **Hotspots**, **Services** (your Nest classes), **Map**, **Runtime**, **Releases**, **SLOs**, **Metrics**, **Microservices** and **Nodes** show what the engine records about every request it handles, and what other services send it. [Observability](observability.html#the-pages) describes each one. They share one time range (1H to 30D, or custom), a **Live** switch and, when more than one service reports, a service picker; a request's trace opens from any of them. What they show is stored, not held in memory: stopping and starting the engine on the same data directory keeps it. Each page shows one range though, the last hour by default, so after a quiet spell the page says when the last request was and offers the range that holds it.

Three of them have a view that doesn't need telemetry: **Accounts** on Users, **Queue & crons** on Jobs and **Stream** on Logs, described below. With `TELEMETRY=off` these pages open on that view, and the others say telemetry is off.

### Accounts (Users)

Your app's users (Better Auth's `users` table), 50 to a page, with a status badge: *banned*, *verified* or *unverified*. **Find by email** is an exact match (case-insensitive: the address is lowercased). Click a user for their id, join date and **sessions** (device, IP address, when it started and when it expires). Admins can **Revoke** a session, which signs that device out, and **Ban user**, which sets `banned: true`, signs the user out everywhere and makes new sign-ins fail (see [banned users](auth.html#banned-users)). **Unban** reverses the flag. A user's page under **Activity** has the same account details next to everything they did.

### Queue & crons (Jobs)

**Crons** from `forge/crons.ts` with their schedule (UTC) and next run. **Jobs** from the scheduler, filterable by state (`pending`, `running`, `success`, `failed`, `canceled`), with the function, arguments and error. Admins can **Cancel** a pending job and **Retry** a failed or canceled one. See [scheduling](scheduling.html).

### Stream (Logs)

**Stream · this server** shows function calls and `console` output as they happen (server-sent events), up to the last 500 entries in view, with **Pause** and **Clear**. **Stored · all servers** is the searchable history, kept for `LOG_RETENTION_DAYS`, with each line's trace.

A `call` entry says whether the function succeeded and how long it took; [HTTP endpoints](http.html#limits-rate-limiting-and-metrics) appear as `http GET /path`. The request id is what a caller sees in an error (`Server error (request …)`), and it's the `x-request-id` response header.

### Data

Browse and edit documents.

- **The table list** groups *Your tables* and *Built in* (Better Auth's tables, marked "Better Auth", and `_storage`), with a live document count for each. System tables like `_admins` and `_audit` aren't listed.
- **A table view** shows documents newest first, 50 to a page, refreshed every few seconds. Columns are `_id`, your fields in schema order, any fields not in the schema, and `_creationTime`. Pick an **index** and fill in values left to right to filter by equality on a prefix of its fields (values parse as JSON when they can: `5`, `true`, otherwise text); **Newest/Oldest** flips the order. **Previous/Next** page through results.
- **A document** opens in a drawer: its id and creation time, its [relationships](#relationships), and its fields as JSON. Admins can **Patch** (merge the fields you wrote), **Replace** (keep only what's there) or **Delete**; **Add document** inserts one. Every write is validated against the schema, like a write from a function (Better Auth's tables are the exception: they're loosely typed so plugins can add fields). Viewers see the JSON read-only.
- **Schema** (a toggle in the table header) lists the fields with their types and whether they're optional, which indexes use each field, the indexes (including search indexes), and the table's relations.
- Deleting a `_storage` document also deletes the object in storage.
- **Query** (owners) opens the code runner with a starting query for this table.

Writes made here publish to live queries and invalidate the [cache](caching.html) like any other write. They bypass your functions' checks, so be careful in tables Better Auth manages.

### Files

Appears when storage is on (S3, or the [built-in storage](storage.html#built-in-storage), which development uses without S3; otherwise it explains how to set it up). Lists `_storage` records newest first with the id, content type, **size** (read from the object itself) and upload time. **Open** gives a presigned link that lasts ten minutes; **Delete** (admins) removes the record and the object. Documents that referenced the file keep a dangling id. See [storage](storage.html).

### Functions

Every function in the manifest with a kind badge (query, mutation, action) and an `internal` mark, with a filter box. Select one to see its argument and return types and run it (admins):

- **Arguments** are a generated form when every argument is a string, number, boolean, id or null; otherwise a JSON editor. You can switch between them.
- **Run as user** takes an email or a `users:…` id so that `ctx.auth.getUserIdentity()` sees that user (the session id is `dashboard`). Empty runs anonymously.
- It runs the real function with the real database, queries included (not through the query cache). Internal functions can be run here too, which clients can't do.
- **Recent runs** keep the last ten per function, with arguments, result or error, and timing. They are stored in your browser (`localStorage`), not on the server.

### Cache

Shown when the query cache is on (`CACHE_TTL_MS`; otherwise the page says how to turn it on). Hit rate, calls served from the cache or by sharing a run already in flight, function runs, the time saved, and charts, over the page's time range (from each server's runtime samples and the recorded requests, so they survive a restart; with `TELEMETRY=off` they count since the server started). Entries and memory used, and entries evicted by writes and for space, are the server's own state right now, so they start again from zero with it. A per-function table marks queries that are cached **per user** (they read `ctx.auth`). Admins can **Clear cache**, which empties this server's cache (or the shared Redis cache) and records it in the audit log. See [caching](caching.html).

### Alerts and Ingest keys

The alert rules over the telemetry and the keys other services send it with: see [observability](observability.html#alerts). The services reporting are on **Microservices**, under Infrastructure. For scraping by Prometheus, `/metrics` is still there (bearer `METRICS_TOKEN`, which is the admin key unless you set it).

### Backups

Every backup, newest first, with what it holds (documents and tables, files and their size, the number of source files and whether that source is the code running now), its kind (manual, scheduled, uploaded, made before a restore, or found in storage without a record) and its size. **Back up now** (admins) makes one, with or without files, and shows its progress. Owners can **Download** an archive, **Upload a backup** from somewhere else, **Restore** one (choosing whether files, and environment variables and settings, come back too; type `restore` to confirm; a safety backup is made first), delete one, and set the **Schedule** (off, hourly, daily or weekly at a UTC time, or a cron expression, how many to keep, with or without files). The card also says where backups are kept. See [Backups](backups.html).

### Security

The security headers (Helmet) of the REST API, the app's pages and the dashboard itself: for each, where they come from (the engine's preset, or your code), exactly what is sent, and, for owners, switches to change them at once: on or off, the Content-Security-Policy enforced, report-only or off, sources added to a directive, framing, HSTS, Cross-Origin-Resource-Policy and Referrer-Policy. Below, the CSP violations browsers reported. See [Security headers](security-headers.html).

### Audit

The audit log: when, who, what, which target and the arguments, newest first (300 entries). It records dashboard writes and the CLI's `import`, `restore`, `env set`, `env rm`, `admin add`, `admin remove` and `migrate --run` (actor `cli`; never the secret values). Reads and sign-ins aren't in it (sign-ins are in the server log). See [audit log](#audit-log).

### Settings

- **Engine settings:** every variable the engine reads ([Configuration](configuration.html)), grouped (Server, Auth, Database, Runtime, Limits, Storage, Backups, Telemetry) and searchable, each with what it does, its default, its value and where that value comes from. Owners change them in place: worker counts, timeouts, limits, the cache, storage and its credentials, telemetry. A variable set in the environment wins and is shown read-only, as are the few that only the environment may set (with the reason). Saved values that need a restart are marked, and **Restart now** restarts the server to apply them. `RUNTIME_WORKERS` (a number or `auto`) shows the processes running and the CPU cores detected, and in `process` mode a new value resizes the pool at once, without dropping calls or subscriptions ([details](configuration.html#changing-the-worker-count-while-running)). Secrets are never shown back. See [settings saved from the dashboard](configuration.html#settings-saved-from-the-dashboard).
- **Function environment variables:** the names of the variables your functions read (never the values), with when each changed. Owners set new values and remove them; **Reload runtime** (admins) applies the change.
- The **schema** (every table with its fields and indexes) and the **live subscriptions** on this server (query, arguments, the topics that will re-run it, and how long it has been open).

## Relationships

Fields declared with `v.id("…")` are links between tables, and the Data page follows them:

- **In the table,** a reference shows the document it points at by its name (or title, or email) instead of an id. Click it to open that document in its own table. A reference whose document was deleted shows as *missing*.
- **In a document's drawer,** **Relationships** lists what it points at, and what points at it (`todos.listId`, 9). **Browse** opens that table with the lookup already applied, using the index on the field.
- **A trail** at the top (*todos › lists · Forge launch › todos · listId = …*) shows how you got here. **Back**, or any step in it, returns you, with that document open again.
- **Where there is no index** on the referencing field, the count is found by scanning, and Browse is replaced by **Query**, which opens the function runner with a query for it (owners only). Adding an index to the field turns it into a normal lookup.
- **Relationships** in the Tools list draws every table with its references as an entity-relationship diagram, or as a list. Click a table to open it, hover to follow its connections. Your own tables are shown with the built-in ones they connect to.
- A table's **Schema** view has a **Relations** section with both directions.
- The function runner has join examples built from your schema.

## Running your own code

On the Data page, **Run function** opens an editor where you write a query or a mutation and run it against the live data, like a custom test query in Convex. Each table's **Query** button opens it with a starting query for that table, and the **Examples** menu has more: counting, filtering with an index, updating documents, logging, joins.

```ts
export default query({
  args: { listId: v.id("lists") },
  handler: async (ctx, { listId }) => {
    console.log("looking up", listId);
    return await ctx.db.query("todos").withIndex("by_list", (q) => q.eq("listId", listId)).collect();
  },
});
```

- **What's in scope:** `query`, `mutation`, `v` and `ForgeError`, so there is nothing to import (import lines are dropped). TypeScript works. `ctx` is what your own functions get; a bare `export default async (ctx) => …` counts as a query. It can't be an action or an `internal*` function.
- **Arguments** are JSON, checked against the `args` you declare. **Run as user** takes an email or `users:…` id, so `ctx.auth` sees that user.
- **Results** appear as a table when the function returns documents (or as JSON), with the time it took, what it wrote to the console, and a copy button. A syntax error shows its line.
- **Queries are read-only.** A mutation commits when it returns and rolls back if it throws; its writes reach live queries and invalidate the [cache](caching.html) like any other.
- **Cmd or Ctrl and Enter** runs it. The editor keeps your last draft in this browser.

This is arbitrary code running inside the function runtime, with its environment (database URL, secrets) and network access, so it is held to a higher bar than the rest of the dashboard:

- only the **owner** role can use it (an admin cannot; the page says so);
- it is **off in production** until you set `ALLOW_CUSTOM_FUNCTIONS=on` (on in dev). When it's off, owners see a notice and the API answers 403;
- every run, with its code and arguments (the first 2,000 characters of them), is in the audit log.

## Audit log

Every change made from the dashboard is recorded in the `_audit` table with the time, the actor (the account's email, or `admin-key`), the action, a target, and the arguments as JSON (cut at 2,000 characters):

| Action | Where it comes from |
|---|---|
| `insertDoc`, `patchDoc`, `replaceDoc`, `deleteDoc` | Data |
| `run` | Functions, Data → Run function |
| `runCustom` | Run function (owners) |
| `cancelJob`, `retryJob` | Jobs → Queue & crons |
| `deleteFile` | Files |
| `revokeSession`, `banUser` | Users |
| `clearCache` | Cache |
| `obs.setErrorState` | Errors (resolve, ignore, reopen) |
| `obs.saveSlo`, `obs.deleteSlo` | SLOs |
| `obs.saveAlertRule`, `obs.deleteAlertRule`, `obs.testAlert` | Alerts (webhook URLs are left out of the recorded arguments) |
| `obs.createKey`, `obs.revokeKey` | Ingest keys (the name, never the key) |
| `backups.create`, `backups.restore`, `backups.delete`, `backups.import`, `backups.download` | Backups (an upload is `backups.import`) |
| `settings.save`, `env.set`, `env.remove` | Settings (the name, never the value) |
| `restart` | Settings → Restart now |

The log has no edit or delete in the UI. Because the arguments of data edits are recorded, **the values you type are stored there**, and every role can read the audit page: don't paste a secret into a document edit.

## Keyboard, search and theme

- **Ctrl or Cmd + K** opens a palette that jumps to a page, a table (in Data) or a function (in Functions), and searches telemetry: operations, errors, users, or a trace by its id or by the request id a caller saw (`Server error (request …)`).
- **Alt + 1 … 9 and Alt + 0** jump to the first ten pages in sidebar order: Overview, Requests, Errors, Logs, Users, Jobs, Spans, Hotspots, Services and Map.
- The address bar follows the view (`#/requests?kind=query&op=todos:list`), so an operation, a trace or an issue can be bookmarked or sent to someone. Links from older versions (`#Data`) still work.
- The theme follows your system, or switch it to light or dark from the top bar. It is remembered in your browser.

## The admin API

The dashboard is a plain client of `/_admin/<op>`, and you can script it. Reads are `GET /_admin/<op>?input=<json>`; changes are `POST /_admin/<op>` with a JSON body. Authenticate with the session cookie, or send `x-admin-key: <ADMIN_KEY>` to act as the owner.

```bash
curl "localhost:3000/_admin/counts?input=%7B%22tables%22:%5B%22todos%22%5D%7D" -H "x-admin-key: $ADMIN_KEY"

curl -X POST localhost:3000/_admin/banUser -H "x-admin-key: $ADMIN_KEY" -H 'x-forge-admin: 1' \
  -H 'content-type: application/json' -d '{"userId":"users:…","banned":true}'
```

- **POST requests need `x-forge-admin: 1`**, a custom header that a cross-site page can't send without a preflight the API never grants. Without it: 403. The sign-in (`POST /_admin/login` with `{ email, password }` or `{ key }`) needs it too.
- **Errors** are `{ "error": { "message", "code", "requestId" } }` with the matching status: 401 not signed in, 403 role too low, 404 unknown operation, 405 wrong method (`docs takes GET`).
- The admin API reports real error messages, even in production.

| Role | Operations |
|---|---|
| none needed | `login`, `logout`, `me` (who you are, or `null`) |
| viewer | `microservices` (this app's name and its `MICROSERVICES`), `manifest`, `docs`, `docsByIds`, `references`, `counts`, `scheduled`, `crons`, `files`, `users`, `sessions`, `audit`, `env` (names only), `recentLogs`, `subscriptions`, `server`, `cache`, `settings` (secrets never), `backups.list`; telemetry: `obs.overview`, `obs.requests`, `obs.jobs`, `obs.operation`, `obs.trace`, `obs.errors`, `obs.error`, `obs.users`, `obs.user`, `obs.spans`, `obs.span`, `obs.hotspots` (`{ type: "nest" }` for the Nest classes alone), `obs.map`, `obs.runtime`, `obs.nodes`, `obs.metrics`, `obs.releases`, `obs.services`, `obs.logs`, `obs.search`, `obs.slos`, `obs.alertRules`, `obs.alertEvents`, `obs.notifications`, `obs.keys`, `obs.source`, and the write `obs.markSeen` |
| admin | `insertDoc`, `patchDoc`, `replaceDoc`, `deleteDoc`, `run`, `cancelJob`, `retryJob`, `deleteFile`, `revokeSession`, `banUser`, `clearCache`, `reload`, `backups.create` (`{ files }`), `obs.setErrorState`, `obs.saveSlo`, `obs.deleteSlo`, `obs.saveAlertRule`, `obs.deleteAlertRule`, `obs.testAlert`, `obs.createKey`, `obs.revokeKey` |
| owner | `runCustom`, `saveSetting` (`{ name, value }`, `null` removes it), `restart`, `env.set` (`{ name, value }`), `env.remove`, `backups.restore` (`{ id, files, config }`), `backups.delete`; `GET /_admin/backups/download?id=` (the archive) and `POST /_admin/backups/upload` (the archive as the body) |

The `obs.*` reads take a time range in milliseconds since the epoch (`from`, `to`) and optionally a `service`; with `TELEMETRY=off` they answer 404. `/_admin/logs/stream` is the server-sent event stream behind the log stream. On a main app with `MICROSERVICES`, `?target=<name>` on any call but `me`, `microservices` and the `obs.*` ones sends it to that microservice, as the signed-in user with their role. The shapes of each operation's input and output follow the dashboard's usage and may change between versions; treat this as a convenience, not a stable public API.

## Security notes

- **Turn it off, or fence it.** The dashboard can read and edit every document. Leave `DASHBOARD` off in production unless you need it, and when it is on, put it behind a VPN or an IP allow-list at your proxy. Serve it over HTTPS so the cookie is `Secure`.
- **Prefer accounts over the key.** `ADMIN_KEY` is a shared owner password: it also unlocks `/metrics` and the CLI's data commands (`import`, `env`, `admin`) over `POST /_cli`. Use per-person accounts for the dashboard, give most people `viewer`, and keep the key for automation. Rotate it by changing the variable and restarting.
- **Role changes take a few seconds.** The server caches a session's identity for 10 seconds, so a removed account or demoted role can keep working for that long.
- **Viewers see your data.** Credentials are hidden (`[hidden]`), but every document in every table is readable. Saving a document the Data page showed you never writes the placeholder back over a real credential: it is left as it was.
- **Custom code is remote code execution** by design. Keep `ALLOW_CUSTOM_FUNCTIONS` off wherever owner sessions are widely shared; see [limits](limits.html).
- **Audit entries hold the values written** to documents, so don't put secrets in documents through the Data page. Settings and environment variables are recorded without their values.
- **Writes are same-origin only.** The cookie is `SameSite=Strict` and every write needs the custom header, so another site can't drive an admin's session.
