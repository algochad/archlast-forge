# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

Bun 1.4.4 (pinned in `mise.toml` and `packageManager`). Run everything from the repo root unless noted.

```bash
bun install
bun run dev                  # demo: engine in Docker + Vite (add -- --no-docker to run the engine in-process)
bun run build                # turbo build (libraries emit dist/, the demo builds)
bun run typecheck            # runs `bun check` per package; depends on codegen
bun run codegen              # regenerates forge/_generated in apps/demo
bun scripts/update-shadcn.ts # refreshes the shadcn/ui starter's components and base colors from the shadcn registry
bun run format               # prettier over ts/tsx/md

bun run test                 # SQLite and in-memory adapters only
bun run services:up          # Postgres, Redis, RustFS in Docker
bun run test:all             # everything, one package at a time, with TEST_* env set
bun run pack:smoke           # pack all packages; scaffold a full-stack app and a backend from the tarballs; build and serve both
bun run e2e                  # the same in Docker (needs Docker): `up`, `dev` with services, uploads, restarts, `down`
bun scripts/e2e-docker.ts caddy   # HTTPS behind Caddy; needs ports 80 and 443
bun scripts/e2e-dev.ts            # `dev` end to end without Docker services (the second half of `bun run e2e`)
bun scripts/use-local.ts ../other-project   # pack this checkout and point another project's @archlast/forge-* dependencies at the tarballs (rerun after changes)
```

Single test file or test name, from the package directory:

```bash
cd packages/runtime && bun test test/values.test.ts
cd packages/runtime && bun test -t "name fragment"
```

The browser tests in `packages/framework` drive Chromium through `playwright-core`; they skip when no browser can be launched (`CHROMIUM_PATH`, or `bunx playwright-core install chromium`). `turbo.json` passes `CHROMIUM_PATH`, `LD_LIBRARY_PATH`, `FONTCONFIG_FILE` and `SCREENSHOTS` through to tests; `SCREENSHOTS=<dir>` makes the template test save images of its pages. The `e2e` scripts need `bun scripts/pack.ts` first and the engine image (`bun packages/cli/src/index.ts engine build`, which they do not rebuild: rebuild it after changing `packages/cli/src/engine.ts` or anything else that runs inside the container).

Postgres, Redis or S3 tests run only when their `TEST_*` variable is set (`TEST_POSTGRES_URL`, `TEST_REDIS_URL`, `TEST_S3_ENDPOINT`); `test:all` sets them, matching `services:up`. Type-level tests live in `packages/runtime/test-types` and run with `bun check -p test-types`.

## Other top-level folders

`benchmarks/*` are standalone load and performance harnesses (`load` has its own README and shell runners; `workers`, `forge-rpc`, `batch`, ... are small apps with a `forge/` folder and are workspace members). `docs/` holds `decisions.md` (see "Decisions to keep"), `releasing.md` and `roadmap.md` (the production-readiness plan, marked implemented; useful for the reasoning behind the Docker engine, not a to-do list).

## Agent skill

`skills/archlast-forge` is the installable skill (`npx skills add algochad/archlast-forge`, the Vercel `skills` format: `SKILL.md` with `name` and `description`, plus `references/*.md`). It teaches agents how to build apps WITH archlast-forge, so it must change in the same commit as anything it describes: a public API or CLI flag, what `create-archlast-forge` writes (the scaffolding reference was written from real scaffolds), the `forge/` layout it recommends (`_modules/`, routers at the top level because codegen only reads non-underscore files), or the docs pages it summarizes. `bun run skill:check` (also in CI) validates front matter, links, that every reference is linked from `SKILL.md`, and that each `import` of an `@archlast/*` package in a code sample names a real export; it can't check prose, so reread the affected reference. Changes that users notice also get a line under "Unreleased" in `apps/docs/content/release-notes.mdx` (the owner turns it into the release's notes on `staging`; CI refuses a version change without them). The docs page is `apps/docs/content/agent-skill.mdx`.

## Publishing a release

Full runbook: `docs/releasing.md`. Read it before releasing; this is the short version.

Publishing points: **npm** (nine packages, lockstep version), the **engine image** on GHCR (`ghcr.io/algochad/archlast-forge-engine:<version>` and `:latest`), and the **docs site** (Coolify, not in a workflow). A `v*` tag runs `.github/workflows/release.yml`, which pushes the image and then publishes to npm (`NPM_TOKEN` secret).

- Publishing can't be taken back (npm never reuses a version). Release only when the user asks for it; a request to commit or push is not one.
- Never tag before CI is green on the commit that gets the tag.
- `master` and `staging` are protected: never push to either. Work on a branch from `staging` and open a pull request into `staging` (`CONTRIBUTING.md`); only `staging` is merged into `master`, and the engine image is built only when `master` is updated.

1. Commit the change itself first (code, tests, docs).
2. `bun scripts/version.ts X.Y.Z` (use Bun 1.4.4; a patch for fixes, a minor for new public API). It only sets `packages/*/package.json`: also update the version in the docs' sample output, image tags, the `^X.Y.Z` example and the `reference.mdx` header (grep for the old version), and the API in `reference.mdx` if it changed.
3. `bun install`, then `bun install --frozen-lockfile` and `bun run --cwd apps/docs build` must pass. Commit as `Version X.Y.Z`, with what the release contains in the body.
4. `staging` and `master` are protected (rulesets: pull requests only, `test` must pass, no force pushes; `master` takes only `staging`). Put the release notes in `apps/docs/content/release-notes.mdx` ("Unreleased" becomes `## X.Y.Z`), commit them and `Version X.Y.Z` on `release/X.Y.Z`, `gh pr create --base staging`, `gh pr merge --merge --delete-branch` (the owner can merge without a second reviewer), then `gh pr create --base master --head staging`, merge it with a merge commit, `git switch master && git pull --ff-only`, wait for CI on that commit (`gh run view`; the `engine-image` build runs only here), then `git tag -a vX.Y.Z -m "Version X.Y.Z" && git push origin vX.Y.Z` and wait for the Release run.
5. Verify, don't trust the green check: `npm view --prefer-online <package> version` for all nine (npm lags a few minutes), and the GHCR manifests for `X.Y.Z` and `latest` (same digest).
6. Redeploy the docs site in Coolify (the repo doesn't record whether it deploys on push: check, or tell the user).

Known gap: a pre-release tag (`-rc.1`) publishes to npm under `next`, but the image job still moves GHCR `latest`. Don't cut one without changing the workflow.

## Architecture

**Forge code and generated types.** An app declares its backend in `forge/` (schema, functions, crons, auth). `archlast-forge codegen` writes `forge/_generated` (`api`, `internal`, `dataModel`), which is committed. `src/` may import only from `forge/_generated`; codegen fails on anything else. Internal functions are left out of `api` and the client router, so their names never reach a client.

**Two processes, one protocol.** The server (`packages/runtime/src/server/server.ts`, `rpc.ts`, `subscriptions.ts`, `bus.ts`, `cache.ts`) owns HTTP, WebSockets, the cache, rate limits and live-query subscriptions. The function runtime (`runtime-core.ts`) owns the `forge/` modules, the database, Better Auth and the scheduler. `runtime.ts` decides how to run it. In dev, and when `RUNTIME_WORKERS > 1`, it is a child process (`child.ts`) that can be restarted alone when code changes. Otherwise it runs inline in the server, which is the production single-worker default. `config.ts` decides, and it refuses `inline` in dev. Both modes share `runtime-core.ts`, so behavior changes belong there, not in either wrapper. `RUNTIME_WORKERS` is a number or `auto` (`runtimeWorkersFor` in `config.ts`: cores from `serverCores()`, which honors the cgroup CPU quota, times `RUNTIME_WORKERS_RATIO`); in process mode the dashboard resizes the pool live (`FunctionRuntime.resize`: added processes start beside the others, removed ones drain and stop, worker 0 always stays and gets a `{ t: "pool" }` event that switches its SQLite read cache off while another process writes). In a child process (`child.ts`), queries wait in a queue that starts a few per event-loop turn, refuses a call at its deadline (`FUNCTION_TIMEOUT_MS` after it was sent) and holds back while more than 4 MB of results are still waiting to be written to the pipe; mutations, actions and HTTP routes bypass it. A query's, mutation's or action's result crosses to the server as its JSON text and its topics as one string (`wire.ts`: `toWire` in the child, `fromWire` in `runtime.ts`), and the server builds `value` from the JSON only if something reads it (`lazyValue`); the object and an array of thousands of topic strings are what made a large result expensive to move. Keep anything new that crosses that pipe small, and don't call `bun:jsc`'s `heapStats()` on a timer (it walks the heap on the main thread: use `process.memoryUsage()`).

**Calls and reactivity.** A query, mutation or action goes through the server to the runtime, which runs it in a transaction. Writes publish topics only after commit: the table, `table:index:[values]` for each index prefix, and `table:by_id:[id]`. Subscriptions re-run queries whose topics changed. Between servers, the Redis bus carries topics and each server filters locally. Every Redis key and channel (cache, bus, both rate limiters) sits under `config.redisPrefix` (`redisPrefixOf` in `config.ts`: `REDIS_PREFIX`, else `archlast-forge:<OTEL_SERVICE_NAME>:`, else the old `archlast-forge:`), so services that share one Redis, as a monorepo's can, don't read each other's cached results or wake each other's subscriptions, while every server of one service shares its keys through the name. `init`/`add`/`workspace sync` (`ensureAppNames`) name every app. `claimPrefix` warns at startup when another app (another `BETTER_AUTH_SECRET`) already uses the prefix. Any new Redis key must be built from the prefix. The query cache is keyed by function and args, and by caller for queries that read `ctx.auth`.

**Storage.** `server/db/` holds the dialect layer (`sqlite.ts`, `postgres.ts`). Each table is `(_id, _creationTime, doc)` with the document stored as JSON, so schema changes don't migrate data. Writes are validated by Zod against the schema through `values.ts`. The SQLite path uses `bun:sqlite` in WAL mode, one serialized writer with group commit, and reader connections; the app database sizes `mmap_size`, `cache_size` and `temp_store` to the server RAM (`serverMemory()`, the cgroup limit in a container) divided by `RUNTIME_WORKERS` (`sqliteMemory`). `read-cache.ts` is an exact per-statement read cache that is only enabled when this process is the only writer. `docstore.ts`'s query builder also has `where` (branded predicates compiled to SQL, field names restricted to identifiers), `orderBy` (keyset cursors for any direction mix), `select`, `skip`, and the writer `insertMany`/`updateMany` (every row validated before any SQL); in dev it explains `where`/`orderBy` statements on SQLite and warns once when they scan or sort without an index (`devWarn`).

**Validators and types.** `packages/runtime/src/values.ts` (`v`) defines validators as plain data, so they can cross into the dashboard and the runtime process. `schema.ts`, `functions.ts` and `relations.ts` build on them, and the client types are derived from `api`.

**Clients.** `packages/client` speaks the wire protocol directly: JSON over HTTP at `POST /rpc/<name>`, and a WebSocket at `/rpc` for live queries. The React, Vue and Svelte packages wrap it. The dashboard is served at `/_dashboard`, with its API at `/_admin/<op>`.

**Modes.** A project is a full-stack app or a backend (`archlast-forge.json`: `mode`, `services`; no file means a backend with no services). `packages/create-archlast-forge` holds the templates (`template/base` plus `framework` or `backend`, and for full-stack apps `template/shadcn`, an overlay that `src/shadcn.ts` copies over the plain pages, with the theme of the chosen base color; `bun scripts/update-shadcn.ts` refreshes its components and colors from the shadcn registry) and `src/stack.ts`, which renders `compose.yaml`, `Dockerfile`, `.env` and the Caddyfile and validates the config; the CLI imports it. `scaffold()` sets up Prettier through `addPrettier` (`.prettierrc` with `tabWidth: 4`, `.prettierignore` for `forge/_generated`, the `format` script and the dev dependency) and then runs Prettier over the new project, so projects are 4-space while the templates in this repo stay in the repo's 2-space style: don't reformat the templates. `src/monorepo.ts` (`--monorepo`, `--microservices`, `--transport`) lays out a Turborepo monorepo from several `scaffold()` calls, writes `packages/api` (re-exports of each backend's `forge/_generated`) and the Nest transport example (a router or controller per service; in the main app, a service class per service with a controller and an action over it, listed by `forge/_services.ts`); `test/monorepo.test.ts` runs that example. `scaffoldMonorepo` is made of pieces (`writeService`, `writeCaller`, `writeShared`, `writeRoot`, ...; the `create-archlast-forge/monorepo` export) and `workspace.ts` holds a monorepo's record (`archlast-forge.workspace.json`: main app, transport, each app's ports; inferred from the folders when missing), so the CLI's commands on an existing project (`monorepo`, `add`, `remove`, `workspace [sync]` in `packages/cli/src/evolve.ts`, `stack` in `stack-edit.ts`, output and prompts in `grow.ts`) write what `init --monorepo` writes. `packages/api` has the main app's types only (each other app in `@<name>/api/<app>`, services not at all): two backends' generated types in one TypeScript project collide on the global `Register`. A backend main app's package is `@<name>/backend`, since `@<name>/api` is `packages/api`. `--mobile` (a full-stack or a backend main app) copies `template/mobile` (Expo) into `apps/mobile` and writes the main app's `forge/auth.ts` with Better Auth's Expo plugin; the client's `headers` and `authPlugins` options are what it needs. `--desktop full|client` (`src/desktop.ts`, `template/desktop`) writes a Tauri app: full mode ships Bun as a sidecar running `engine/desktop-engine.ts` (the engine in production on 127.0.0.1, data in the app's data folder; `scripts/bundle-engine.ts` prepares the bundle), client mode a React page for a remote backend. Backend: `dev` runs the engine in Docker; `up`/`down` run `compose.yaml` (`packages/cli/src/stack.ts`).

**Full-stack apps.** `packages/framework` (on React Router's data router) scans `app/routes` into a route manifest (`routes.ts`), generates entry files into `<project>/.forge/gen` (`generate.ts`), and bundles for the browser and the server with `Bun.build` (`build.ts`; if the project has `bun-plugin-tailwind`, the browser build loads it from the project, which is how the shadcn/ui starter gets Tailwind v4; in production the browser bundle is minified, the server bundle is minified for whitespace and syntax with names kept and a linked source map, and both drop `debugger`). `server.tsx`'s `createApp` returns the `AppHost` that `startServer({ app })` calls for every request the engine doesn't own (`packages/runtime/src/server/server.ts`): it runs loaders with a per-request context, renders with `renderToReadableStream`, embeds `window.__FORGE__` (loader data, the TanStack query cache, the viewer, sanitized errors, and the render's `now` and `timeZone`), and serves `/_app/*` and `public/`. `client.tsx` hydrates the document. Anything that makes the server's text differ from the browser's first render makes React discard the server HTML (a time zone, `Date.now()`, a query argument from the clock): `time.tsx`'s `useTimeZone()` (zone from the `forge-tz` cookie, UTC on a first visit) and `useNow()` return the server's values while hydrating and the browser's afterwards, `hydration.ts` reports mismatches (`onRecoverableError`), and `test/hydration.test.ts` fails on any hydration error with the browser in another zone than the server. Development is one process on the host with rebuild and live reload (`dev.ts`); the CLI loads the framework from the project at runtime (`packages/cli/src/app.ts`), and `engine prepare` builds the app inside the image while linking React from the engine so there is one copy. Convention docs: `apps/docs/content/framework.md`.

**Docs site.** `apps/docs` is a React single-page app: `bun run --cwd apps/docs build` bundles `index.html` (-> `src/main.tsx`) with `Bun.build` into `dist/` (`--serve` previews on :4000). Pages are `content/*.mdx`, loaded one chunk per page through `PAGES` in `src/nav.ts`, which also holds the sidebar `GROUPS` (a new page goes in both; the build fails if they disagree, or if a link to `x.html` names no page). `mdx.ts` is the Bun plugin that compiles them with `@mdx-js/mdx` and a remark plugin: heading ids (repeats get `-1`, `-2`), the outline (`headings` export) and `search.json`, links rewritten from `page.html#id` to routes, and fenced code highlighted at build time by `highlight.ts` (Shiki, both themes as CSS variables) into `<Code>`. Add components for pages in `components` in `src/Doc.tsx`. `src/Landing.tsx` is the landing page; its code samples come from `src/snippets.ts`, run as a Bun macro so Shiki never ships. Its motion (blur-in words, pointer grid and card spotlight, reveal on scroll, count-up) is CSS in `landing.css` plus small hooks, after ReactBits, and stops under `prefers-reduced-motion`. `style.css` and `landing.css` are the styles; Geist fonts come from `@fontsource-variable/*` and are inlined into the CSS by Bun. `static.tsx` then writes what readers without JavaScript need: `<page>/index.html` (the page's text rendered with `react-dom/server` into the built shell, replaced by the app on load, so no hydration), `<page>.md` (the source with page links pointing at `.md`, its section and previous/next page under the title, and its source link at the end), `llms.txt` and `index.md` (the same index: key facts, how to read the docs, start-here by task, every page with its line), `llms-full.txt`, one `llms-<section>.txt` per sidebar section, `robots.txt`, `404.html` and, with `SITE_URL` set at build time, `sitemap.xml` and canonical links; the build fails if a page lacks its text or its navigation, or a page or section file is missing from `llms.txt`. The one-line description of each page (llms.txt, meta descriptions) is `DESCRIPTIONS` in `summaries.ts`, typed on the page list, so a new page fails the build until it has one (and `TASKS` is the start-here map). The Caddyfile answers `Accept: text/markdown` on a page's address with its `.md` (`build.ts --serve` does too). Each page has a Copy page button (`CopyPage` in `src/Doc.tsx`). Routes are root-relative, so the host serves the site from its root and answers a missing path with `404.html` and status 404. `compose.yaml`, `Dockerfile` and `Caddyfile` in `apps/docs` build the site and serve `dist` with Caddy (the service only `expose`s port 80, for a proxy such as Coolify's to reach; run it locally with `docker compose run --build --rm -p 8080:80 docs`) (a page is a folder with an `index.html`, anything missing answers `404.html` with status 404, hashed `chunk-*` files are cached for a year; `SITE_URL` is a build argument); the Dockerfile copies only `apps/docs`, so it does not use the root lockfile. The intro page is `introduction`.

**Files, backups and settings.** `storage.ts`: `S3Storage`, or `LocalStorage` (`STORAGE=local`, the default in dev without S3) keeping files in `DATA_DIR/storage` and served by the server at `/_storage/<key>` with URLs it signs (`serveLocalStorage`; sandboxed responses). With it or the dashboard on, Bun's body limit is `MAX_UPLOAD_MB` and every other body is read through `readBytes`/`readText` (`rpc.ts`) to keep `MAX_REQUEST_BYTES`: read new bodies through them too. `server/backup/`: `tar.ts` (streaming .tar.gz) and `backups.ts` (`writeArchive`, `restoreArchive`, the `Backups` registry/schedule in worker 0 of the runtime, stores: a folder or S3, chosen by `loadBackupConfig`). A restore writes through `Executor.rewrite` and publishes `RESET_TOPIC`, on which every server resets its cache and re-runs subscriptions. `settings.ts` lists every engine variable (add new ones there, with `envOnly` or `live` where it applies); the server reads `_settings` before its config (`withSettings`: the environment wins), and `startServer({ restart })` lets the dashboard restart it in place (the CLI's `serve.ts` provides it). Docs: `backups.mdx`, `storage.mdx#built-in-storage`, `configuration.mdx#settings-saved-from-the-dashboard`; reasons: `docs/decisions.md`. The dashboard is always bundled in production mode (`development: false`): restart to see edits to it.

**Telemetry.** `server/telemetry/` is the built-in observability the dashboard's Observe and Performance pages read (`obs.<op>` admin ops; docs: `apps/docs/content/observability.mdx`, decisions: `docs/decisions.md#observability`). The server owns a `Telemetry` recorder (`recorder.ts`): every request (`/rpc`, live re-runs, `/http`, `/api/auth`, pages, jobs) is a `Root` from `begin()` to `end()`, counted into per-minute rollups with log histograms (`histogram.ts`), and only some are recorded in detail (`TELEMETRY_DETAIL_PER_SECOND`) or kept (`TELEMETRY_TRACES_PER_SECOND`, tail-sampled with weights). Detail reaches the function runtime as a `trace` parent on the call message; `context.ts` (`logContext`, an `AsyncLocalStorage`) records function, database (`tracedTx`) and `fetch` spans there, and they come back on the result as `telemetry`. Batches go once a second to a Worker thread (`worker.ts` behind `client.ts`) that owns the store (`store.ts`: `DATA_DIR/telemetry.db` on SQLite, `_otel_*` tables on Postgres), its reads (`queries.ts`), SLOs, alerts and ingest keys (`settings.ts`), and OTLP ingest (`otlp.ts`, `protobuf.ts`) for `/otlp/v1/*`. `traceway.ts` is ported from Traceway (MIT; notice in `packages/runtime/THIRD_PARTY_NOTICES.md`). `export.ts` also sends traces to `OTEL_EXPORTER_OTLP_ENDPOINT`. Forge code reaches it through `trace`/`metrics` (`src/telemetry.ts`) and Nest's decorators (`timeClass` in `nest.ts`) via `Symbol.for("archlast-forge.telemetry")`; `timeClass` also puts an interceptor on controllers and gateways that records microservice-transport messages (Forge RPC included, under the caller's `traceparent`) and gateway messages as `rpc` and `ws` requests through that bridge's `entry` (`runtime-core.ts`, detail-sampled like HTTP). The worker answers one query at a time on synchronous SQLite, so a slow query stalls every dashboard call (a quadratic latest-sample query once took 89 s and a proxy answered 502): keep reads indexed and grouped, and test them on thousands of rows. One dashboard for a monorepo: a microservice with `DASHBOARD_URL` keeps no store and posts its recorder's batches to the main app's `POST /_telemetry` (`forward.ts`); the main app's `MICROSERVICES` lists them, and `?target=<name>` on an admin call (not `obs.*`, `me`, `microservices`) is forwarded there with `DASHBOARD_TOKEN` and the user's role (`toMicroservice` in `server.ts`). Dashboard: `api.ts` adds the target (`setBackend`, the top bar's picker), and the pages Microservices, Nodes (`obs.nodes`: server processes `host:pid` with their `/wN` workers) and Services (Nest classes: `obs.hotspots { type: "nest" }`). `create-archlast-forge`'s `ensureDashboard` writes those variables into a monorepo's `.env` files.

**OpenAPI and API docs.** `server/openapi.ts` builds an OpenAPI 3.1 document (an `openapi` admin op in the runtime) from public functions, `forge/http.ts` routes (optional `query`/`body`/`returns` validators, checked in `runtime-core` before the handler by `checkHttpRequest`) and Nest routes (`routesOf` in `nest.ts`, `@Contract` checked by an interceptor); the server serves it at `API_DOCS_PATH/openapi.json` (`API_DOCS`, on in dev) and hands the rest of that path to `startServer({ apiDocs })`: `packages/dashboard/src/api-docs` (React + MDX page bundled by `Bun.build` on first request, the app's `forge/docs/*.mdx`, and the Scalar explorer vendored brotli-compressed in `packages/dashboard/vendor/scalar`, refreshed by `bun scripts/update-scalar.ts`). Docs: `api-docs.mdx`.

**HTTP endpoints.** `forge/http.ts` (like `crons.ts` and `auth.ts`, a special module that `listModules` skips) exports `httpRouter()`. The server forwards `/http/*` to the function runtime as an `{ t: "http" }` message (like `/api/auth`), which matches the route and runs the handler as an action. Routing is in `server/http.ts`.

**NestJS.** `src/nest.ts` is `@archlast/forge-runtime/nest`: it re-exports `@nestjs/common` (and a few `@nestjs/core` tokens) so projects never import `@nestjs/*`. `nest(http, { controllers, providers })` in `forge/http.ts` adds a `pathPrefix` route for every method whose handler is an HTTP action that passes the request to `ForgeAdapter`, a Nest HTTP adapter that never listens: Nest registers its routes on a small Express-style router, and `handle()` runs them, parses bodies and builds a `Response`. HttpExceptions answer as in Nest; other errors are rethrown, so the engine answers them as it does an HTTP action's. Services extend `ForgeService<Ctx>` (`this.ctx`) or take `@InjectCtx()`; both resolve the request-scoped `CTX` provider from what Nest knows as the request. `inject(ctx, Service)` registers the call's ctx under a fresh context id (one per ctx, kept in a WeakMap) and resolves the service. One Nest app per process. Bun applies the tsconfig of the directory it runs in, not `forge/tsconfig.json`, so `server/project.ts` registers a `Bun.plugin` that compiles `forge/` files containing decorators on their own with `Bun.build` (`experimentalDecorators`, `emitDecoratorMetadata`, every import external, inline source map); files without decorators load as before. `nest-websockets.ts`, `nest-graphql.ts` and `nest-microservices.ts` are the `/nest/websockets`, `/nest/graphql` and `/nest/microservices` entries; they import `@archlast/forge-runtime/nest` by name (a relative import makes the build put `nest.ts` in a shared chunk and lose its `export *`). `nest()` options also take `cors`, `microservices` (connected before `init()`, started after) and `setup(app)`. Nest's `req`/`res` have Express's and Node's API; a `res` that is written to or flushed before it ends becomes a stream, marked with `Symbol.for("archlast-forge.stream")`. Gateway sockets: the server upgrades WebSockets under `/http/*` (the `/rpc` origin check and rate limit), keeps them by id, and sends `{ t: "ws", op: "open" | "message" | "close" }` events (`HostEvent` in `protocol.ts`, no answer) to the runtime. `FunctionRuntime.wsEvent` pins every socket to worker 0 (and the server sends Engine.IO polling requests, `?EIO=`, there too), and `runtime-core` hands events to whatever set `Symbol.for("archlast-forge.sockets")` (nest.ts's `dispatch`, which routes by path through `onSocket`). The runtime answers with `{ t: "ws", op: "send" | "close" }`. `runtime-core` sets `Symbol.for("archlast-forge.host")` (identityOf, actionCtx, wsSend, wsClose, relay, worker) for the project's copy of nest.ts. `createPubSub` publishes as `{ t: "relay" }`, which the server sends to every worker (`Symbol.for("archlast-forge.relay")` delivers it). `websockets: "socket.io"` uses `ForgeIoAdapter`: Nest's `IoAdapter` on an engine.io server whose `wsEngine` takes the engine's sockets, with polling through the HTTP adapter. Microservices connect on worker 0 only. Streamed HTTP bodies (that symbol, or `text/event-stream`) pass through inline; from a child process the result goes first and the bytes follow as `{ t: "chunk" }` messages (`child.ts` pumps, `RuntimeProcess` rebuilds the stream, and a client leaving sends `{ t: "cancel", id }` back). GraphQL is `ForgeGraphQLDriver`: Yoga on GET/POST at its path, and `graphql-ws` subscriptions on `onSocket(path)`. Tests: `packages/runtime/test/nest.test.ts` against `test/fixture-nest`, which has its own tsconfig and is type-checked separately (`bun check -p test/fixture-nest`); its main server runs functions in a child process (`RUNTIME_MODE=process`) so sockets and chunks cross IPC, and a second block runs them inline; `test/fixture-nest-io` (Socket.IO) and `test/fixture-nest-sdl` (schema-first GraphQL, `nest(http, AppModule)`) are checked the same way. `bun scripts/e2e-docker.ts nest` checks a packed backend in Docker (`nest --no-docker`: the same on SQLite with `start --no-docker`).

**Forge RPC.** `src/nest-rpc.ts` is `@archlast/forge-runtime/nest/rpc`: typed calls between forge backends over tRPC v11, backend to backend only (codegen's frontend-import check refuses it in `src/`/`app/`, and both classes throw where `window` exists) (docs: `forge-rpc.mdx`, reasons: `docs/decisions.md#forge-rpc`). Routers are declared as nestjs-trpc declares them (`@Router({ alias })`, `@Query`/`@Mutation({ input, output })`, `@Input(key?)`). `@Router` registers each method as a `MessagePattern("<alias>.<method>")` under the `FORGE_RPC` transport id, with its schemas in the handler's `extras`, and makes the class a controller with `ForgeRpcFilter`. That filter is where errors become the engine's envelope, because Nest's RPC proxy filters exceptions before any transport sees them. `ForgeRpcServer` (a custom strategy, in `nest()`'s `microservices`) builds a tRPC router from those handlers and serves it with the fetch adapter on a `Bun.serve` of its own, with `isDev: false` and an error formatter so no stack or internal message leaves. `ForgeRpcClient` is a `ClientProxy` on `httpBatchLink`, every call a POST. `createForgeRpcClient<Rpc>()` is the typed proxy (`.query`/`.mutate`). Both sides need `FORGE_RPC_TOKEN`. `archlast-forge codegen` writes `forge/_generated/rpc.ts` (`packages/cli/src/rpc-types.ts`): it imports the router files in a subprocess and turns their schemas into types through JSON Schema. Monorepos default to `--transport forge-rpc`, with `packages/contracts` re-exporting each service's `rpc.ts`. Generated and documented code imports Nest only through the runtime's entries.

**CLI.** `packages/cli` is `archlast-forge`. `dev`, `build`, `start` and `engine` drive the engine container (`docker.ts`, `engine.ts`, image from `docker/engine.Dockerfile`), or run it in-process with `--no-docker`. Data commands (`migrate`, `export`, `import`, `backup` (a `.tar.gz` name makes a full backup), `restore`, `env`, `admin`) run inside the running server through `POST /_cli` (`cli-ops.ts`), so an import reaches subscribers. Without a server they open the database themselves. `upgrade` (`upgrade.ts`) moves a project to another release: it rewrites the `@archlast/forge-*` versions in `package.json` and `forge/package.json` and the engine image tag in the `Dockerfile` and `compose.yaml` as text (formatting kept), adds the Prettier setup where missing (`addPrettier` from `create-archlast-forge`, shared with `scaffold`; the code is not reformatted), installs, and runs `codegen` with the CLI it just installed.

**Packaging.** Internal packages point `exports` at `src/*.ts` and ship source. Bun and Vite run them directly. Only the libraries (runtime, client, react, vue, svelte) build `dist/`. The runtime build must keep `child.ts` as its own entry, because the runtime spawns `child.js` next to its module, and `nest.ts` and its four companions (`nest-websockets.ts`, `nest-microservices.ts`, `nest-graphql.ts`, `nest-rpc.ts`) as more, for `@archlast/forge-runtime/nest/*`. The libraries are not minified, so users can read them. Versions move in lockstep (`scripts/version.ts`).

## Decisions to keep

`docs/decisions.md` records the settled choices and the reasons. Check it before changing any of these:

- SQLite is `bun:sqlite` only. Turso was tried and removed. Postgres is the other supported engine.
- tRPC was removed from the reactive path: `/rpc` and live queries use the plain JSON/WebSocket protocol above. tRPC is used only in Forge RPC, the transport between forge apps.
- Actions are at-most-once with no retries. Scheduled mutations are exactly-once.
- Only `ForgeError` and argument validation errors reach callers. Other errors become "Server error (request id)" outside dev.
- This is a self-hosted framework: one deployment per app. Multi-tenant hosting is out of scope.
