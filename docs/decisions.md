# Decisions

Answers to questions the build prompt and architecture doc left open, and the choices made while building. Newest last.

## Scope and tooling

- **Everything in one pass.** No milestones: dashboard, Postgres, Redis, storage, scheduler and crons are all in.
- **Bun 1.4.4**, installed with mise and pinned in `mise.toml` and `packageManager`. **bun** is the package manager. 1.4.4 is the floor (`engines`, `packageManager`, `@types/bun`, both Dockerfiles, CI): 1.4.3 has published security issues that 1.4.4 fixes (TLS, WebSockets, the database clients and the package manager; CVE-2026-111497, the bundled brotli decoder, among them), and the engine serves untrusted traffic on Bun's HTTP server.
- **Internal packages ship TypeScript source** (Turborepo's just-in-time packages). Bun runs them and Vite bundles them. Only the demo has a build step. The dashboard is a Bun HTML import, bundled by the server.
- **Typecheck with `bun check`.** The root `turbo.json` also makes `typecheck` depend on the same package's `codegen`, so codegen runs before the demo typechecks.

## Data

- **Documents are stored as JSON** (user decision). Each table is `(_id, _creationTime, doc)`, with `doc` stored as TEXT (SQLite) or JSONB (Postgres). Writes are validated against the schema. There are no per-field columns, so a schema change never migrates data.
- **Migrations** create tables and sync expression indexes. Index names hash their definition, so changing an index's fields drops and recreates it. Dropped tables keep their data. `archlast-forge migrate` applies migrations and reports stored documents that no longer match the schema.
- **IDs** are `<table>:<32 hex>`, so `db.get(id)` knows which table to read and `v.id("lists")` rejects IDs from other tables.
- **Index queries support `q.eq` only**, on a prefix of the index fields, as in the architecture doc. Results are ordered by the remaining index fields, then `_creationTime`.
- **Postgres**: writes run SERIALIZABLE and retry serialization conflicts with jittered backoff, which is safe because mutations are deterministic. Queries run REPEATABLE READ READ ONLY. JSON parameters are bound as `?::text::jsonb`, because Bun JSON-encodes a string bound directly to jsonb a second time.
- **SQLite**: `bun:sqlite` in WAL mode, one write connection (serialized in-process), and four `query_only` reader connections. **Turso (`@tursodatabase/database`) was tried and dropped** (user decision, Oct 2026; the adapter is in commit 5527bb2). At 2,000 users it used about 1.7x the runtime CPU of `bun:sqlite`, had a worse latency tail, hung the process when write transactions overlapped on separate connections (worked around by running them one at a time), builds an index over a loaded 2.5M-row table in over 2.5 GB, allows one process per file, and has no FTS5. Numbers: `benchmarks/twelve-dollar/README.md`.

## Reactivity and caching

- **Topic granularity**: the table (for full scans and writes), `table:index:[values]` for each index-key prefix, and `table:by_id:[id]` for `db.get`. A write publishes the old and new values of every index prefix.
- **Publish after commit only.** A failed mutation publishes nothing.
- **Redis bus**: one pub/sub channel carries all topics, and each server filters locally (`shortcut:` comment in `bus.ts`).
- **Query cache**: on by default (`CACHE_TTL_MS`, 60 s; 0 turns it off), in dev too. It's keyed by (function, args). A query seen reading `ctx.auth` is cached per caller: its key includes the identity, resolved fresh on each call, so a revoked session stops matching. It's skipped when any invalidation arrives during the run (`shortcut:` comment in `subscriptions.ts`). Each server evicts on bus events, and reads wait for pending evictions.

## Functions

- **Actions are at-most-once with no retries** (user decision). Scheduled mutations are exactly-once: the job row is claimed inside the mutation's own transaction. A scheduled action is claimed as `running` first. If the process crashes mid-action, the job stays `running` (`shortcut:` comment in `scheduler.ts`).
- **Crons** live in `forge/crons.ts` and are evaluated in UTC. Every server computes the same job ID for each run (`cron:<name>:<time>`), so each run is inserted once.
- **Function runtime** is a child process, not a Bun Worker, because Bun documents Worker termination as experimental. It owns the `forge/` modules, the database, Better Auth and the scheduler. The server process owns HTTP/WS, the bus, the cache and subscriptions.
- **Code or dependency changes restart only the function runtime** (user decision). HTTP and WebSocket stay up. The RPC handler is rebuilt after each load and sockets use whichever is current, so they see the new functions, and every subscription re-runs.
- **No RPC framework** (user decision; tRPC was removed). Each public function is `POST /rpc/<name>` (`/rpc/todos:add`, JSON arguments in the body, `{ result }` or `{ error: { message, code, data?, requestId } }` back with the matching HTTP status); queries also answer `GET /rpc/<name>?args=<json>`. POST requires `content-type: application/json`, which a cross-site form can't send without a preflight. Live queries use one WebSocket at `/rpc` with `{ type: "subscribe", id, name, args }` and `{ type: "unsubscribe", id }`; the server answers `{ type: "data", id, data }` (the first message is the current result) or `{ type: "error", id, error }`. The client reconnects with jittered exponential backoff and subscribes again, so a reconnect refetches. Arguments are validated in the function runtime. The dashboard API is plain JSON too: `GET /_admin/<op>?input=<json>` and `POST /_admin/<op>`. Not carried over from tRPC: request batching (each call is its own HTTP request).

## HTTP endpoints

- **`forge/http.ts`** default-exports `httpRouter()`, as `crons.ts` does with `cronJobs()`. `http.route({ method, path | pathPrefix, handler: httpAction(...) })` mirrors Convex.
- **Served under `/http`**, on the same origin as everything else (`path: "/hello"` answers at `/http/hello`, and the handler sees `/hello`). Convex uses a separate domain; a single server has no such thing, and a fixed prefix can't shadow `/rpc`, `/api/auth`, `/_admin` or `/_dashboard`.
- **A handler is an action** with a `Request` and a `Response`: the action context, the action timeout, and no database handle of its own (it calls mutations). It runs in the function runtime like auth requests do, so `forge/` code reloads and the single-process inline mode work unchanged.
- **Bodies are bytes both ways.** The IPC channel uses structured clone, so `ArrayBuffer`s cross as they are. Bodies are buffered, not streamed.
- **No CORS, no request id from the handler.** Routes answer their own `OPTIONS`. The server adds only `x-request-id`.
- **Errors** use the same rules as function calls (`toPublicError`): `ForgeError` and validation errors reach the caller, anything else is a 500 "Server error (request id)".
- Not done: streaming bodies, `HEAD` routes, a route list in the dashboard, and support in `createTestBackend`. (HTTP calls are traced now, named by route pattern: see [Observability](#observability).)

## Auth

- **Better Auth by default** (user decision), through an adapter over the document store. `users`, `sessions`, `accounts` and `verifications` are added to every schema and visible in the dashboard. Writes to them publish topics like any other write. They aren't validated against the schema, so Better Auth plugins can add fields.
- `forge/auth.ts` (optional) default-exports `defineAuth(options)`. Without it, email and password sign-in is on.
- **Identity** is resolved once per request from the `cookie`/`authorization` headers, before the function's transaction starts.
- WebSockets carry cookies only on the handshake, so the client reconnects when the session changes.
- In dev, `BETTER_AUTH_SECRET` and `ADMIN_KEY` are generated once and kept in `DATA_DIR/.dev-secrets.json`. Outside dev, `BETTER_AUTH_SECRET` is required.

## Server-side dependencies

- `forge/` has its own `package.json`. In this monorepo it is a workspace member (`apps/*/forge`).
- `codegen` and `dev` run `bun install` when that manifest or the nearest `bun.lock` changes. They pass `--ignore-scripts` unless the manifest lists `trustedDependencies`, in which case Bun runs scripts for those packages only.
- A missing package fails at load with the `bun add` command to fix it.
- Codegen fails if `src/` imports anything from `forge/` other than `forge/_generated`.

## Config

- Startup fails fast on: a non-postgres `DATABASE_URL`, `REPLICAS > 1` without `REDIS_URL` or Postgres, an unreachable Redis, only one of `S3_ENDPOINT`/`S3_BUCKET` set, and a missing `BETTER_AUTH_SECRET` outside dev.

## Validation

- **Zod runs validation; `v` stays the public API.** Validators remain plain data, so they can still cross into the dashboard and the function runtime. Each one compiles once to a Zod schema, cached per validator object. Args, documents and return values are all checked by Zod. Error messages keep the `args.title must be a string` form.
- **`returns` validators** (`query({ returns: v.string(), ... })`): when given, the validator is the function's return type, and the handler is type-checked against it. At runtime a mismatch fails the call. A mutation checks its return value inside its own transaction, so a mismatch rolls the mutation back. A handler that returns nothing counts as `null`, so it pairs with `v.null()`. A mismatch is reported as an internal error, not a bad request, because it's a server bug.
- Added `v.null()` and `v.union(...)` so that common return types such as `Doc | null` can be expressed.
- Known gap: TypeScript allows extra properties on a returned object, but the runtime object check is strict, so the extra fields fail at runtime.
- Like Convex, a handler that calls `api.<same module>.*` needs an explicit return type annotation to break the inference cycle.

## Scope

- **Self-hosted framework, not a multi-tenant platform** (user decision). One deployment per app. Hosting many customers' projects (tenant isolation, metering, a control plane) is out of scope for now.
- **Planned: the engine runs as a Docker container, started and controlled by the CLI** (user direction). The design and its open questions are in [roadmap.md](roadmap.md#target-architecture-the-engine-as-a-docker-container-controlled-by-the-cli). Until it's built, the CLI runs the engine in its own process.

## Production readiness (self-hosted)

Decided without asking, as directed, while implementing [roadmap.md](roadmap.md).

- **Internal functions.** `internalQuery`/`internalMutation`/`internalAction` are left out of the client router and `api`, and codegen puts them in `internal`. Calling one returns "Unknown function", so their names don't leak. The dashboard, the scheduler, crons, migrations and `ctx.run*` may call them.
- **Timeouts.**
  - *Soft timeout, in the function runtime:* queries and mutations get `FUNCTION_TIMEOUT_MS` (10 s), actions `ACTION_TIMEOUT_MS` (10 min). Transaction handles refuse use after the call ends, so a timed-out handler can't write afterwards.
  - *Hard deadline, in the server:* the timeout plus 5 s. A process that misses it is presumed stuck in synchronous code, so it's killed and respawned. Requests go only to processes that have reported ready.
- **Runtime pool.** `RUNTIME_WORKERS` processes per server, round-robin. Only the first runs the scheduler, migrations and the schema check.
- **Request limits.** Fixed-window rate limiting per client IP (memory, or Redis when configured) on HTTP calls, auth and WebSocket messages. There are also caps on body and message size and on subscriptions per connection. Bun's WebSocket backpressure limit (4 MiB) drops slow clients, which then reconnect and refetch. Better Auth's limiter uses the same Redis counter through `customStorage.consume`.
- **Errors.** `ForgeError` (message and data) and argument validation errors reach callers. Everything else is "Server error (request id)" outside dev, logged with that request id. Return-value mismatches count as internal.
- **Admin.** Accounts live in `_admins` (Argon2 hashes from `Bun.password`), with 12-hour sessions in `_admin_sessions` (stored as token hashes) and roles owner, admin and viewer. Access uses an HttpOnly SameSite=Strict cookie plus an `x-forge-admin` header on writes (CSRF). `ADMIN_KEY` acts as an owner. Every write is recorded in `_audit`. The dashboard is off outside dev unless `DASHBOARD=on`.
- **TLS.** Outside dev, startup fails unless `BETTER_AUTH_URL` is https (`ALLOW_INSECURE_HTTP=1` overrides).
- **Queries.**
  - *Ranges:* bounds on the next index field after the equality prefix.
  - *Order and pagination:* `order()`, plus keyset `paginate()` with base64url cursors over (remaining index fields, `_creationTime`, `_id`). Documents with a missing optional field in the index can be skipped by range and paging comparisons.
  - *Reactivity:* ranges and pages are tracked at the equality prefix.
  - *Built-in index:* `by_creation_time` is available on every table.
- **Search.** `searchIndex(name, { searchField, filterFields })`. SQLite uses an FTS5 table kept in sync by the document store and tracked in `_search_indexes`. Postgres uses a GIN index over `to_tsvector('simple', …)`. Every term must match, the last as a prefix, and search reads depend on the whole table.
- **Migrations.**
  - *Postgres indexes:* built `CONCURRENTLY` outside transactions, under a session advisory lock; invalid leftovers are rebuilt.
  - *Data migrations:* `migration({ table, migrateOne })` registers an internal mutation that processes one page per transaction. Progress lives in `_migrations`, and runs resume.
  - *Schema check:* outside dev, startup refuses when stored documents don't match the schema (`SCHEMA_CHECK=off` skips it).
- **Overload.** The function runtime is single-threaded, so past its capacity calls queue. A call is only presumed stuck, and its process killed, when the process has answered nothing since the call went in (a synchronous loop); one that is merely behind keeps its other calls. More than `MAX_PENDING_CALLS` (1000) waiting calls per runtime process are refused at once with 503 and `Retry-After: 1`. Before this, a queue over the 15 s hard timeout killed the runtime and failed every call in flight, again and again.
- **Hot path.** A cached query result keeps its serialized JSON with the entry (`Result.json`), so a hit does no JSON work, and cache invalidation in this process is synchronous. IPC messages sent in one turn of the event loop travel as one `batch` in both directions (a write's publish, log and result are three). Signed-in calls resolve the caller from the signed session cookie and a direct read of the session when nothing could change what a session means (no plugins, no secondary storage, no secret rotation); the signature check is remembered per cookie value, the session is read on every call so a revoked one stops working at once; anything else goes through Better Auth. Rate limiting off means the client address is never looked up.
- **Throughput on one core.** Production runs functions in the server process (`RUNTIME_MODE=inline`); dev keeps the child process for hot reload. SQLite writes use group commit: write transactions that queue up while one runs share one SQLite transaction, each in its own savepoint (it sees the ones before it, fails alone, and resolves only after the shared COMMIT). WAL checkpoints run on a background thread with its own connection once the WAL passes 32 MiB, never on the thread that serves requests. Inside the runtime, an exact read cache (`read-cache.ts`) keeps document reads by statement, tagged with the same topics the query cache uses; it is only on when this process is the database's only writer, never serves a table with uncommitted writes, and a read-only query that used cached rows re-runs rather than read a newer snapshot after a commit. Like counts in `include` are one covering `COUNT(*)` per parent, cached per parent. Call logs are written once a second in 250-row statements with time-ordered ids.
- **CLI data commands** (`migrate`, `export`, `import`, `backup`, `env`, `admin`) run inside the running server when one answers: `POST /_cli` with `{ cmd, args }` and the admin key, executed in the function runtime, so an import reaches subscribers and nothing contends with the server for the write lock. With no server running they open the database themselves. Values and passwords are never written to the audit log.
- **Data portability.** Export and import use JSON Lines, preserving ids and validating on import. Import refuses non-empty tables unless `--replace`. Backups use SQLite `VACUUM INTO`; for Postgres, use `pg_dump`.
- **Environment variables.** Stored in `_env` and loaded into the function runtime before user code; the process environment wins. `env set` reloads a running engine (SIGHUP for a container, the admin reload endpoint otherwise).
- **Shortcuts closed.**
  - *Lease sweep:* actions stuck in `running` fail after the action timeout plus 60 s.
  - *Redis bus:* now one channel per topic, plus an all-topics channel published only when the query cache is on.
  - *Cache invalidation:* tracked per topic, with a bounded history.
- **Observability.** JSON server logs in production; Prometheus `/metrics` behind `METRICS_TOKEN` or `ADMIN_KEY`; `x-request-id` accepted, generated and echoed. Everything else (function logs, traces, runtime samples, the dashboard's charts) is the telemetry store: see [Observability](#observability) below. It replaced the `_logs`, `_metrics` and `_cache_stats` tables and the span-per-call exporter.
- **Health and shutdown.** `/health` reports liveness and `/ready` readiness. SIGTERM marks the server not ready, closes WebSockets with 1012, drains HTTP for up to 10 s, then stops the runtime.

## Docker engine (the open questions from the roadmap)

1. **Code delivery.** In dev, `forge/` is mounted read-only at `/src/forge` and the engine syncs it into its own filesystem (`/app/forge`), so the host's `node_modules` never shadows the container's. In production, `archlast-forge build` creates an app image `FROM` the engine with the code and dependencies baked in (`engine prepare`).
2. **Server dependencies.** Installed inside the container, from `forge/package.json` minus `@archlast/forge-*` and `workspace:` entries; `@archlast/forge-runtime` is linked to the engine's copy. `node_modules` sits on a named volume. The host also installs, but only for editor types.
3. **Docker access.** The CLI shells out to `docker`; `DOCKER=podman` switches binaries.
4. **Services.** The engine only, by default. `--with postgres,redis,s3` starts sibling containers on a per-project network and wires their URLs in.
5. **Versioning.** The engine image is `ghcr.io/algochad/archlast-forge-engine:<cli version>` (`ARCHLAST_ENGINE_IMAGE` overrides). Inside this repo the CLI builds it if it's missing; a published CLI pulls it.
6. **Without Docker.** `--no-docker` (or `ARCHLAST_NO_DOCKER=1`) keeps the in-process mode, and the CLI falls back to it with a notice when Docker is unavailable. Tests use it.
7. **Networking.** The container's port 3000 is published on `--port`, and `host.docker.internal` reaches host services. Dev and production containers have different names, so one never replaces the other.
8. **CLI surface.** `dev`, `build`, `start`, `stop`, `logs`, `status`, `engine build`. Data and config commands run inside a running engine through `docker exec`.

## Modes: full-stack apps and backends

Decided together, as directed ("a framework mode on React with a lightweight bundle, like Next.js or React Router; a backend mode hosted as a container with the services it needs; the CLI supports both; init lets you choose").

- **A project has a mode** (`archlast-forge.json`: `mode` and `services`), chosen by `init` / `bun create archlast-forge`. A project without the file is a backend with no services, so nothing from before changes.
- **`init` defaults to the production stack.** A full-stack app starts with PostgreSQL, Redis, S3 storage and Caddy ticked, a backend with the first three, under the question "Which services will production need?". Only what stays ticked goes into `compose.yaml`, so unticking all of it gives SQLite and the app alone. The same list is what `dev` starts in Docker; `dev --no-docker` develops on SQLite.
- **Full-stack apps start with shadcn/ui** (user request: "add default shadcn", asking for the base color). `init` asks "Add shadcn/ui?" (default yes; `--shadcn`/`--no-shadcn`) and "Which base color?" (`--base-color`, default neutral; the seven shadcn offers today). The API (`scaffold({ shadcn })`) is opt-in, so only the command line defaults to it. It is the `base-nova` style, shadcn's own default today, which uses Base UI and the `cn` package; the library and style are not asked about, and the style cannot be changed after init (shadcn's rule for `components.json`). The files come from the shadcn registry through `scripts/update-shadcn.ts`, not from running the shadcn CLI while scaffolding, so a scaffold needs no network and every project of a version starts the same; the base-color CSS is the same text `shadcn init` writes (checked byte for byte for neutral). The starter's pages are rewritten with the components and keep the plain starter's test hooks (`.who`, `.msg`, `#email`). The plain starter stays (`--no-shadcn`) because the tutorial and the recipes are written against its stylesheet.
- **New projects come formatted with Prettier, four spaces to an indent** (user request: "the scaffolding includes prettier formatter, also 4 spaces tab is the standard"). `init` writes `.prettierrc` (`{ "tabWidth": 4 }`, the rest Prettier's defaults), a `.prettierignore` for `forge/_generated` (codegen rewrites it), a `format` script and `prettier` in `devDependencies`, then runs `prettier --write .` in the new folder, the same command as the project's `bun run format`. Formatting the result, not the templates, means the generated files (`compose.yaml`, `archlast-forge.json`, the shadcn theme) and the components refreshed from the shadcn registry come out formatted too, and the templates never drift. It runs Prettier as a child process so `scaffold()` stays synchronous; that costs about 1.3 s per scaffold, and `create-archlast-forge` depends on `prettier`.
- **`archlast-forge upgrade` moves a project to a release** (user request: "an upgrade command that will upgrade the entire project, backend only or the fullstack framework"). The version comes from `bun info @archlast/forge-runtime@<spec>` (default `latest`), so it follows the registry the project installs from and an unknown version is refused before anything is written. The archlast-forge dependencies in both `package.json` files and the engine image tag in the `Dockerfile` and `compose.yaml` are replaced as text, so a file keeps its formatting and edits; `workspace:`, `file:` and tag specs, and a non-version image tag, are left alone. Then `bun install` (root, then `forge/`) and `codegen` with the newly installed CLI. It also adds the Prettier setup new projects get (user request: "even the upgrade should trigger the scaffold of prettier so that old projects ... get it"), through the same `addPrettier` as `scaffold`, piece by piece where missing: `.prettierrc` only when the project has no Prettier config at all, so a config of its own wins, and `format`/`prettier` only when absent. It doesn't reformat the code: a whole-project reformat is a diff to review on its own (and conflicts with open branches), so the CLI says to run `bun run format`. It doesn't touch the rest of `compose.yaml` (the file is the user's), React or other dependencies, or the data. Projects whose CLI predates it run it once with `bunx --package @archlast/forge-cli@latest archlast-forge upgrade`.
- **Tailwind goes through Tailwind's own Bun plugin, loaded from the project.** The framework's browser build adds `bun-plugin-tailwind` when `bun-plugin-tailwind` resolves from the project root, and does nothing otherwise, so the framework package gains no dependency and projects without Tailwind build as before. The plugin carries Tailwind's compiler and its native scanner for every platform (27 MB), which is why it is not a dependency of the framework. Dark mode is the `.dark` class (shadcn's convention) with a script in `root.tsx` that follows the system until the toggle is used.
- **Full-stack apps run inside the engine process.** `startServer({ app })` takes a host that is called for every request the engine has no route for (`/rpc`, `/api/auth`, `/http`, `/_admin`, `/_dashboard`, `/_cli`, `/health`, `/ready`, `/metrics` stay the engine's). The host can call public functions in-process as the visitor (queries through the query cache, as a private copy), ask who the visitor is, check the rate limit, and opt a response out of the idle timeout. The runtime package knows nothing about React.
- **The router is React Router's data router (8.5, pinned), not our own.** File routes, the build, server rendering, the live cache and the viewer are ours; matching, nested layouts, loaders, redirects, error boundaries, scroll and history are React Router's, which has the edge cases covered. `@archlast/forge-framework` re-exports a curated part of it.
- **File routes** (`app/routes`): `index.tsx`, `[param]`, `[...splat]`, `_layout.tsx`, `(group)/`, and `_`-prefixed names are private. Two files for one URL, or a parameter mixed with text, fail the build with the file names. `app/root.tsx` exports `Layout` (the `<html>` document, also around error pages), a default component and optionally `ErrorBoundary`. There is no `<title>` convention: React 19 hoists `<title>` and `<meta>` into `<head>`.
- **Loaders are isomorphic.** `loader({ request, params, ctx })` runs on the server for the first request and in the browser afterwards. `ctx.query` fetches and puts the result in the TanStack cache under the key `useQuery` uses, so the page renders with data on the server, the cache is embedded (`dehydrate`) and restored in the browser (`hydrate`), and the live subscription replaces it with the same value. `ctx.viewer()` is memoized per request on the server and asks Better Auth (`disableCookieCache`) in the browser, because the session store lags a sign-in by a moment and a loader that redirects anonymous visitors would otherwise bounce a user who just signed in.
- **The viewer is part of the page.** `window.__FORGE__` carries `{ dev, now, timeZone, viewer, queries, hydration }`. `useViewer()` renders on the server, and follows sign-in and sign-out through `ArchlastForgeClient.onSessionChange`, which fires only once something uses `auth`, so a page that never signs in makes no session request. `useSession()` got a server snapshot (pending), because `useSyncExternalStore` throws without one.
- **Errors are sanitized before they are rendered.** The server renders with the same errors it embeds for the browser: `ForgeError` messages and call failures (which already carry public messages) pass; any other error becomes `Server error (request <id>)` outside dev, and is logged in full. Rendering the original error leaked a loader bug's message into the HTML.
- **Times hydrate cleanly, with two hooks and no new rule for loaders** (user request, after a real-browser check with the server in UTC and the browser in another zone: a time formatted without a zone, `Date.now()` in a render, and a query argument worked out from the clock each made React throw the server's HTML away, `Minified React error #418` in production). `useTimeZone()` and `useNow(interval)` return what the server rendered with while the browser hydrates (its instant, `now`, and the zone it used, `timeZone`, both in `window.__FORGE__`) and the browser's own right after, through `useSyncExternalStore`'s server snapshot, so the switch is an ordinary update and not a mismatch. The server learns the zone from the `forge-tz` cookie, which the browser sets only once a component has used `useTimeZone` (the zone name and nothing else, validated with `Intl.DateTimeFormat` before use; `Max-Age` one year, `SameSite=Lax`). The cookie was chosen over a client hint header or a query parameter because it needs no round trip, and the HTML was already `vary: cookie`, `private, no-cache`, so nothing about caching changed. The first visit has no cookie and renders in UTC, then moves to the visitor's zone after hydration: the alternative, a blocking script that sets the zone before React runs, would make that first render depend on something the server cannot see. Arguments that come from the clock are worked out once in the loader and read with `useLoaderData` (already how the page gets one value on both sides), so there is no hook for them. `hydrateRoot` gets `onRecoverableError`, which does what React does without one (`reportError`) and adds a console warning for mismatches that points at the docs, and in dev a notice on the page; the minified production message was the only clue before. Nothing private is added to the page: the zone is the visitor's own, echoed back to them. Existing apps that do nothing keep working: the hooks are opt-in and the extra fields are ignored.
- **Server rendering** uses `renderToReadableStream` and waits for `allReady`, so the status code and headers are right and there are no half pages. No streaming, no static generation, no route actions (a server-handled POST on a page URL would need CSRF protection; mutations are called from the browser).
- **Build** (`Bun.build`, twice): the browser bundle (split per route, hashed, minified, with gzip and brotli copies stored next to it) and the server bundle (one file, packages external, CSS ignored). The metafile maps each route to its chunk and shared imports, which become `modulepreload` links; all CSS is linked in `<head>`, because Bun merges the CSS of lazily loaded routes into the entry's stylesheet. Output goes to `.forge/build/<version>`; dev keeps the previous version for pages already open. `metafile` paths are relative to the working directory, not to `root`.
- **Development** is one process on the host: the engine and the app, rebuilding in about 0.2 s, reloading browsers over server-sent events, with build errors shown over the page. Docker runs only the services (PostgreSQL, Redis, RustFS), on 127.0.0.1 with free ports, and `dev` stops the ones it started when it ends; data stays in named volumes.
- **Production in a container**: `engine prepare` copies `app/`, installs the app's own dependencies, **links** React and the `@archlast/forge-*` packages from the engine image (two copies of React break hooks), generates the types and builds. `engine serve` then serves the build. A stale host lockfile that names local tarballs no longer breaks the server-dependency install: it is retried without the lockfile.
- **Backends are a stack.** `init` writes `compose.yaml` (the app and the chosen services, wired with health checks and `depends_on`), a `Dockerfile` (`FROM ${ENGINE_IMAGE}`, `COPY . /src`, `engine prepare`), `.dockerignore`, `.env` (secrets generated once, mode 0600, never overwritten) and `.env.example`; with Caddy, a `Caddyfile`. The compose file is the user's afterwards. PostgreSQL and Redis are not published; RustFS publishes one port, because browsers use presigned URLs; with Caddy only 80 and 443 are. The dashboard is on in the stack. `up` builds with a spinner, waits for the engine image's health check, and prints the addresses; on failure it shows the end of the build output or the app's last log lines.
- **Services in `dev` follow where the engine runs.** For an engine on the host they publish ports on localhost; for an engine in Docker they share a network and use container names. `dev` waits for PostgreSQL and Redis to accept connections before starting the engine.
- **Packaging**: `@archlast/forge-framework` is a library (`dist/` with code splitting, so one copy of the router context); the CLI loads it from the project at runtime, so a backend never installs React. `create-archlast-forge` ships source with `@clack/prompts`; the CLI depends on it for `init`.
- **Not done**: streaming and static generation, route actions, per-route CSS on demand, hot module replacement (a save reloads the page), a route list in the dashboard, `createTestBackend` support for pages, and Caddy is tested end to end only for `localhost` (its own certificate authority); issuing real certificates needs a public domain and is not tested.

## Packaging

- Libraries (runtime, client, react, vue, svelte) publish `dist/`: bundled ESM (each entry separately, because the runtime spawns `child.js` next to its own module) plus `.d.ts` from `tsc --emitDeclarationOnly`. Bun-run packages (cli, dashboard, create-archlast-forge) publish source.
- Releases are lockstep (`scripts/version.ts`). `scripts/pack.ts` stages the packages, pins `workspace:` dependencies and packs tarballs; `--smoke` proves them in a fresh project. A tag runs the release workflow, which publishes to npm (needs `NPM_TOKEN`) and pushes the engine image to GHCR; the runbook is `docs/releasing.md`.
- **npm names**: `@archlast/forge-runtime`, `-client`, `-react`, `-vue`, `-svelte`, `-framework`, `-dashboard`, `-cli`, and the unscoped `create-archlast-forge`. They live in the existing `archlast` org, which already publishes `@archlast/cli`, `@archlast/client` and `@archlast/sdk-*` (another product), so every name here carries the `forge-` prefix to stay clear of them. The command is still `archlast-forge`, and the engine image is `ghcr.io/algochad/archlast-forge-engine`.
- MIT licensed, and the repository is meant to be public. Packages carry the license, repository and engine (`bun >=1.4.4`) fields; `pack.ts` adds the license and a short README to each tarball. The release workflow builds the engine image before it publishes, and publishes prereleases (`v0.2.0-rc.1`) under the `next` tag. `react` is a `^19.3.1` peer, not an exact pin.
- **Minify where it is safe** (user decision, from Bun's minifier docs). A full-stack app's production browser bundle is fully minified, as before. Its server bundle is minified for whitespace and syntax but not identifiers, so names stay, and gets a linked source map, so stack traces point at the source. Production bundles drop `debugger` statements, and so does the docs site. The published libraries are not minified, as Bun's docs advise for code other people read. The engine is not compiled to one executable (`bun build --compile`): the user chose not to, and the engine spawns child processes and runs `bun install` in the image, which a single binary would have to rework.

## NestJS

- **NestJS lives in the runtime, as `@archlast/forge-runtime/nest`** (user decision: "nestjs is a backend framework so it will live in the backend", available to both modes). Projects import Nest's decorators, exceptions and pipes from there and never install `@nestjs/*`; the runtime depends on `@nestjs/common` and `@nestjs/core` 12, `reflect-metadata`, `rxjs` and `path-to-regexp`. Only projects that import the subpath load Nest.
- **Our own adapter, not `@krisanalfa/bunest-adapter`** (user decision, after the facts below). bunest 0.6.0 declares NestJS 11 as a peer (Nest is at 12), its one file imports graphql-yoga, graphql, `@nestjs/graphql` and `@nestjs/websockets` when it loads, and its speed comes from owning a `Bun.serve` with Bun's router. The engine already owns the server and forwards `/http/*` into the function runtime, which is where a controller gets its ctx, so bunest would have meant a second server and a local hop. `ForgeAdapter` takes requests straight from the engine's `/http` routing: Nest's routes go on a small Express-style router (path-to-regexp 8, as Nest 12 writes paths), and `handle()` returns a Web `Response`.
- **A request is an HTTP action.** `nest()` mounts Nest as `pathPrefix` routes (default `/`) built with `httpAction()`, so rate limits, request ids, logs, metrics and the action time limit apply, `http.route()` routes keep priority, and controllers get an `ActionCtx` (`@Ctx()`): they reach data through `ctx.runQuery`/`ctx.runMutation`, which keeps writes in transactions and reads reactive. HttpExceptions answer as Nest answers them; a `ForgeError` answers 400 and anything else 500 with the request id, exactly as from an HTTP action.
- **Services get the call's ctx through request scope.** `ForgeService<C>` has `this.ctx` (property injection of the request-scoped `CTX` provider), and `@InjectCtx()` does the same for a constructor parameter. `inject(ctx, Service)` registers the ctx as the "request" of a new context id and resolves the service, so a function's services see that function's ctx and share instances within the call; singletons stay singletons. `inject`'s type only accepts a ctx that has what `C` asks for (a query can't get a `ForgeService<MutationCtx>`). The cost is an instance of each request-scoped class per call.
- **The engine compiles decorators itself.** Bun applies the tsconfig of the directory the process runs in, not the one next to the file, so `forge/tsconfig.json`'s `experimentalDecorators` would be ignored from the CLI or the engine image. `loadProject` registers a `Bun.plugin` for the `forge/` directory: a file that contains a decorator is built on its own with `Bun.build` (the flags forced, extending `forge/tsconfig.json`, every import external, inline source map, so stack traces keep their lines); other files load unchanged. Bun's transpiler alone moved lines, which is why it is `Bun.build`. The templates set both flags in `forge/tsconfig.json` (and `experimentalDecorators` in a full-stack app's root tsconfig, which type-checks `forge/` through `api.ts`) for editors and `tsc`.
- **The whole of Nest is in the runtime** (user decision: CORS, WebSocket gateways, microservices, GraphQL and Express-style writes "fully supported", with bunest as the reference, and every package in the runtime rather than optional). `@nestjs/websockets`, `@nestjs/microservices`, `@nestjs/platform-socket.io` (with `socket.io` and `engine.io`), `@nestjs/graphql`, `graphql`, `graphql-yoga`, `graphql-ws`, `cors` and the clients Nest's transports load (`ioredis`, `nats`, `mqtt`, `kafkajs`, `amqplib` and `amqp-connection-manager`, `@grpc/grpc-js` and `@grpc/proto-loader`) are dependencies, so no transport needs an install. A packed backend's `node_modules` measures 122 MB, about 32 MB of it the transport clients and Socket.IO. Bundling them into the runtime was rejected: users' resolvers and gateways need the same `graphql` and Nest classes their types name. They load only for projects that import them. The companions are `/nest/websockets`, `/nest/graphql` and `/nest/microservices`; they import the package by its own name, because a relative import made the build put `nest.ts` in a shared chunk, which loses its `export *` of `@nestjs/common` (a CommonJS package whose names Bun can't list).
- **The engine holds gateway sockets; the runtime has the gateways.** The server upgrades WebSockets under `/http/*` (the `/rpc` origin check and rate limit apply) and sends their events to the function runtime as messages that need no answer (`{ t: "ws", op: "open" | "message" | "close" }`); the runtime sends to or closes a socket the same way. A socket stays with the worker that took its open, and when a worker stops or crashes its sockets are closed so clients reconnect. The runtime gives a project's `nest.ts` what it needs through a `Symbol.for` global (identity, an `ActionCtx`, send, close), because the project's copy of the package is not the engine's, and `nest.ts` registers where socket events go the same way. `ForgeWsAdapter` speaks `@nestjs/platform-ws`'s protocol (JSON `{ event, data }`); `websockets: "socket.io"` swaps in `ForgeIoAdapter`, Nest's `IoAdapter` with an engine.io server whose `wsEngine` hands over the engine's sockets, and whose long-polling requests come through the HTTP adapter. The caller is resolved once from the upgrade request.
- **Every gateway socket is held by worker 0.** With `RUNTIME_WORKERS > 1`, `wsEvent` pins opens to the first worker and the server sends Engine.IO polling requests (`?EIO=`) there too, so `server.clients`, Socket.IO rooms and a polling session's state are in one place. Gateway handlers don't spread across workers; HTTP routes and GraphQL queries do. Events crossing workers go through `createPubSub`, the engine's: a publish is a `{ t: "relay" }` message that the server sends to every worker. Several engine servers (the Redis bus) don't share sockets or pubsub events; the database is how to reach everyone there.
- **Responses stream when they are written.** Nest's `res` has Express's and Node's API. Until a handler writes or flushes, the response is one body; after, it is a stream. The engine passes a stream through when the Response is marked with `Symbol.for("archlast-forge.stream")` or is `text/event-stream` (so plain HTTP actions can stream SSE too). Inline it is the Response's own body; from a child process the result goes first and the bytes follow as `{ t: "chunk" }` messages. A client that leaves cancels the stream: inline the Response's body is cancelled; from a child process the server sends `{ t: "cancel", id }` and the child cancels its reader, so `req` and `res` get `"close"` in both.
- **GraphQL is our driver on Yoga, not Apollo or bunest's.** Nest's drivers pick an integration by `httpAdapter.getType()`, and ours is neither Express nor Fastify. `ForgeGraphQLDriver` takes the schema `@nestjs/graphql` builds, serves it with Yoga (which runs on Web requests, the form the engine already has) on GET and POST at `path`, and runs subscriptions with `graphql-ws`'s `makeServer` on `onSocket(path)`.
- **Microservices listen inside the function runtime.** `nest(http, { microservices })` calls `connectMicroservice()` for each and `startAllMicroservices()` after `init()`. Their handlers get an anonymous `ActionCtx` (a message has no caller) through the engine's `Ctx`, which shadows Nest's in `/nest/microservices` (Nest's is `TransportCtx`). Only the first runtime process (`ARCHLAST_WORKER` 0) connects them, so a port is bound once with `RUNTIME_WORKERS > 1`.
- **Still out:** `listen()`, static assets, views, versioning other than URI, `@Ip()`. One Nest app per process (`nest()` once), which is one per deployment.

## Observability

- **Built into the engine and its dashboard** (user request: "a builtin observable system dashboard + the reactive dashboard system we have", after Traceway and NestJS Observe). One dashboard at `/_dashboard`: the observability pages (Observe, Performance) next to the BaaS ones (Backend, Admin). Nothing to install, `TELEMETRY=off` to turn it off; then the dashboard says so instead of failing, and Users, Jobs and Logs open on the views that don't need it.
- **Traceway is ported, not forked.** Traceway (MIT) is Go, Svelte and ClickHouse; the engine is one Bun process on SQLite or Postgres. Its exception fingerprint and endpoint impact score (Apdex and its floors) are ported to TypeScript in `telemetry/traceway.ts`, with the notice in `packages/runtime/THIRD_PARTY_NOTICES.md` (shipped in the tarball). Changes, marked in the file: only the app's own stack frames are hashed when there are any (dependency frames move with every upgrade), message-only errors have their variable parts taken out, and Apdex T depends on the kind of request.
- **NestJS Observe is matched, not copied.** It is proprietary: its feature set and page structure (overview, requests, errors grouped into issues, users, jobs, spans, hotspots, map, runtime, releases, SLOs, alerts) were the reference, in our own design and code. None of its code, artwork, logo or text is used.
- **A store of its own.** On SQLite, `DATA_DIR/telemetry.db`: SQLite has one writer, and telemetry in `app.db` would queue behind the app's writes (and hold them up). On Postgres, `_otel_*` tables in the app's database, so every server shares them. The store, its queries, compaction and alert checks run on a Bun Worker thread, so a 30-day chart never delays a request; the server sends it batches once a second.
- **Every request counted, detail sampled.** Per-minute rollups per operation with log-scale histograms (8% buckets) make counts exact and percentiles accurate to a few percent at any traffic. Spans are recorded for up to `TELEMETRY_DETAIL_PER_SECOND` (200) requests a second, then for a share that keeps that rate, weighted 1/share in span statistics; the rest run untraced in the function runtime. Recording every span cost about 17% of throughput on uncached calls at saturation; with the detail rate, throughput with telemetry on is within the noise of off (about 4,300 vs 4,100 calls a second on one core; 14,500 vs 15,000 cached). Kept traces are tail-sampled after they finish: errors and slow requests (over 4×T) have their own budget, `TELEMETRY_TRACES_PER_SECOND` (25) each, with weight 1/probability so counts read from kept traces stay unbiased. A caller's sampled `traceparent` forces detail, as OpenTelemetry's parent-based sampler does.
- **Spans** come from the function runtime through `AsyncLocalStorage`: each function (nested calls included), each database statement (a wrapper on the transaction), each outbound `fetch` (which carries `traceparent` on), Nest methods and `trace.span()`. Own time is a span's duration minus the union of its children's; Hotspots groups it by code unit (forge module, Nest class, database, host).
- **Nest classes are timed by our decorators.** `Injectable`, `Controller`, `Resolver` and `WebSocketGateway` from `@archlast/forge-runtime/nest` wrap the class's methods (keeping Reflect metadata), so only the user's classes are spans, not Nest's or libraries'.
- **Releases** are named by the platform's commit variable (`FORGE_RELEASE`, `GIT_COMMIT`, `GITHUB_SHA`, …) or a hash of `forge/`, and judged on the 30 minutes before and after, cut at the minute, with at least 20 requests a side.
- **OTLP ingest without an SDK.** `/otlp/v1/{traces,logs,metrics}` take protobuf (a hand-written decoder for the OTLP v1 messages; `protobufjs` is only a test dependency) or JSON, gzip or deflate. Ingest keys are stored hashed, can pin a service name, and are not needed in dev. Cumulative metrics become per-minute deltas, resetting only when a value drops. An engine's own export pointed back at it (same `OTEL_SERVICE_NAME`, marked by an `x-forge-service` header) is ignored with one warning, because those requests are recorded already.
- **Alerts** are checked every minute in the worker and posted to Slack-compatible webhooks (`text`). A window with no requests keeps a rule's state: no data proves neither a problem nor a recovery. Deleting an SLO deletes its burn-rate rules.
- **Not done:** session replay, on-call schedules and paging, AI or LLM call tracing, status pages, assigning or commenting on issues, retention per signal, sampling decisions shared across services, and GC or event-loop utilization metrics (Bun exposes neither). The Docker end-to-end run (`bun run e2e`) was not repeated for this work, because Docker was unavailable where it was built.

## Many users on one server

From a hospital-scale load test of an app on the engine (300 signed-in staff, every function behind an authorization check). Findings were checked against the code and profiles first; the measurements are in `benchmarks/hospital/README.md`.

- **A query can declare `access`, and then its result is shared.** The engine can't tell a check from a use of `ctx.auth`, so it cached any query that touched it once per user: 300 users meant 300 runs of the same query, and 300 re-runs after each change. A query may now say which part is the check (`access`, run for every caller on every serve and push) and which is the data (the handler, run once for everyone who passes, with `ctx.auth` made unavailable so the result can't depend on the caller). It is opt-in because only the author knows. Rejected: guessing from behaviour (a result that happens to match for two callers proves nothing), and a key by role (the engine would have to know what a role is).
- **The check is watched like any read.** What `access` read, and the caller's own session and user rows, are topics: a write to one evicts the kept check and wakes a subscription, so a deactivated user or an ended session is refused on the very next call and cut off live. A refusal is never kept. A check is kept only for a caller that could be pinned to topics (the direct session path); with Better Auth plugins or secondary storage it runs every time.
- **The server keeps who is calling.** Resolving the caller was a round trip to the function runtime on every authenticated call, which capped a cached authenticated query at about a quarter of an anonymous one. The server now keeps the identity per credential until a write to the session or user it came from, or the session's end or refresh, whichever is first. Not a time-to-live alone: that would let a ban wait out the timer. Anonymous requests skip the lookup.
- **Queued queries start a few per turn, not all at once.** Against SQLite a query never waits for I/O, so a burst ran as one long run of microtasks: nothing was sent and no message read until the last query was done. The server, hearing nothing, took the backlog for a hang and killed the process, failing every call in it. The process now starts as many as fit a 4 ms slice at the pace queries have been taking (a cheap query batches as before, a heavy one goes alone). Mutations are not queued: the one writer runs them in turn, and mutations that start together are committed together (group commit), which one start per turn halved. Rejected: one query per turn (measured 15% slower at 10% writes).
- **Overload is refused early.** A query that would wait longer than a function may run is refused at once with the retryable `503`, from the pace the process has shown over the last two seconds (not trusted until it has five answers, and not once stale, so a burst after quiet gets in); a queued query that has waited that long is refused by the process instead of being run for a caller who has gone. Mutations, actions and HTTP routes are not queued this way, so none of them holds a place.
- **A slow run no longer multiplies.** Callers waiting on a run that a write overlapped each started their own run; now one starts it and the rest join, and under steady writes that was the difference between one run and one per waiting caller. A run that a write overlaps still can't be cached or shared. That is correct, and it is why a query over data that is written constantly gains little from any cache.
- **Calls go to the process with the fewest waiting**, not round-robin, so a long call holds up only what is queued behind it. Queue depth is in the Runtime page's in-flight figure, `/metrics`, and a warning at about two seconds of work waiting.
- **A result crosses to the server as its JSON text, and its topics as one string.** The server answers with the JSON and never needs the object unless something reads `value`, which then parses from the text (once; `lazyValue`). The object tree and a long array of topic strings were most of what a large result cost to move. Standalone, a round trip took 0.51 ms with the tree against 0.08 ms without for 34 KB of JSON, and 4.4 ms against 0.7 ms for 273 KB; 5,000 topics took 2.5 ms as an array and 0.3 ms as one string (beside 550 KB of JSON, 3.1 ms against 1.0 ms in all). With a busy sender the tree also made a 550 KB result arrive 1.8 s late on average against 1.2 s as JSON alone. A shared (Redis) cache entry loses its second copy of the data too, and entries from an older server (with both) are still read. Rejected: compressing (the cost is serialization, not bytes on the wire), and a separate channel for results (the pipe is the only one between the processes that survives a restart).
- **Results the pipe hasn't taken yet hold the queue back.** A busy runtime process can only write to the pipe between its own turns, about 4 MB a second, which a 150 ms query returning 550 KB roughly equals. Past that the backlog grew in the pipe, where nothing could refuse a call and answers reached the server seconds after they were made. Large results (64 KB and up) are sent as messages of their own and `process.send` reports each one, and no queued query starts while more than 4 MB are unreported (or none was written for 5 s, which means the pipe is not draining). Measured on the 200-user census burst, four rounds each: the first tenth of the answers at 2.5–5.3 s instead of about 11 s, the median served call at 7.6–10.0 s instead of 11.2–11.6 s, the same number served (mean 101 against 99). 1 MB and 2 MB windows served fewer (mean 87 and 87) for no better median; 4 MB stays. Small results never reach the limit, so the common case is unchanged. A call that waited past its deadline is dropped on every turn and by a timer, whatever the process is doing.
- **The process sampler reads the heap with `process.memoryUsage()`.** `bun:jsc`'s `heapStats()` walks the heap synchronously: 36 ms at 27 MB of live objects, 180 ms at 109 MB, 490 ms at 281 MB, in the server and in every runtime process every 10 s. `memoryUsage()` gives the same figures in 0.02 ms (its `heapUsed` can include garbage not yet collected, as Node's does). The observability stack was measured as a whole and is not what held the extreme burst back: with telemetry and the sampler both off, tail latency in the stress scenario and the burst were unchanged within noise.
- **`RUNTIME_WORKERS` still defaults to 1.** More processes help queries that compute and hurt light ones (each call crosses to a process and back: about twice the CPU of running inline), so a default would be a loss for as many apps as it helps. The warning says when to raise it.

## Backups, built-in storage and settings

Asked for together: "a backup system for the entire baas … schedule backups, download them and restore, snapshots of the data and functions and files", "an in process s3 engine … so that we still have object storage if we're in dev mode and did not opt for an s3 storage", and "all the things that are configurable for the baas should be configurable in the dashboard … put it in the settings module", with no breaking changes. Three choices were put to the user and are marked.

- **A backup is one `.tar.gz`** (`server/backup/`): `manifest.json` first, then the documents as `export` JSON Lines, the scheduled jobs and migration states, `_env` and `_settings` with their values, the `forge/` source (no `node_modules`, `data/`, dot files or files over 10 MB) and every object a `_storage` row names. Plain tar so `tar tzf` reads it, written and read as streams by a small ustar/PAX implementation of our own: `Bun.Archive` holds every entry in memory, and a backup with its files can be larger than that. Dashboard accounts, sessions, the audit log and telemetry are left out: they are the deployment's, not the app's.
- **The snapshot is one read transaction** (SQLite's reader snapshot, Postgres `repeatable read read only`), rows read raw and paged by `_id`, so a backup never holds half a mutation and writes carry on. Files are read afterwards; one deleted meanwhile is counted as missing, not an error.
- **Where backups go** (user's choice: next to the files, plus a bucket of their own): `BACKUP_S3_*` (a bucket of their own, recommended off-machine) wins, then `BACKUP_DIR`, then the files' bucket under `_backups/` with `STORAGE=s3`, then `DATA_DIR/backups`. The list is the `_backups` table; archives in the store that it doesn't know about are listed as "found" so a fresh database can restore from a bucket. A folder is per server, so with replicas use a bucket.
- **Restore brings back data and files, not code** (user's choice). Code ships with git and the image, and in production it is baked into the image, so writing `forge/` back would be wrong there and destructive in dev. The source is in the archive, and the dashboard marks backups made with code other than what runs (a hash of the same file set). Environment and settings are restored only when asked: restoring into another deployment would replace its keys.
- **A restore is all or nothing for data**: a safety backup first (its failure stops everything), files next (written back under their keys; files added since stay), then every schema table truncated and refilled, validated by the current schema, with jobs and migrations (and config if chosen) in one transaction. It publishes no per-document topics (`Executor.rewrite`); it publishes `_forge:reset` once, and every server drops its query cache and re-runs its subscriptions, so other servers on the bus see it too. Tables the backup has and the schema doesn't are refused before anything is written.
- **Scheduled backups run on every server and happen once**: worker 0 of each server checks `BACKUP_SCHEDULE` (cron, UTC) every 30 s and claims the slot by inserting a row whose id is the slot time; only the insert that lands runs. A missed slot runs once on return. `BACKUP_KEEP` prunes scheduled ones only; manual, uploaded and safety backups stay until deleted.
- **Built-in storage, not an S3 server** (user's choice: on in dev without S3, opt-in in production with `STORAGE=local`, so a deployment without storage stays one). Files live in `DATA_DIR/storage/objects` (types in `meta/`) and the engine serves `/_storage/<key>` with URLs it signs itself (HMAC over method, key and expiry with a key derived from `BETTER_AUTH_SECRET`; the host is not signed, so they work through any address). It implements the `Storage` interface `ctx.storage` already used, so functions are unchanged; speaking the S3 wire protocol (SigV4, XML listings, multipart) would only serve tools nothing here uses. Uploads stream to a temp file and are renamed in place. Responses carry `Content-Security-Policy: sandbox` and `nosniff`, because files are served from the app's own origin and an uploaded HTML page must not run as the app. `REPLICAS > 1` refuses it.
- **Bigger bodies only where uploads go.** With the built-in storage or the dashboard on, Bun's body limit is raised to `MAX_UPLOAD_MB` and every other body (`/rpc`, `/http`, `/api/auth`, `/otlp`, `/_cli`, the admin API) is read through `readBytes`/`readText`, which keep `MAX_REQUEST_BYTES` (413 `PAYLOAD_TOO_LARGE`), declared lengths and chunked bodies alike. Without either, Bun's limit is what it was.
- **Settings live in `_settings`, under the environment.** `server/settings.ts` lists every variable the engine reads with its group, type, default and doc. The server reads `_settings` itself at startup (before the runtime, which owns the database, exists: workers and limits depend on it), and the process environment wins over every stored value, so an existing deployment means exactly what it did. Values are checked when saved (type, then a full `loadConfig` with them); a stored set that stops being valid later is ignored at startup with the reason shown, rather than keeping the engine down. Environment-only: `DATA_DIR`/`DATABASE_URL` (where the settings are), `PORT`/`HOST` (port mapping), `REDIS_URL` (connected before serving), `REPLICAS`, and `BETTER_AUTH_URL`/`BETTER_AUTH_SECRET`/`ADMIN_KEY`/`DASHBOARD` (a wrong value locks you out). Owner only; audited without values.
- **Applying is a restart, not hot reconfiguration.** Most settings are read once into objects (the cache, the limiter, Bun.serve, the runtime pool); making each live was many small risks. The CLI's `serve()` restarts the server in place (`startServer({ restart })`, `stop({ keepApp })`) from the dashboard's **Restart now**; an embedder without it is told to restart the process. Backup settings are read per use and apply at once.
- **The dashboard is bundled in production mode everywhere**, dev included (`development: false`): minified (434 KB of JS instead of 1.7 MB) and on React's production build. The cost is that edits to the dashboard's own source need a restart in this repo.
