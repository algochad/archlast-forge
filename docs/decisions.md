# Decisions

Answers to questions the build prompt and architecture doc left open, and the choices made while building. Newest last.

## Scope and tooling

- **Everything in one pass.** No milestones: dashboard, Postgres, Redis, storage, scheduler and crons are all in.
- **Bun 1.4.4**, installed with mise and pinned in `mise.toml` and `packageManager`. **bun** is the package manager. 1.4.4 is the floor (`engines`, `packageManager`, `@types/bun`, both Dockerfiles, CI): 1.4.3 has published security issues that 1.4.4 fixes (TLS, WebSockets, the database clients and the package manager; CVE-2026-111497, the bundled brotli decoder, among them), and the engine serves untrusted traffic on Bun's HTTP server.
- **Internal packages ship TypeScript source** (Turborepo's just-in-time packages). Bun runs them and Vite bundles them. Only the demo has a build step. The dashboard is a Bun HTML import, bundled by the server.
- **Typecheck with `bun check`.** The root `turbo.json` also makes `typecheck` depend on the same package's `codegen`, so codegen runs before the demo typechecks.

## Data

- **Documents are stored as JSON** (user decision). Each table is `(_id, _creationTime, doc)`, with `doc` stored as TEXT (SQLite) or JSONB (Postgres). Writes are validated against the schema. There are no per-field columns, so a schema change never migrates data.
- **Migrations** create tables and sync expression indexes. Index names hash their definition, so changing an index's fields drops and recreates it. Dropped tables keep their data. `archlast-forge migrate` applies migrations and reports stored documents that no longer match the schema.
- **IDs** are `<table>:<32 hex>`, so `db.get(id)` knows which table to read and `v.id("lists")` rejects IDs from other tables.
- **Index queries started with `q.eq` only**, on a prefix of the index fields, as in the architecture doc. They now also take range bounds (`gt`, `gte`, `lt`, `lte`) on the field after the `eq` prefix: see [Reading data](../apps/docs/content/queries.mdx). Results are ordered by the remaining index fields, then `_creationTime`.
- **Postgres**: writes run SERIALIZABLE and retry serialization conflicts with jittered backoff, which is safe because mutations are deterministic. Queries run REPEATABLE READ READ ONLY. JSON parameters are bound as `?::text::jsonb`, because Bun JSON-encodes a string bound directly to jsonb a second time.
- **SQLite**: `bun:sqlite` in WAL mode, one write connection (serialized in-process), and four `query_only` reader connections. **Turso (`@tursodatabase/database`) was tried and dropped** (user decision, Oct 2026; the adapter is in commit 5527bb2). At 2,000 users it used about 1.7x the runtime CPU of `bun:sqlite`, had a worse latency tail, hung the process when write transactions overlapped on separate connections (worked around by running them one at a time), builds an index over a loaded 2.5M-row table in over 2.5 GB, allows one process per file, and has no FTS5. Numbers: `benchmarks/twelve-dollar/README.md`.
- **`where`, `orderBy`, `select` and batch writes on `ctx.db`** (user request: an EF Core-inspired builder; inventory approved). `where((q) => …)` compiles to SQL with the dialect's field expressions (`json_extract` / `doc->`), so SQLite's expression indexes serve `eq` and ranges, and rejected rows are never loaded; it composes with `withIndex` (which still decides the read set: topics stay at the equality prefix, coarser than the condition, never missed), `skip`, `count`, pages and totals. A predicate is a branded object only the builder makes, and field names must be identifiers (they go into SQL text): values are always parameters. `not` is `CASE WHEN … THEN 1 ELSE 0 END = 0` and `neq` includes a missing field, so a NULL comparison counts as not matching what is negated. `prefix` is a range on SQLite (index-friendly) and `starts_with` on Postgres. `orderBy` replaces the index's order; ties go by `_creationTime`, `_id` in the last key's direction (so an index serves the order), mixed directions page with an expanded keyset condition. `select` projects after filters and joins (they need whole documents): it shrinks results, not reads. In dev, on SQLite, a `where`/`orderBy` statement is explained once per process and warns when the plan scans the table (or walks a whole index while filtering) or sorts in a temp B-tree. `insertMany`/`updateMany` validate every row with the same `checked()` as single writes before any SQL, so `partial` mode only reports rows that never reached the database (a failed statement aborts a Postgres transaction); `insertMany` writes 200 rows per `INSERT`. Creation times now strictly increase within a process (`max(now, last + 0.001 ms)`), so a batch keeps its order. Measured: see the Batch writes section of Reading data.
- **Numbered pages are `skip(n)`, a chainable step** (user request from an app with "page 3 of 10" tables, which emulated it with `take(page * size).slice(from)` and loaded every earlier page). Without a `filter()` it is `LIMIT … OFFSET n` on the same statement, so skipped documents are never loaded or counted against the scan limit; with one, `n` counts documents that pass every filter, wherever `skip` is in the chain, and the scan limit applies. It is capped at 100,000 (the scan limit), and two calls add up. `count()` and the aggregates after it cover what is left. With `paginate()` it places only the first page (`cursor: null`): applying it again with a cursor would skip `n` more on every page, and this way the `continueCursor` carries on with keyset paging. `paginate()` takes both kinds too (user request: "the paginate supports both cursor based and skip + take type of pagination as well as the client side hooks"): `paginationOpts` gains `offset` (counted from the cursor, or the start, and added to a `skip()`) and `withTotal` (`total`, the whole range after filters, one `COUNT` without a filter), both optional in `paginationOptsValidator`, so every existing paginated query serves numbered pages unchanged and a client chooses per call. React has `useNumberedPage(ref, args, { page, pageSize })` beside `usePaginatedQuery`, on the same query; the caller keeps the page number (state or URL) so it works with loaders, and `pageArgs`/`windowArgs` (from the client, re-exported by React, Vue and Svelte) build the arguments for loaders, Vue's `useQuery` and Svelte's `query`. Vue and Svelte get no dedicated pagination hooks: they had none, and their live query with those arguments is the whole hook. Not on search queries, which are ranked and capped at 1024.
- **A transaction callback that throws synchronously fails its own call.** On `:memory:` (and for statements outside a transaction) SQLite calls go through the writer's queue; a callback that threw before returning its promise used to stop the queue and leave its caller waiting forever. The engine always passes async callbacks, so only a plain callback to `db.transaction` could hit it; the contract tests' `skip(-1)` cases did.

- **SQLite's memory follows the server's RAM** (user request: "set the ram for sqlite based on the size of ram of the current server"). The app database's connections (not the telemetry database's or the CLI's short-lived ones) set `mmap_size` to a quarter of the RAM (64 MiB to SQLite's 2 GiB cap), `cache_size` to an equal share of a sixteenth over the writer and the four readers (8 MiB to 1 GiB in all), and `temp_store = MEMORY`. The RAM is `min(totalmem(), process.constrainedMemory())`, so a container's memory limit counts rather than the host's, divided by `RUNTIME_WORKERS` because each runtime process holds its own connections. The mapping takes no memory beyond the OS's own file cache, which it reclaims under pressure, so the quarter is not memory taken from the app; the page caches are real allocations, hence the small share. Measured on a 116 MiB database already in the OS cache (medians of five runs): random reads by id 995 → 675 ms, range reads 364 → 298 ms, full `json_extract` scans unchanged (CPU-bound). No variable: the defaults are bounded, and the knob can come when someone needs it.

## Monorepos and microservices

User request: "Monorepo support in the CLI using Turborepo … shared forge types in a package … several forge backends in one monorepo … wire them together with NestJS transports … one service calling another"; inventory approved.

- **`--monorepo` (or `--microservices`, which implies it)** lays out Bun workspaces `apps/*` and `packages/*` with `turbo.json` (dev persistent and uncached; typecheck after its dependencies). Each app is made by the same `scaffold()` as a single project, so it stays a whole project with its own stack files and deploys on its own (one deployment per app, as always). The main app is `apps/web` (framework) or `apps/api` (backend).
- **Shared types are a package** (`packages/api`) with the main app's `api` and `dataModel`, and each other app in a file of its own (`@<name>/api/<app>`); services aren't in it (clients call the main app, and services are called over a transport). Each backend's `forge/_generated/dataModel.ts` declares the global `Register.schema`, so one TypeScript project can hold one backend's types: with two, `tsc` reports TS2717. The backends are workspace dev dependencies so turbo runs their typecheck (which runs codegen) first. Nothing is copied, so it can't go stale. (0.12.0 to 0.13.0 re-exported every backend from one index, which failed `typecheck` in any monorepo with a service.)
- **Services talk through Nest's transports, which the engine already runs** (`nest(http, { microservices })`, first runtime process only). Each service answers `<service>.hello` with a controller that runs a mutation in its own database; the main app gets a service class per service that makes the calls, with a controller (`POST /http/<service>/hello`) and an action (`inject(ctx, Service)`) over it (user decision: "by default we will call the clients in a service or in a class", and "the route can still be called in the reactive function (action) too"). TCP needs nothing; Redis and NATS add `ioredis`/`nats` to the backends and read the broker from `MICROSERVICES_REDIS_URL`/`MICROSERVICES_NATS_URL`. In dev the services run on this machine (`dev --no-docker --port 300n`), so TCP ports 400n are reachable; a Docker dev engine would publish only HTTP.
- Tested by generating a monorepo with two services and running the example: the main app's action reaches `orders` over TCP, which counts the calls in its database. `bun install` and `turbo run typecheck` on a generated monorepo were run by hand later (see below). Not tested: the Redis and NATS variants.

## Changing a project that exists (monorepo, add, remove, stack)

User request: "the cli should support a lot of things, like we can transform a clean fullstack app into a mono repo, we can add more microservice or add another fullstack app and other features that already exist in our entire system but can be controlled via cli", and then "why are the changes in the create-archlast-forge? I am asking for enhancements for packages/cli".

- **The commands are in the CLI, the generators stay in the scaffolder.** `packages/cli/src/evolve.ts` (convert, add, remove, sync), `stack-edit.ts` and `grow.ts` (what a person at a terminal sees) are the CLI's. They call the pieces `scaffoldMonorepo()` is now made of (`writeService`, `writeCaller`, `writeShared`, ... in `create-archlast-forge/src/monorepo.ts`, exported as `create-archlast-forge/monorepo`), because the templates are there and `init --monorepo` must write what `add service` writes: one code path, not two copies of the templates.
- **A monorepo has a record**, `archlast-forge.workspace.json`: the main app, the transport, and each service's and app's ports (dev port, and the transport's). Ports are recorded, not derived from order, so a service added after an app doesn't clash with it. A monorepo made before the file existed has it inferred from the folders (`infer` in `workspace.ts`): services are the backends with a router or a controller of their own, the transport is read from their `http.ts`.
- **`monorepo` moves a project into `apps/web` or `apps/api`** with `rename`, and keeps what the repository owns at the root (`.git`, `.github`, editor folders, the licence). `compose.yaml` pins `name:`, so the Docker project and its volumes don't change when the folder does. Prettier runs only over files the command wrote (`format(root, files)`), and over an existing file such as `http.ts` only if it was already Prettier-clean (`isFormatted`): a user's code is not reformatted. It asks first (`confirm()`), refuses without `--yes` when there is no terminal, and has `--dry-run`.
- **The main app's service classes are listed by a file the commands own**, `forge/_services.ts` (`serviceControllers`, `serviceProviders`), which `http.ts` mounts once with `nest()`. Adding or removing a service rewrites the list and never edits `http.ts` again. An `http.ts` that already calls `nest()` (one per process) is not edited: the command says which two lists to add.
- **Removing deletes folders, so it asks**, and removes only the files `add service` wrote in the main app. `mobile` and `desktop` are removable too; the main app is not.
- **`stack add|remove` never overwrites an edit.** `compose.yaml` is replaced only if it equals what the old services would have rendered (both formatted by Prettier, since the scaffold formatted the original); otherwise the new one is `compose.new.yaml`. `.env` only gains the keys the new services need, with new secrets; no value is changed.
- **Found by running it for real (`bun install` and `turbo run typecheck` on a converted project with a service and an app, from the published 0.13.0 packages), not by the tests**, three defects of the generated monorepo that have been there since 0.12.0, none of them from the new commands:
  - A backend main app (`apps/api`) and `packages/api` were both `@<name>/api`: `bun install` refused ("Workspace name already exists"). The main app's package is now `@<name>/backend` (`packageOf`), and `workspace sync` renames an old one.
  - `packages/api` had no Bun types, so the service classes' `process.env` failed to typecheck. It has `@types/bun` and `types: ["bun"]` now.
  - `packages/api` re-exported every backend's types. Each backend's generated `dataModel.ts` declares the global `Register.schema`, so two backends in one TypeScript project collide (TS2717), and `bun run typecheck` failed in any monorepo with a service. `packages/api` now has the main app's types, each other app in a file of its own (`@<name>/api/<app>`), and no services: clients call the main app, and the main app calls services over a transport, with `packages/contracts`.
  - The same collision made Forge RPC's inferred output types (`Awaited<ReturnType<Router["method"]>>`, with an `import type` of the router) fail the caller's typecheck. A procedure without an `output` schema is `unknown` now, and codegen warns (see Forge RPC).
- **The main app is any folder, and mobile is for any main app** (found by adopting the archlast-medico repo, a hand-made monorepo with `apps/medico` and the scope `@medico`). `Workspace.main` is a folder name and `Workspace.scope` replaces the root package's name as the scope of `packages/*`; a monorepo without the file takes the only app with an `archlast-forge.json` for the main app, and says how to write the file when it can't tell. Package names are read from each app's `package.json` (`appPackage`), not computed, since a hand-made monorepo names its apps its own way. Whether the main app is a backend or a full-stack app is read from its `archlast-forge.json` (`modeOf`), not guessed from the folder name. The rule that `--mobile` and `add mobile` needed a backend main app is gone: "Expo has no full-stack option" is about the phone app not being a full-stack app, and an Expo app is a client of the main app's engine, which serves the same `/rpc` and sign-in in both modes. The mobile and desktop templates name the main app with `__MAIN__` and its typed API with `__API__` (`<main>Api`).
- **`upgrade` moves a monorepo whole** (`upgradeWorkspaceFiles`): a service and the app that calls it, or the phone app and the engine, must be on one release, and `^0.14.0` doesn't include 0.15.0, so apps and packages left behind would skew. It was found when upgrading archlast-medico, where `upgrade` in `apps/medico` would have left `apps/mobile` and `packages/api` on the old release.
- Tested: `packages/cli/test/evolve.test.ts` (convert, including a converted project running with a service, add and remove again and again, ports, apps, mobile and desktop, inference, sync, unique package names, the stack), `grow.test.ts` (the commands as a user runs them), and `create-archlast-forge/test/monorepo.test.ts`. Run by hand: `monorepo` with `bun install`, codegen and `turbo run typecheck` on a real project, and the question answered in a terminal. Not tested: `bun run dev` of a converted monorepo with every app at once, mobile and desktop apps built (Rust and Expo aren't here), and Docker stacks of the apps (`up`).

## Mobile apps (Expo)

User request: "React Native (Expo) template, backend mode only … Better Auth session handling suitable for native apps (secure token storage, not cookies only) … reconnect … offline … no fullstack option"; inventory approved.

- **`--mobile` adds apps/mobile to a monorepo** (it implies one) and is refused with a full-stack app, by flag and in the prompts (the question is only asked for a backend). Expo SDK 58 (React Native 0.88, React 19.3.0); `@forge/react`'s React peer range is now `^19.0.0` so Expo's React doesn't warn.
- **The session is Better Auth's Expo plugin, kept in secure storage**: `expoClient` (Keychain/Keystore through expo-secure-store) in the app, `expo()` with the app's scheme in `trustedOrigins` in the backend's `forge/auth.ts`, both at 1.7.12 to match the engine's Better Auth. A plugin turns off the engine's direct session check (documented). The client gained two options for it: `headers` (every call, and the socket handshake in React Native's `(url, protocols, { headers })` form; asked each time, may be async) and `authPlugins` (passed to `createAuthClient`). Both are additions; browsers are unaffected.
- **Types without bundling the backend**: the app types `api` with a type-only import from `packages/api` over `anyApi`, so Metro never resolves the backend's generated code or its dependencies.
- **Background and offline**: `AppState` active → `client.reconnect()` (subscriptions are sent again and refetch). No offline store: the client has none, so the template keeps last data on screen and lets calls fail; documented as such.
- Tested: the client with a WebSocket that takes headers like React Native's, against a real engine: signed calls, a signed socket, live updates after a mutation; the scaffold's files and checks. Not tested: building or running the Expo app (no simulator here), the server plugin in a running engine (it needs Expo's packages).

## Desktop apps (Tauri)

User request: "Tauri desktop template. Full-stack mode runs the engine locally inside the desktop app, without Docker. A client-only mode connects to a remote forge backend"; inventory approved (with a spike first).

- **Spike: one compiled binary doesn't work as is.** `bun build --compile` of the CLI builds (112 MB) but stops at start: the engine reads files beside its source (its `package.json` for the version, the dashboard's page, the vendored explorer, fonts, worker scripts), which the binary's `$bunfs` doesn't have. Making every one of those embeddable would touch every way the engine runs.
- **So Bun itself is the sidecar**: `scripts/bundle-engine.ts` ships `apps/web` built for production with its production dependencies, `desktop-engine.ts`, and the Bun binary (`binaries/bun-<target triple>`, Tauri's sidecar naming); the Rust shell starts it on a free port, waits for it, opens the window on it and kills it on exit. That is exactly `start --no-docker`, which pack:smoke covers. The cost is size: Bun (~90 MB) plus dependencies.
- **The engine stays local**: `HOST=127.0.0.1`, production mode, `BETTER_AUTH_URL` on the loopback with `ALLOW_INSECURE_HTTP` (nothing else reaches it), data in Tauri's `app_data_dir`, and a secret made on first start and kept there (0600).
- **Client mode** is a React page bundled by `Bun.build` with the backend's address in `config.js` (`FORGE_URL` at build time), typed with a type-only import like the Expo app. The backend must trust Tauri's origins; signing in goes through the bearer plugin and `headers`.
- Tested: both scaffolds, placeholder icons (RGBA PNGs written by the scaffolder, `tauri icon` replaces them), and the starter run for real (loopback only, data and secret placed, not reachable from the LAN address). Not done: compiling the Rust or running Tauri (no Rust or webview libraries here).

## OpenAPI and the API docs page

User request: "Generate an OpenAPI 3.1 document from the /http routes and NestJS controllers … derived from the same validators the engine uses … Scalar … docs UI in React and MDX … disabled by default in production"; inventory approved.

- **Schemas come from validators the engine enforces, so they can't drift.** `/http` routes gain optional `query`, `body`, `returns` (and `summary`, `description`, `tags`); the runtime checks `query` and `body` before the handler (400 with the reason) and leaves the request unread for it. Nest methods get `@Contract({ params, query, body, returns })`: metadata plus an interceptor that checks the same way and throws `BadRequestException`. Public RPC functions are in the document too (args and `returns` already exist); internal ones never are. Nest routes are read from Nest's own metadata (`path`/`method` on the controllers in `ModulesContainer`) after the app starts; the mount's catch-all route is marked (`NEST_MOUNT`) and left out.
- **Made in the runtime, served by the server**: an `openapi` admin op builds it from the manifest, `forge/http.ts` and the Nest routes; the server caches it per manifest (a reload makes a new one), adds `servers` (`BETTER_AUTH_URL` if set, else the request's origin), minifies it, answers with an ETag and brotli or gzip. Repeated object schemas move to `components.schemas`, so only used ones exist.
- **`API_DOCS` is on in dev and off otherwise**; `API_DOCS_PATH` (default `/_api`) can't be under an engine path. The document advertises what is callable anyway, so the setting is about publishing, not access.
- **The docs page is the dashboard package's** (`@archlast/forge-dashboard/api-docs`, passed to `startServer({ apiDocs })` by the CLI): React and MDX in the docs site's tokens, bundled by `Bun.build` on first request (minified, split per page, hashed, cached a year), with the app's `forge/docs/*.mdx` compiled by `@mdx-js/mdx` (MIT, new dependency of the dashboard package) and React's JSX runtime taken from the page, so a backend without React works. Fonts are declared in the page's head and served as the two Latin `woff2` files, because Bun inlines every `url()` of a stylesheet (all subsets: 150 KB gzipped). First load: about 72 KB gzipped.
- **The explorer is Scalar, vendored**: `@scalar/api-reference` (MIT) is 56 MB installed; its standalone bundle is 4.9 MB, kept brotli-compressed (1.06 MB) in `packages/dashboard/vendor/scalar` with the license and version by `scripts/update-scalar.ts`, sent as is to clients that take brotli and decompressed once for the rest. On its own page, so the docs page and apps never load it. Its hosted features (toolbar with share and SDKs, Ask AI, telemetry, web fonts) are off, so nothing about the API leaves the server.
- No size budget was given; measured instead: the document 115 KB pretty and inline → 57 KB minified with shared schemas → 3.2 KB gzip (test fixture); the docs page 72 KB gzipped (a test fails above 90 KB); the explorer 1.06 MB brotli, loaded only at /explorer.

## Reactivity and caching

- **Topic granularity**: the table (for full scans and writes), `table:index:[values]` for each index-key prefix, and `table:by_id:[id]` for `db.get`. A write publishes the old and new values of every index prefix.
- **Publish after commit only.** A failed mutation publishes nothing.
- **Redis bus**: one pub/sub channel carries all topics, and each server filters locally (`shortcut:` comment in `bus.ts`).
- **Redis keys are per service.** Everything in Redis (query cache, topic channels, rate limits) sits under `config.redisPrefix`. Before it, every app used the fixed prefix `archlast-forge:`, so two backends on one Redis (a monorepo's services) served each other's cached results for equal function names and arguments and woke each other's subscriptions on equal table names. The prefix is `REDIS_PREFIX`, else `archlast-forge:<OTEL_SERVICE_NAME>:`, else (no name) the old `archlast-forge:`. The identity is the service's name because that is what is the same on every server of a service however many run, and different between services (`init`, `add app`, `add service` and `workspace sync` give every app of a monorepo a name of its own). A first version hashed `BETTER_AUTH_SECRET` instead and was dropped: rotating the secret moved every key, and an upgrade moved the keys of every app, including plain ones with nothing to isolate. Keeping `archlast-forge:` for an unnamed app means upgrading it changes nothing. What stays: two apps given the same name (or both unnamed) still share keys, so each start writes a hash of its `BETTER_AUTH_SECRET` under `<prefix>owner` and logs a warning when it finds another app's (a warning, not a refusal: a rotated secret looks the same and settles after one restart); and naming a replicated app that had no name moves its keys, so servers on different versions miss each other's writes until the last is upgraded, which `REDIS_PREFIX=archlast-forge:` on every server avoids.
- **Query cache**: on by default (`CACHE_TTL_MS`, 60 s; 0 turns it off), in dev too. It's keyed by (function, args). A query seen reading `ctx.auth` is cached per caller: its key includes the identity, resolved fresh on each call, so a revoked session stops matching. It's skipped when any invalidation arrives during the run (`shortcut:` comment in `subscriptions.ts`). Each server evicts on bus events, and reads wait for pending evictions.

## Functions

- **Actions are at-most-once with no retries** (user decision). Scheduled mutations are exactly-once: the job row is claimed inside the mutation's own transaction. A scheduled action is claimed as `running` first. If the process crashes mid-action, the job stays `running` (`shortcut:` comment in `scheduler.ts`).
- **Crons** live in `forge/crons.ts` and are evaluated in UTC. Every server computes the same job ID for each run (`cron:<name>:<time>`), so each run is inserted once.
- **Function runtime** is a child process, not a Bun Worker, because Bun documents Worker termination as experimental. It owns the `forge/` modules, the database, Better Auth and the scheduler. The server process owns HTTP/WS, the bus, the cache and subscriptions.
- **Code or dependency changes restart only the function runtime** (user decision). HTTP and WebSocket stay up. The RPC handler is rebuilt after each load and sockets use whichever is current, so they see the new functions, and every subscription re-runs.
- **No RPC framework on the reactive path** (user decision; tRPC was removed from it; [Forge RPC](#forge-rpc), the transport between forge apps, speaks its wire format through an implementation of its own). Each public function is `POST /rpc/<name>` (`/rpc/todos:add`, JSON arguments in the body, `{ result }` or `{ error: { message, code, data?, requestId } }` back with the matching HTTP status); queries also answer `GET /rpc/<name>?args=<json>`. POST requires `content-type: application/json`, which a cross-site form can't send without a preflight. Live queries use one WebSocket at `/rpc` with `{ type: "subscribe", id, name, args }` and `{ type: "unsubscribe", id }`; the server answers `{ type: "data", id, data }` (the first message is the current result) or `{ type: "error", id, error }`. The client reconnects with jittered exponential backoff and subscribes again, so a reconnect refetches. Arguments are validated in the function runtime. The dashboard API is plain JSON too: `GET /_admin/<op>?input=<json>` and `POST /_admin/<op>`. Not carried over from tRPC: request batching (each call is its own HTTP request).

## HTTP endpoints

- **`forge/http.ts`** default-exports `httpRouter()`, as `crons.ts` does with `cronJobs()`. `http.route({ method, path | pathPrefix, handler: httpAction(...) })` mirrors Convex.
- **Served under `/http`**, on the same origin as everything else (`path: "/hello"` answers at `/http/hello`, and the handler sees `/hello`). Convex uses a separate domain; a single server has no such thing, and a fixed prefix can't shadow `/rpc`, `/api/auth`, `/_admin` or `/_dashboard`.
- **A handler is an action** with a `Request` and a `Response`: the action context, the action timeout, and no database handle of its own (it calls mutations). It runs in the function runtime like auth requests do, so `forge/` code reloads and the single-process inline mode work unchanged.
- **Bodies are bytes both ways.** The IPC channel uses structured clone, so `ArrayBuffer`s cross as they are. Bodies are buffered, not streamed.
- **No CORS, no request id from the handler.** Routes answer their own `OPTIONS`. The server adds only `x-request-id`.
- **Errors** use the same rules as function calls (`toPublicError`): `ForgeError` and validation errors reach the caller, anything else is a 500 "Server error (request id)".
- Streaming: a response with `text/event-stream` (or a Nest stream) is passed through as it is written. Not done: `HEAD` routes, a route list in the dashboard, and support in `createTestBackend`. (HTTP calls are traced now, named by route pattern: see [Observability](#observability).)

## Auth

- **Better Auth by default** (user decision), through an adapter over the document store. `users`, `sessions`, `accounts` and `verifications` are added to every schema and visible in the dashboard. Writes to them publish topics like any other write. They aren't validated against the schema, so Better Auth plugins can add fields.
- `forge/auth.ts` (optional) default-exports `defineAuth(options)`. Without it, email and password sign-in is on.
- **Identity** is resolved once per request from the `cookie`/`authorization` headers, before the function's transaction starts.
- WebSockets carry cookies only on the handshake, so the client reconnects when the session changes.
- In dev, `BETTER_AUTH_SECRET` and `ADMIN_KEY` are generated once and kept in `DATA_DIR/.dev-secrets.json`. Outside dev, `BETTER_AUTH_SECRET` is required.

## Server-side dependencies

- `forge/` has its own `package.json`. In this monorepo it is a workspace member (`apps/*/forge`).
- `codegen` and `dev` run `bun install` when that manifest or the nearest `bun.lock` changes. They pass `--ignore-scripts` unless the manifest lists `trustedDependencies`, in which case Bun runs scripts for those packages only.
- A missing package fails at load with the `bun add` command to fix it.
- Codegen fails if `src/` imports anything from `forge/` other than `forge/_generated`.

## Config

- Startup fails fast on: a non-postgres `DATABASE_URL`, `REPLICAS > 1` without `REDIS_URL` or Postgres, an unreachable Redis, only one of `S3_ENDPOINT`/`S3_BUCKET` set, and a missing `BETTER_AUTH_SECRET` outside dev.

## Validation

- **Zod runs validation; `v` stays the public API.** Validators remain plain data, so they can still cross into the dashboard and the function runtime. Each one compiles once to a Zod schema, cached per validator object. Args, documents and return values are all checked by Zod. Error messages keep the `args.title must be a string` form.
- **`returns` validators** (`query({ returns: v.string(), ... })`): when given, the validator is the function's return type, and the handler is type-checked against it. At runtime a mismatch fails the call. A mutation checks its return value inside its own transaction, so a mismatch rolls the mutation back. A handler that returns nothing counts as `null`, so it pairs with `v.null()`. A mismatch is reported as an internal error, not a bad request, because it's a server bug.
- Added `v.null()` and `v.union(...)` so that common return types such as `Doc | null` can be expressed.
- Known gap: TypeScript allows extra properties on a returned object, but the runtime object check is strict, so the extra fields fail at runtime.
- Like Convex, a handler that calls `api.<same module>.*` needs an explicit return type annotation to break the inference cycle.

## Scope

- **Self-hosted framework, not a multi-tenant platform** (user decision). One deployment per app. Hosting many customers' projects (tenant isolation, metering, a control plane) is out of scope for now.
- **Planned: the engine runs as a Docker container, started and controlled by the CLI** (user direction). The design and its open questions are in [roadmap.md](roadmap.md#target-architecture-the-engine-as-a-docker-container-controlled-by-the-cli). Until it's built, the CLI runs the engine in its own process.

## Production readiness (self-hosted)

Decided without asking, as directed, while implementing [roadmap.md](roadmap.md).

- **Internal functions.** `internalQuery`/`internalMutation`/`internalAction` are left out of the client router and `api`, and codegen puts them in `internal`. Calling one returns "Unknown function", so their names don't leak. The dashboard, the scheduler, crons, migrations and `ctx.run*` may call them.
- **Timeouts.**
  - *Soft timeout, in the function runtime:* queries and mutations get `FUNCTION_TIMEOUT_MS` (10 s), actions `ACTION_TIMEOUT_MS` (10 min). Transaction handles refuse use after the call ends, so a timed-out handler can't write afterwards.
  - *Hard deadline, in the server:* the timeout plus 5 s. A process that misses it is presumed stuck in synchronous code, so it's killed and respawned. Requests go only to processes that have reported ready.
- **Runtime pool.** `RUNTIME_WORKERS` processes per server, round-robin. Only the first runs the scheduler, migrations and the schema check.
- **Request limits.** Fixed-window rate limiting per client IP (memory, or Redis when configured) on HTTP calls, auth and WebSocket messages. There are also caps on body and message size and on subscriptions per connection. Bun's WebSocket backpressure limit (4 MiB) drops slow clients, which then reconnect and refetch. Better Auth's limiter uses the same Redis counter through `customStorage.consume`.
- **Errors.** `ForgeError` (message and data) and argument validation errors reach callers. Everything else is "Server error (request id)" outside dev, logged with that request id. Return-value mismatches count as internal.
- **Admin.** Accounts live in `_admins` (Argon2 hashes from `Bun.password`), with 12-hour sessions in `_admin_sessions` (stored as token hashes) and roles owner, admin and viewer. Access uses an HttpOnly SameSite=Strict cookie plus an `x-forge-admin` header on writes (CSRF). `ADMIN_KEY` acts as an owner. Every write is recorded in `_audit`. The dashboard is off outside dev unless `DASHBOARD=on`.
- **TLS.** Outside dev, startup fails unless `BETTER_AUTH_URL` is https (`ALLOW_INSECURE_HTTP=1` overrides).
- **Queries.**
  - *Ranges:* bounds on the next index field after the equality prefix.
  - *Order and pagination:* `order()`, plus keyset `paginate()` with base64url cursors over (remaining index fields, `_creationTime`, `_id`). Documents with a missing optional field in the index can be skipped by range and paging comparisons.
  - *Reactivity:* ranges and pages are tracked at the equality prefix.
  - *Built-in index:* `by_creation_time` is available on every table.
- **Search.** `searchIndex(name, { searchField, filterFields })`. SQLite uses an FTS5 table kept in sync by the document store and tracked in `_search_indexes`. Postgres uses a GIN index over `to_tsvector('simple', …)`. Every term must match, the last as a prefix, and search reads depend on the whole table.
- **Migrations.**
  - *Postgres indexes:* built `CONCURRENTLY` outside transactions, under a session advisory lock; invalid leftovers are rebuilt.
  - *Data migrations:* `migration({ table, migrateOne })` registers an internal mutation that processes one page per transaction. Progress lives in `_migrations`, and runs resume.
  - *Schema check:* outside dev, startup refuses when stored documents don't match the schema (`SCHEMA_CHECK=off` skips it).
- **Overload.** The function runtime is single-threaded, so past its capacity calls queue. A call is only presumed stuck, and its process killed, when the process has answered nothing since the call went in (a synchronous loop); one that is merely behind keeps its other calls. More than `MAX_PENDING_CALLS` (1000) waiting calls per runtime process are refused at once with 503 and `Retry-After: 1`. Before this, a queue over the 15 s hard timeout killed the runtime and failed every call in flight, again and again.
- **Hot path.** A cached query result keeps its serialized JSON with the entry (`Result.json`), so a hit does no JSON work, and cache invalidation in this process is synchronous. IPC messages sent in one turn of the event loop travel as one `batch` in both directions (a write's publish, log and result are three). Signed-in calls resolve the caller from the signed session cookie and a direct read of the session when nothing could change what a session means (no plugins, no secondary storage, no secret rotation); the signature check is remembered per cookie value, the session is read on every call so a revoked one stops working at once; anything else goes through Better Auth. Rate limiting off means the client address is never looked up.
- **Throughput on one core.** Production runs functions in the server process (`RUNTIME_MODE=inline`); dev keeps the child process for hot reload. SQLite writes use group commit: write transactions that queue up while one runs share one SQLite transaction, each in its own savepoint (it sees the ones before it, fails alone, and resolves only after the shared COMMIT). WAL checkpoints run on a background thread with its own connection once the WAL passes 32 MiB, never on the thread that serves requests. Inside the runtime, an exact read cache (`read-cache.ts`) keeps document reads by statement, tagged with the same topics the query cache uses; it is only on when this process is the database's only writer, never serves a table with uncommitted writes, and a read-only query that used cached rows re-runs rather than read a newer snapshot after a commit. Like counts in `include` are one covering `COUNT(*)` per parent, cached per parent. Call logs are written once a second in 250-row statements with time-ordered ids.
- **CLI data commands** (`migrate`, `export`, `import`, `backup`, `env`, `admin`) run inside the running server when one answers: `POST /_cli` with `{ cmd, args }` and the admin key, executed in the function runtime, so an import reaches subscribers and nothing contends with the server for the write lock. With no server running they open the database themselves. Values and passwords are never written to the audit log.
- **Data portability.** Export and import use JSON Lines, preserving ids and validating on import. Import refuses non-empty tables unless `--replace`. Backups use SQLite `VACUUM INTO`; for Postgres, use `pg_dump`.
- **Environment variables.** Stored in `_env` and loaded into the function runtime before user code; the process environment wins. `env set` reloads a running engine (SIGHUP for a container, the admin reload endpoint otherwise).
- **Shortcuts closed.**
  - *Lease sweep:* actions stuck in `running` fail after the action timeout plus 60 s.
  - *Redis bus:* now one channel per topic, plus an all-topics channel published only when the query cache is on.
  - *Cache invalidation:* tracked per topic, with a bounded history.
- **Observability.** JSON server logs in production; Prometheus `/metrics` behind `METRICS_TOKEN` or `ADMIN_KEY`; `x-request-id` accepted, generated and echoed. Everything else (function logs, traces, runtime samples, the dashboard's charts) is the telemetry store: see [Observability](#observability) below. It replaced the `_logs`, `_metrics` and `_cache_stats` tables and the span-per-call exporter.
- **Health and shutdown.** `/health` reports liveness and `/ready` readiness. SIGTERM marks the server not ready, closes WebSockets with 1012, drains HTTP for up to 10 s, then stops the runtime.

## Docker engine (the open questions from the roadmap)

1. **Code delivery.** In dev, `forge/` is mounted read-only at `/src/forge` and the engine syncs it into its own filesystem (`/app/forge`), so the host's `node_modules` never shadows the container's. In production, `archlast-forge build` creates an app image `FROM` the engine with the code and dependencies baked in (`engine prepare`).
2. **Server dependencies.** Installed inside the container, from `forge/package.json` minus `@archlast/forge-*` and `workspace:` entries; `@archlast/forge-runtime` is linked to the engine's copy. `node_modules` sits on a named volume. The host also installs, but only for editor types.
3. **Docker access.** The CLI shells out to `docker`; `DOCKER=podman` switches binaries.
4. **Services.** The engine only, by default. `--with postgres,redis,s3` starts sibling containers on a per-project network and wires their URLs in.
5. **Versioning.** The engine image is `ghcr.io/algochad/archlast-forge-engine:<cli version>` (`ARCHLAST_ENGINE_IMAGE` overrides). Inside this repo the CLI builds it if it's missing; a published CLI pulls it.
6. **Without Docker.** `--no-docker` (or `ARCHLAST_NO_DOCKER=1`) keeps the in-process mode, and the CLI falls back to it with a notice when Docker is unavailable. Tests use it.
7. **Networking.** The container's port 3000 is published on `--port`, and `host.docker.internal` reaches host services. Dev and production containers have different names, so one never replaces the other.
8. **CLI surface.** `dev`, `build`, `start`, `stop`, `logs`, `status`, `engine build`. Data and config commands run inside a running engine through `docker exec`.

## Modes: full-stack apps and backends

Decided together, as directed ("a framework mode on React with a lightweight bundle, like Next.js or React Router; a backend mode hosted as a container with the services it needs; the CLI supports both; init lets you choose").

- **A project has a mode** (`archlast-forge.json`: `mode` and `services`), chosen by `init` / `bun create archlast-forge`. A project without the file is a backend with no services, so nothing from before changes.
- **`init` defaults to the production stack.** A full-stack app starts with PostgreSQL, Redis, S3 storage and Caddy ticked, a backend with the first three, under the question "Which services will production need?". Only what stays ticked goes into `compose.yaml`, so unticking all of it gives SQLite and the app alone. The same list is what `dev` starts in Docker; `dev --no-docker` develops on SQLite.
- **Full-stack apps start with shadcn/ui** (user request: "add default shadcn", asking for the base color). `init` asks "Add shadcn/ui?" (default yes; `--shadcn`/`--no-shadcn`) and "Which base color?" (`--base-color`, default neutral; the seven shadcn offers today). The API (`scaffold({ shadcn })`) is opt-in, so only the command line defaults to it. It is the `base-nova` style, shadcn's own default today, which uses Base UI and the `cn` package; the library and style are not asked about, and the style cannot be changed after init (shadcn's rule for `components.json`). The files come from the shadcn registry through `scripts/update-shadcn.ts`, not from running the shadcn CLI while scaffolding, so a scaffold needs no network and every project of a version starts the same; the base-color CSS is the same text `shadcn init` writes (checked byte for byte for neutral). The starter's pages are rewritten with the components and keep the plain starter's test hooks (`.who`, `.msg`, `#email`). The plain starter stays (`--no-shadcn`) because the tutorial and the recipes are written against its stylesheet.
- **New projects come formatted with Prettier, four spaces to an indent** (user request: "the scaffolding includes prettier formatter, also 4 spaces tab is the standard"). `init` writes `.prettierrc` (`{ "tabWidth": 4 }`, the rest Prettier's defaults), a `.prettierignore` for `forge/_generated` (codegen rewrites it), a `format` script and `prettier` in `devDependencies`, then runs `prettier --write .` in the new folder, the same command as the project's `bun run format`. Formatting the result, not the templates, means the generated files (`compose.yaml`, `archlast-forge.json`, the shadcn theme) and the components refreshed from the shadcn registry come out formatted too, and the templates never drift. It runs Prettier as a child process so `scaffold()` stays synchronous; that costs about 1.3 s per scaffold, and `create-archlast-forge` depends on `prettier`.
- **`archlast-forge upgrade` moves a project to a release** (user request: "an upgrade command that will upgrade the entire project, backend only or the fullstack framework"). The version comes from `bun info @archlast/forge-runtime@<spec>` (default `latest`), so it follows the registry the project installs from and an unknown version is refused before anything is written. The archlast-forge dependencies in both `package.json` files and the engine image tag in the `Dockerfile` and `compose.yaml` are replaced as text, so a file keeps its formatting and edits; `workspace:`, `file:` and tag specs, and a non-version image tag, are left alone. Then `bun install` (root, then `forge/`) and `codegen` with the newly installed CLI. It also adds the Prettier setup new projects get (user request: "even the upgrade should trigger the scaffold of prettier so that old projects ... get it"), through the same `addPrettier` as `scaffold`, piece by piece where missing: `.prettierrc` only when the project has no Prettier config at all, so a config of its own wins, and `format`/`prettier` only when absent. It doesn't reformat the code: a whole-project reformat is a diff to review on its own (and conflicts with open branches), so the CLI says to run `bun run format`. It doesn't touch the rest of `compose.yaml` (the file is the user's), React or other dependencies, or the data. Projects whose CLI predates it run it once with `bunx --package @archlast/forge-cli@latest archlast-forge upgrade`.
- **Tailwind goes through Tailwind's own Bun plugin, loaded from the project.** The framework's browser build adds `bun-plugin-tailwind` when `bun-plugin-tailwind` resolves from the project root, and does nothing otherwise, so the framework package gains no dependency and projects without Tailwind build as before. The plugin carries Tailwind's compiler and its native scanner for every platform (27 MB), which is why it is not a dependency of the framework. Dark mode is the `.dark` class (shadcn's convention) with a script in `root.tsx` that follows the system until the toggle is used.
- **Full-stack apps run inside the engine process.** `startServer({ app })` takes a host that is called for every request the engine has no route for (`/rpc`, `/api/auth`, `/http`, `/_admin`, `/_dashboard`, `/_cli`, `/health`, `/ready`, `/metrics` stay the engine's). The host can call public functions in-process as the visitor (queries through the query cache, as a private copy), ask who the visitor is, check the rate limit, and opt a response out of the idle timeout. The runtime package knows nothing about React.
- **The router is React Router's data router (8.5, pinned), not our own.** File routes, the build, server rendering, the live cache and the viewer are ours; matching, nested layouts, loaders, redirects, error boundaries, scroll and history are React Router's, which has the edge cases covered. `@archlast/forge-framework` re-exports a curated part of it.
- **File routes** (`app/routes`): `index.tsx`, `[param]`, `[...splat]`, `_layout.tsx`, `(group)/`, and `_`-prefixed names are private. Two files for one URL, or a parameter mixed with text, fail the build with the file names. `app/root.tsx` exports `Layout` (the `<html>` document, also around error pages), a default component and optionally `ErrorBoundary`. There is no `<title>` convention: React 19 hoists `<title>` and `<meta>` into `<head>`.
- **Loaders are isomorphic.** `loader({ request, params, ctx })` runs on the server for the first request and in the browser afterwards. `ctx.query` fetches and puts the result in the TanStack cache under the key `useQuery` uses, so the page renders with data on the server, the cache is embedded (`dehydrate`) and restored in the browser (`hydrate`), and the live subscription replaces it with the same value. `ctx.viewer()` is memoized per request on the server and asks Better Auth (`disableCookieCache`) in the browser, because the session store lags a sign-in by a moment and a loader that redirects anonymous visitors would otherwise bounce a user who just signed in.
- **The viewer is part of the page.** `window.__FORGE__` carries `{ dev, now, timeZone, viewer, queries, hydration }`. `useViewer()` renders on the server, and follows sign-in and sign-out through `ArchlastForgeClient.onSessionChange`, which fires only once something uses `auth`, so a page that never signs in makes no session request. `useSession()` got a server snapshot (pending), because `useSyncExternalStore` throws without one.
- **Errors are sanitized before they are rendered.** The server renders with the same errors it embeds for the browser: `ForgeError` messages and call failures (which already carry public messages) pass; any other error becomes `Server error (request <id>)` outside dev, and is logged in full. Rendering the original error leaked a loader bug's message into the HTML.
- **Times hydrate cleanly, with two hooks and no new rule for loaders** (user request, after a real-browser check with the server in UTC and the browser in another zone: a time formatted without a zone, `Date.now()` in a render, and a query argument worked out from the clock each made React throw the server's HTML away, `Minified React error #418` in production). `useTimeZone()` and `useNow(interval)` return what the server rendered with while the browser hydrates (its instant, `now`, and the zone it used, `timeZone`, both in `window.__FORGE__`) and the browser's own right after, through `useSyncExternalStore`'s server snapshot, so the switch is an ordinary update and not a mismatch. The server learns the zone from the `forge-tz` cookie, which the browser sets only once a component has used `useTimeZone` (the zone name and nothing else, validated with `Intl.DateTimeFormat` before use; `Max-Age` one year, `SameSite=Lax`). The cookie was chosen over a client hint header or a query parameter because it needs no round trip, and the HTML was already `vary: cookie`, `private, no-cache`, so nothing about caching changed. The first visit has no cookie and renders in UTC, then moves to the visitor's zone after hydration: the alternative, a blocking script that sets the zone before React runs, would make that first render depend on something the server cannot see. Arguments that come from the clock are worked out once in the loader and read with `useLoaderData` (already how the page gets one value on both sides), so there is no hook for them. `hydrateRoot` gets `onRecoverableError`, which does what React does without one (`reportError`) and adds a console warning for mismatches that points at the docs, and in dev a notice on the page; the minified production message was the only clue before. Nothing private is added to the page: the zone is the visitor's own, echoed back to them. Existing apps that do nothing keep working: the hooks are opt-in and the extra fields are ignored.
- **Server rendering** uses `renderToReadableStream` and waits for `allReady`, so the status code and headers are right and there are no half pages. No streaming, no static generation, no route actions (a server-handled POST on a page URL would need CSRF protection; mutations are called from the browser).
- **Build** (`Bun.build`, twice): the browser bundle (split per route, hashed, minified, with gzip and brotli copies stored next to it) and the server bundle (one file, packages external, CSS ignored). The metafile maps each route to its chunk and shared imports, which become `modulepreload` links; all CSS is linked in `<head>`, because Bun merges the CSS of lazily loaded routes into the entry's stylesheet. Output goes to `.forge/build/<version>`; dev keeps the previous version for pages already open. `metafile` paths are relative to the working directory, not to `root`.
- **Development** is one process on the host: the engine and the app, rebuilding in about 0.2 s, reloading browsers over server-sent events, with build errors shown over the page. Docker runs only the services (PostgreSQL, Redis, RustFS), on 127.0.0.1 with free ports, and `dev` stops the ones it started when it ends; data stays in named volumes.
- **Production in a container**: `engine prepare` copies `app/`, installs the app's own dependencies, **links** React and the `@archlast/forge-*` packages from the engine image (two copies of React break hooks), generates the types and builds. `engine serve` then serves the build. A stale host lockfile that names local tarballs no longer breaks the server-dependency install: it is retried without the lockfile.
- **Backends are a stack.** `init` writes `compose.yaml` (the app and the chosen services, wired with health checks and `depends_on`), a `Dockerfile` (`FROM ${ENGINE_IMAGE}`, `COPY . /src`, `engine prepare`), `.dockerignore`, `.env` (secrets generated once, mode 0600, never overwritten) and `.env.example`; with Caddy, a `Caddyfile`. The compose file is the user's afterwards. PostgreSQL and Redis are not published; RustFS publishes one port, because browsers use presigned URLs; with Caddy only 80 and 443 are. The dashboard is on in the stack. `up` builds with a spinner, waits for the engine image's health check, and prints the addresses; on failure it shows the end of the build output or the app's last log lines.
- **Services in `dev` follow where the engine runs.** For an engine on the host they publish ports on localhost; for an engine in Docker they share a network and use container names. `dev` waits for PostgreSQL and Redis to accept connections before starting the engine.
- **Packaging**: `@archlast/forge-framework` is a library (`dist/` with code splitting, so one copy of the router context); the CLI loads it from the project at runtime, so a backend never installs React. `create-archlast-forge` ships source with `@clack/prompts`; the CLI depends on it for `init`.
- **Not done**: streaming and static generation, route actions, per-route CSS on demand, hot module replacement (a save reloads the page), a route list in the dashboard, `createTestBackend` support for pages, and Caddy is tested end to end only for `localhost` (its own certificate authority); issuing real certificates needs a public domain and is not tested.

## Packaging

- Libraries (runtime, client, react, vue, svelte) publish `dist/`: bundled ESM (each entry separately, because the runtime spawns `child.js` next to its own module) plus `.d.ts` from `tsc --emitDeclarationOnly`. Bun-run packages (cli, dashboard, create-archlast-forge) publish source.
- Releases are lockstep (`scripts/version.ts`). `scripts/pack.ts` stages the packages, pins `workspace:` dependencies and packs tarballs; `--smoke` proves them in a fresh project. A tag runs the release workflow, which publishes to npm (needs `NPM_TOKEN`) and pushes the engine image to GHCR; the runbook is `docs/releasing.md`.
- **npm names**: `@archlast/forge-runtime`, `-client`, `-react`, `-vue`, `-svelte`, `-framework`, `-dashboard`, `-cli`, and the unscoped `create-archlast-forge`. They live in the existing `archlast` org, which already publishes `@archlast/cli`, `@archlast/client` and `@archlast/sdk-*` (another product), so every name here carries the `forge-` prefix to stay clear of them. The command is still `archlast-forge`, and the engine image is `ghcr.io/algochad/archlast-forge-engine`.
- MIT licensed, and the repository is meant to be public. Packages carry the license, repository and engine (`bun >=1.4.4`) fields; `pack.ts` adds the license and a short README to each tarball. The release workflow builds the engine image before it publishes, and publishes prereleases (`v0.2.0-rc.1`) under the `next` tag. `react` is a `^19.3.1` peer, not an exact pin.
- **Minify where it is safe** (user decision, from Bun's minifier docs). A full-stack app's production browser bundle is fully minified, as before. Its server bundle is minified for whitespace and syntax but not identifiers, so names stay, and gets a linked source map, so stack traces point at the source. Production bundles drop `debugger` statements, and so does the docs site. The published libraries are not minified, as Bun's docs advise for code other people read. The engine is not compiled to one executable (`bun build --compile`): the user chose not to, and the engine spawns child processes and runs `bun install` in the image, which a single binary would have to rework.

## Docs site

- **A React single-page app with MDX pages** (user decision). `apps/docs` bundles with `Bun.build` and routes with React Router, the version the framework uses. Pages are MDX so a page can use React components; `components` in `src/Doc.tsx` is where they are added. The old output was one static HTML file per page.
- **Code is highlighted at build time**, by a remark plugin, and ships as HTML in each page's chunk. Shiki is not in the browser. The landing page's samples do the same through a Bun macro.
- **Every page is also static HTML, Markdown and an llms.txt entry** (user request: agents could not read the site). `static.tsx` runs after the bundle and writes `dist/<page>/index.html` (the built `index.html` with that page's title, description, canonical and Markdown alternate, and the page's text, sidebar and pager rendered with `react-dom/server` in place of the empty root), `dist/<page>.md` (the `.mdx` source, which is plain Markdown, with `page.html#id` links pointing at `.md` files), `llms.txt`, `llms-full.txt` (https://llmstxt.org), `robots.txt` and `404.html`. It is not hydrated: `createRoot` replaces the HTML once the app loads, and `preload` brings the page's chunk in first so no blank frame shows between the two. The cost is that the static HTML has the sidebar and article but no top bar or outline, so there is a small jump for readers with a browser. Each page has a Copy page button (it copies the `.md`) and a View as Markdown link. `SITE_URL=https://docs.example.com` at build time adds canonical links and `sitemap.xml` (it is a build argument in `compose.yaml`); without it links in `llms.txt` and the Markdown are root-relative and there is no sitemap. `Accept: text/markdown` is not negotiated: agents use `.md` or `llms.txt`.
- **Routes are root-relative** (`/auth`, `/auth#heading`), so the site must be served from the root of a host. A page is a folder with an `index.html`, and Caddy answers anything missing with `404.html` and a real 404 status (no more `index.html` for unknown paths, which crawlers read as a page). A sub-path needs a router `basename` and a `publicPath` in `build.ts`.
- **Landing-page motion is after ReactBits** (no dependency: it is CSS plus small hooks, because ReactBits' components use `motion` and `gsap`, and its license is MIT with the Commons Clause, so no code was copied). Everything is switched off by `prefers-reduced-motion`.

## Database adapters: Postgres and MongoDB

User request: "optimize the postgresql adapter (since the bun sqlite version is fast now)", "add a mongodb support next, ensure that all are well optimized", then "group commit only happens on sqlite, postgresql and mongodb should be fast at parallel queries and parallel writes". Measured with `benchmarks/db-adapters/bench.ts` (one workload through `Executor` and `DocStore` on any adapter) and small scripts, on a 4-core machine where the database server (Docker) shares the cores with Bun. Postgres 17 and MongoDB 7 (a replica set of one), Bun 1.4.4.

- **A read of one statement runs without a transaction.** `BEGIN`, the statement and `COMMIT` are three round trips through Bun's driver (488 µs for a lone `SELECT`); the statement alone is 148 µs. A read can't say in advance how many statements it will make, so `Executor.read` passes `rerunnable: true` and the adapter starts it with no transaction; if it makes a second statement it is thrown away and run again inside one (a read is deterministic and writes nothing; the executor already re-runs reads for `SnapshotMoved`). A function that catches the error of its second statement is run again too (`tripped` is checked after it returns). When most reads need the transaction, trying first is skipped until a probe finds otherwise. `db.transaction()` without the option runs its function exactly once, as before: two contract tests that write inside a read function showed why this is opt-in. A Postgres `get(id)` went from 0.44 ms to 0.18 ms, and 64 concurrent gets from 8,800 to 29,700 a second (40,000 with the changes below). MongoDB's version is the same with a snapshot transaction (2.3 ms, against 0.45 ms for a `find`).
- **Group commit stays SQLite's.** SQLite has one writer, so running queued writes back to back in one transaction saves its commits. Postgres and MongoDB have many connections, and a group runs its jobs one after another on one: 20,000 patches (a select and an update) with 32 callers ran at 6,133 a second as a transaction each on 32 connections, 4,180 on 8, and 2,830–3,905 grouped with savepoints on 4–8 connections. The jobs of a group each pay a round trip per statement, which parallel connections overlap. MongoDB has no savepoints, so one failed job would abort the group. What Postgres and MongoDB get instead is below.
- **Writes get a pool of their own on Postgres** (`DATABASE_WRITE_POOL_SIZE`, twice `DATABASE_POOL_SIZE`). On 4 cores, concurrent patches went from 3,100 a second on 8 connections to 4,300 on 16 and inserts from 4,250 to 5,700, with the reads' pool of 8 still answering 41,000 gets a second; one pool of 32 for both cost the reads a quarter of their throughput (33,000 a second). Connections open as load needs them, so the maximum costs nothing idle; the server warns at startup if `RUNTIME_WORKERS × (both pools) + 3` is over Postgres's `max_connections`. The commit's flush is part of what a write waits for (`synchronous_commit = off` raised patches and inserts by 30–38% in the same test), but it is a durability setting of the server, so it is not ours to change; it is listed under tuning in the docs.
- **Point reads that arrive while every connection is busy go out as one** (`db/coalesce.ts`): a `get(id)` outside a transaction waits only if the pool is full, and the waiting ones for a table become one `_id IN (…)` when a connection frees. MongoDB's driver costs about 150 µs of JavaScript an operation (24% of it in the socket write, 12% in BSON), so 64 concurrent gets went from 4,500 to 12,400 a second; on Postgres the engine's own per-read work dominates and it made no difference (45,000 either way).
- **Many rows are one statement.** `Dialect.bulkInsert` and `bulkUpdate` (Postgres: one JSON parameter and `jsonb_array_elements`, so the statement text never changes and is prepared once): 100 updates were 15.6 ms as 100 statements in a transaction and 2.0 ms as one; `updateMany` of a document twice in a call writes the last version once. `childrenOf` and `countChildren` (a `LATERAL` join) answer the children or counts of 100 parents in 1.2 ms against 14.6 ms and 5.8 ms; `OR` of equalities stayed for "all children", where `IN (subselect)` was 2.6× slower. A `filter()` scan fetches 1,024 documents at a time (256 on SQLite), not eight round trips for 2,000. The Postgres driver's object is kept as the document (`::text` and `JSON.parse` was slower), and `= ANY` is no faster than `IN` for `getMany`.
- **sum, avg, min and max are the database's** when the answer is exactly the loop's (no `filter()` or `skip()`, every value a number, integers that add exactly for the sum, fewer documents than the scan limit); otherwise the pass over the documents words the errors as before. `Dialect.numberStats` (`TOTAL` and `typeof` on SQLite, `jsonb_typeof` and `numeric` on Postgres, `$group` on MongoDB) returns counts; DocStore decides. SQLite's first statement reads the value alone, so an index answers it, and checks values of 0 or 1 against the document's JSON type (JSON `true` reads as 1). The field is read once per document on Postgres (an `OFFSET 0` fence): 10,000 documents took 150 ms in JavaScript, 38 ms with the field read three times and 19 ms once.
- **MongoDB: documents.** `createMongoDb` (`db/mongodb.ts`, the official driver 7.8.0, which works under Bun): a collection per table, a document `{ _id, _creationTime, doc: {…}, _s_<index>: [words] }` with the fields nested as the SQL adapters keep them in a column, and the indexes the SQL adapters build (`doc.<field>…`, then `_creationTime` and `_id`), so a range, an order and a keyset page are one index. DocStore compiles a MongoDB filter and sort beside the SQL it builds for each predicate, bound, equality and keyset (`Predicate.mongo`, `plan().filter/sort`) and calls `tx.mongo` (`MongoOps`) where it would run SQL; the SQL adapters build nothing extra that they use. Search indexes are an array of each document's words, one entry for each occurrence; a search matches every word with the last a prefix, and ranks by BM25 computed in the aggregation (`MongoOps.search`: term counts and lengths from the array, the average length over the matches with `$setWindowFields`, no IDF because every match has every word). Postgres ranks with `ts_rank(…, 1)` (length-normalized; its count of a repeated word is weak, so only SQLite and MongoDB agree on the exact order of the ranking test). `include` with `take` is one aggregation (`$documents` and a `$lookup` with a pipeline) because a transaction allows one operation at a time. The adapter queues a transaction's operations itself: `Promise.all` of gets is ordinary in functions and MongoDB refuses overlapping operations in a session. At connection it checks `hello` and `buildInfo`: a standalone server (no transactions) or a version before 6.0 fails at startup with the fix, not at the first write. Spans for each operation are recorded like statements.
- **MongoDB: the engine's own tables are collections, written by the same SQL.** The scheduler, dashboard admins and sessions, the audit log, environment, migrations, settings and backups are SQL with hand-written statements in about ten files, and the scheduler's rows must commit with a mutation's documents (scheduled mutations are exactly-once). Three ways were possible. A relational store beside MongoDB (SQLite in `DATA_DIR`, or Postgres) breaks that atomicity and a second server, and adds a second database to run. A per-table interface with a SQL and a MongoDB implementation rewrites about 45 call sites that work and are tested on two databases. `db/mongodb-sql.ts` interprets the statements as they are: a tokenizer and a reader for SELECT (columns, `*`, `COUNT(*)`, `MAX()`), INSERT (with `ON CONFLICT … DO NOTHING | DO UPDATE SET … = excluded.…`), UPDATE (with `RETURNING`, run as `findOneAndUpdate` so a claim is atomic), DELETE, `WHERE` of `=`, `<`, `<=`, `>`, `>=`, `IN` and `LIKE 'x%'` joined by AND, `ORDER BY` columns and `LIMIT`. It runs inside the caller's transaction (`txOf` gives `query`/`execute` the session), so `schedule(tx, …)` is in the same MongoDB transaction as the mutation's inserts, and a rolled-back mutation takes its job with it. Anything outside those shapes throws "MongoDB can't run this SQL", and `test/db-system.test.ts` runs every statement the engine makes on every adapter and compares the answers, so a new statement fails there first. A table's primary key that is not `_id` (`name` of `_env`, `_settings`, `_migrations`) is kept in `_id`, a row has every column (`null` where unset, as SQL returns), and `SYSTEM_TABLES` lists the columns, the unique keys (`_admins.email`) and the indexes. The same interpreter serves the SQL a backup runs against a document table (counts, `SELECT … WHERE "_id" > ? ORDER BY "_id" LIMIT 1000`). Backups and restores, the CLI's data commands, the dashboard's data pages and Better Auth needed nothing else: they were DocStore or this SQL. `readStoredSettings` reads `_settings` through the same adapter before the server's configuration exists.
- **MongoDB: a mutation uses a transaction only when it needs one.** A transaction costs MongoDB several commands (a start with the first operation, a commit) and a journal wait; a one-document write costs one command, and is atomic by itself. A mutation that inserted one document took 1,557 a second and one that read a document and wrote it back 789 (p50 40 and 76 ms at 64 in flight, the database's core full), against 3,870 and 1,836 on Postgres. The adapter (`mongodb.ts`, `Live`) goes on without a session for as long as that is correct: (a) a blind insert of one document is held; (b) the first document read by id is read on its own (one document is a consistent snapshot) and kept, so reading it again is not a command; (c) a write of that document is held as a conditional one, `updateOne({ _id, doc: <as it was read> })`, so it applies only if the document is still as it was read, and its absence is a write conflict that `Executor.mutate` retries like any other (the stored value is the version: no field is added to documents, and a document with an operator-looking top-level key, `$x`, takes the transaction path); (d) the mutation ends with at most one held write, which goes out alone. Inserts held this way, from every mutation that is running, go out as one unordered `insertMany` while the one before is in flight (a lone one goes out at once, nothing waits for a batch to fill; each mutation hears of its own document, so a duplicate `_id` fails only its own). Anything else — a second document read, a query, a count, SQL for the engine's tables, a second write, a read after a held write — needs the transaction: with nothing read yet it starts and writes what was held; with a document already read, `NeedsTransaction` makes the adapter run the function again inside one (`TransactionOptions.rerunnable`, now also passed by `Executor.mutate`, whose per-run state, the topics and the after-commit tasks, is reset at the start of every run; a function that catches the error still gets the rerun). The guarantee is the same as a transaction's, which on MongoDB is snapshot isolation: reads are validated only for the documents written, and the one document read is the one checked. When most mutations of a process fall back, new ones start in a transaction (an average over the last runs, with a probe every 32nd). Insert one document: 1,557 → 8,242 a second (p50 40 → 6.9 ms; Postgres 3,870); read one and write it back: 789 → 1,374 (p50 76 → 44 ms; Postgres 1,836, SQLite 13,300). The rest is MongoDB's: the same find and update with a real change, from the driver alone on those cores, is 2,216 a second, and 3,107 with `w=1&journal=false` in `DATABASE_URL` (the engine: 1,962), which trades a majority-acknowledged, journaled write for speed and is not the default. `retryWrites=false` and `readConcern` other than snapshot (+14% in a raw test, and reads that could be rolled back) were tried and left alone. A second read of a document in a transaction is also not a command now.
- **MongoDB: what stays different.** (1) **Writes are snapshot isolation, not serializable**: MongoDB has no serializable level, and its transactions detect only write-write conflicts, so two mutations that each read documents and write others can both commit (write skew), where Postgres aborts one. Making reads conflict means writing a guard document for each read and each predicate (a topic), which turns every mutation that queries a list into a writer of that list's guard: more retries on the hot path to close a gap few functions have. A function that needs it increments a counter document both mutations touch. (2) The telemetry store stays a SQLite file in `DATA_DIR`, one for each server (the dashboard of a server shows its own traffic; Postgres shares one). (3) `backup` (a file copy of SQLite) is not offered; `mongodump` or a full backup is. (4) Field names that are indexed or filtered must be plain identifiers, as on every database (they go into SQL text and paths). (5) The driver decodes BSON in JavaScript: a 20-document `find` costs 0.28 ms of CPU, 0.12 ms of it BSON (`raw: true` would skip it, and then the work moves to ours). On one core that is about 4,400 uncached 20-document queries a second against 9,500 on Postgres; `RUNTIME_WORKERS` adds cores. Engine numbers (`benchmarks/load/engine-compare.sh`, `WHICH=mongodb`, 4 vCPU, database on its own core): cached query 47,000 a second; uncached query over 64 lists 3,100 (5,800 with `RUNTIME_WORKERS=2`), p50 18 ms (9.7 ms); mutation (insert one document) 8,240 a second, p50 7 ms, and read-one-write-it-back 1,370, p50 44 ms (see the bullet above; before that change 1,560 and 790, which were a majority-acknowledged transaction each); fan-out to 1,000 subscribers p50 72 ms, p99 104 ms, one run per write, as on SQLite and Postgres.

## Forge RPC

User request: a tRPC-backed microservice transport with typed calls through Nest's `ClientProxy`, "name it forge rpc", routers declared "based from nest trpc" (nestjs-trpc), contracts "generated", recommended "only for forge-to-forge microservices communication", the monorepo template suggesting it, "optimized too if possible", and Nest only through the runtime's own entries. Inventory first (verified against Nest 12.3.2, tRPC 11.19.0, Zod 4.6.7, Bun 1.4.4).

- **Backend to backend only** (user decision: "it will never be used in a frontend or web app"). A frontend calls its own backend's functions, and that backend calls the service, so `FORGE_RPC_TOKEN` stays on servers. Codegen's frontend-import check fails on `@archlast/forge-runtime/nest/rpc` and `forge/_generated/rpc` in `src/` or `app/`, and both classes throw where `window` exists (browsers, React Native, Tauri pages).
- **A Bun-only fork of tRPC v11's HTTP protocol, written for Forge RPC** (user request, after the profile below: "fork it and optimize the hell out of it", "minify the trpc fork, make it bun native only", "at least 2x faster than tcp"). tRPC is MIT, and the first version of Forge RPC ran on `@trpc/server`/`@trpc/client` 11.19.0, pinned. Its compiled output spent the calls on Babel's `_objectSpread2` helper (about a fifth of the CPU of a call, in every middleware layer and in the client: replacing that one function with `Object.assign` made the benchmark 27% faster), on one `AbortController` per call and on layers of observables, none of which a backend-to-backend call needs. Trimming the library would have kept most of it; `src/forge-rpc/` keeps only what Forge RPC uses and keeps tRPC's **wire format**, so a stock tRPC client still calls a Forge RPC server and Forge RPC's caller still calls a stock tRPC server (`test/forge-rpc.test.ts` runs both). Notice in `THIRD_PARTY_NOTICES.md`. `@trpc/*` are dev dependencies now: only that test uses them, and users no longer install them.
- **Routers as nestjs-trpc declares them, built on Nest's own handlers.** `@Router({ alias })` applies `MessagePattern("<alias>.<method>", FORGE_RPC, { forgeRpc: { kind, input, output } })` to each `@Query`/`@Mutation` method, then `Controller()` and `UseFilters(ForgeRpcFilter)` to the class. `FORGE_RPC` is a `Symbol.for` transport id, so only `ForgeRpcServer` gets them (Nest's listener filter), other transports in the same app don't, and the server reads each method's schemas from the handler's `extras`. `@Input(key?)` is Nest's `Payload(key?)`. Guards, pipes, interceptors and DI work because these are ordinary Nest handlers.
- **Errors go through our class filter, because Nest's runs first.** A custom transport never sees an exception: Nest's RPC proxy has already turned an `RpcException` into `{ status: "error", message }` and anything else into "Internal server error" (logged on stderr, with no request id). `ForgeRpcFilter` maps a `ForgeError` (by name, across copies) and an `RpcException` to `BAD_REQUEST`, and logs anything else with the call's request id before answering "Server error (request id)". These are the engine's envelope fields, `{ message, code, data?, requestId }`, plus Nest's `status`. tRPC runs with `isDev: false` and an error formatter: its default dev mode puts `data.stack` in every response (the engine leaves `NODE_ENV` unset), and it sends an unexpected error's message as it is. A remote `BAD_REQUEST` becomes a `ForgeError` in the caller, so a service's user-facing error reaches the end user as the service meant.
- **The server is one function from a `Request` to a `Response`, for `Bun.serve`** (`forge-rpc/server.ts`). It reads the path and the `batch` flag from the URL string without `new URL`, checks the token once per request, parses the body once, runs a batch's calls together, and writes the answer by joining each call's JSON text: no per-call `Response`, no options objects. Zod schemas are called directly and synchronously (`safeParse`), switching to `safeParseAsync` only for a schema that turns out to be async; any other Standard Schema goes through `~standard.validate`. The token header that passed is remembered in a `Set` (it hashes the whole string before it compares, so how much of a wrong guess matches isn't visible to timing); anything else is compared as SHA-256 digests with `timingSafeEqual`, as before. A wrong token is refused before the procedure is looked up, so it no longer tells a caller which procedures exist. The body limit is `MAX_REQUEST_BYTES` (Bun's `maxRequestBodySize`), and one request carries at most 256 calls.
- **The client prefers a WebSocket and falls back to HTTP batches.** A measurement decided it: one sequential round trip in Bun costs 80 µs with `fetch`, 8.7 µs on a WebSocket and 8.4 µs on a raw socket, and a profile of a lone call showed no JavaScript to remove (half the time waiting in the event loop, 37% inside `fetch`). So HTTP alone was 3.4× slower than TCP for a caller with nothing to batch (9,100 calls a second against 31,000), and ahead only from about 5 concurrent callers. `Bun.serve` takes the WebSocket on the same port: an upgrade that carries the token (the check is the HTTP one), then frames of calls, `[[id, "router.method", input?, traceparent?], …]` (a negative id: the call has no input, because `null` is an input of its own), answered by frames of `[[id, {"result"|"error"}], …]`, the objects the HTTP array holds. Calls are chunked at 128 to a frame (the server takes 256). Where a frame's answers go back in one frame once all its calls are done, with `setImmediate` as the limit for a slow call: sending each answer when its promise settled gave 1.8 answers a frame at 64 callers and half the throughput. A service that refuses the upgrade (a proxy, an older Forge RPC, a tRPC server) gets its calls over HTTP and is not tried again for 30 s. A call sent on a connection that then drops fails with `SERVICE_UNAVAILABLE` (it may have run, and calls are at-most-once, like actions); calls that only waited for the connection go over HTTP. The WebSocket is `unref`ed, so it never keeps a process alive. A traced caller sends its `traceparent` in the frame and records the `http` client span that `fetch` would have recorded (`outboundSpan`, through the telemetry bridge). `websocket: false` on the client always uses HTTP.
- **The HTTP path batches in a microtask: calls made in the same tick are one `fetch` (up to 32 a request, every call a POST).** One `AbortController` and one timer serve a whole request, not each call: the request is aborted when every call in it has ended (answered, timed out or unsubscribed from). 32 beat 8 and 16 and matched 64 to 256 at 64 concurrent callers. A POST carries a query too (the server allows it), so `publish()` needs no contract to know a pattern's kind, and a 64 KB input never goes in a URL. `ForgeRpcClient.send()` is its own small observable: Nest's builds an rxjs pipeline for connecting and serializing that Forge RPC has no use for. The calls of one HTTP request answer together, so one slow call in a batch holds up the others in it.
- **Deadlines are the client's own timer**, one per request (`timeoutMs`, default 5000, code `TIMEOUT`): every call in it still waiting when it fires fails with `TIMEOUT` and the request is aborted. Unsubscribing a call stops it answering; the request itself is aborted once none of its calls is left. `SERVICE_UNAVAILABLE` is a call with no Forge RPC answer (nothing listening, or something else answering). `emit()` fails: request-response only.
- **One shared token, `FORGE_RPC_TOKEN`**, at least 16 characters. The server requires it at construction (an unset variable would otherwise make the expected header "Bearer undefined"). The client reads it at its first call and fails that call with `UNAUTHORIZED`, because `ClientsModule.register()` and class fields make clients as their modules load: a check at construction made every app without the variable fail to load, even one that never calls the service. The header is compared as SHA-256 digests with `timingSafeEqual`, so the token's length doesn't leak either.
- **The contract is generated, types only.** Codegen imports the forge/ files that contain `@Router(` in a process of its own (decorator plugin registered, `compileDecorators` from `@archlast/forge-runtime/server`), reads `Symbol.for("archlast-forge.rpc.router")` off the exported classes, and turns each schema into a type through JSON Schema (Zod's `toJSONSchema` with `io` and `unrepresentable: "any"`, else Standard JSON Schema). A procedure without an output schema gets `unknown`, and codegen warns. It first got `Awaited<ReturnType<Router["method"]>>`, with an `import type` of the router: found by typechecking a real monorepo, that import puts the service's `_generated/dataModel` (which declares the global `Register.schema`) into the caller's TypeScript project, and the caller's typecheck fails with TS2717. It is written to `forge/_generated/rpc.ts` (removed when there are no routers). The caller validates nothing: types catch mistakes at compile time, and the service checks input and output. That also means no Zod version has to match across apps.
- **Monorepos default to it** (`--transport forge-rpc`). Each service gets `forge/<service>.router.ts` and a `ForgeRpcServer` on `<SERVICE>_RPC_PORT`; the main app's service class for it holds a `createForgeRpcClient<ServiceRpc>()` client; `packages/contracts` re-exports each service's `rpc.ts`. That is a package of its own, not part of `packages/api`, which depends on the main app (a cycle). Every app's `.env` gets the same generated token. Generated code imports only the runtime's entries, never `@nestjs/*` or `@trpc/*`.
- **Where the time went, and what it is now.** Profiled with `bun --cpu-prof` on `benchmarks/forge-rpc/bench.ts` (one engine, 64 concurrent callers through `ClientProxy`, 4-core Xeon, answers checked): TCP spent about 30% of its CPU in `writeBuffered`, a socket write per message each way, and the first Forge RPC about a fifth in tRPC's spread helper and another 13% in abort signals. Steps, small calls a second against TCP's 37,000 on the same run: the first version 14,600; the fork over HTTP with Nest's own handler chain and `send()` 67,000; recording the telemetry entry in the transport (below) 78,000; `@Router` classes without the generic transport interceptor, which wrapped every call in an observable and a promise, 130,000 over HTTP batches; the WebSocket transport with answers coalesced per frame 137,000 to 146,000 in the benchmark (TCP 33,000 to 34,000: 4.2×). Other setups, small calls a second: three client processes of 32 callers each against a server on one core, 199,000 to 217,000 (TCP 54,000); three processes of one caller each, 38,000 to 39,000 (TCP 23,000 to 25,000); one caller in the same process, 49,000 (TCP 29,000). 64 KB calls, where the time is in moving bytes: 4,060 to 4,370 against TCP's 3,150 to 3,270. Redis wasn't measured (no server on this machine; `BENCH_REDIS_URL` adds it).
- **Telemetry is recorded by the transport, not by an interceptor.** `timeClass(target, "controller", false)` leaves out the interceptor that records microservice messages as `rpc` requests (the others still get it), and `ForgeRpcServer` calls the same `entry` around the handler, under the caller's `traceparent`. The exception the entry records is the original one (`ForgeRpcFilter` keeps it on the wire error), so a `ForgeError` is still the caller's and a crash is still an error. The request id is made when something asks for it (an error, `getRequestId()`), not for every call.
- **The fork is built minified, on its own** (`@archlast/forge-runtime/forge-rpc`, `dist/forge-rpc/index.js`, 8.7 KB; `nest-rpc.js` imports it by the package's name, which the build leaves external, as it does for the Nest companions). This is the one part of the runtime that ships minified: the rule that libraries stay readable is for the code people debug into, and this file is a protocol they read from `src/forge-rpc/` and `docs/`. It is Bun only (`Bun.serve`, Bun's `fetch`, `queueMicrotask`), and not a stable API: use `/nest/rpc`.
- Tested: `packages/runtime/test/nest.test.ts` ("Forge RPC", against `fixture-nest/shop.router.ts` in a child runtime process), type checks in `fixture-nest/_rpc-types.ts`, codegen in `packages/cli/test/rpc-codegen.test.ts`, and a generated monorepo run end to end in `packages/create-archlast-forge/test/monorepo.test.ts` (codegen, a type check that also has to fail on a wrong argument, the call). Not tested: services in separate containers, and Forge RPC under `RUNTIME_WORKERS > 1` (it listens in worker 0, as the TCP test checks for TCP).

## NestJS

- **NestJS lives in the runtime, as `@archlast/forge-runtime/nest`** (user decision: "nestjs is a backend framework so it will live in the backend", available to both modes). Projects import Nest's decorators, exceptions and pipes from there and never install `@nestjs/*`; the runtime depends on `@nestjs/common` and `@nestjs/core` 12, `reflect-metadata`, `rxjs` and `path-to-regexp`. Only projects that import the subpath load Nest.
- **Our own adapter, not `@krisanalfa/bunest-adapter`** (user decision, after the facts below). bunest 0.6.0 declares NestJS 11 as a peer (Nest is at 12), its one file imports graphql-yoga, graphql, `@nestjs/graphql` and `@nestjs/websockets` when it loads, and its speed comes from owning a `Bun.serve` with Bun's router. The engine already owns the server and forwards `/http/*` into the function runtime, which is where a controller gets its ctx, so bunest would have meant a second server and a local hop. `ForgeAdapter` takes requests straight from the engine's `/http` routing: Nest's routes go on a small Express-style router (path-to-regexp 8, as Nest 12 writes paths), and `handle()` returns a Web `Response`.
- **A request is an HTTP action.** `nest()` mounts Nest as `pathPrefix` routes (default `/`) built with `httpAction()`, so rate limits, request ids, logs, metrics and the action time limit apply, `http.route()` routes keep priority, and controllers get an `ActionCtx` (`@Ctx()`): they reach data through `ctx.runQuery`/`ctx.runMutation`, which keeps writes in transactions and reads reactive. HttpExceptions answer as Nest answers them; a `ForgeError` answers 400 and anything else 500 with the request id, exactly as from an HTTP action.
- **Services get the call's ctx through request scope.** `ForgeService<C>` has `this.ctx` (property injection of the request-scoped `CTX` provider), and `@InjectCtx()` does the same for a constructor parameter. `inject(ctx, Service)` registers the ctx as the "request" of a new context id and resolves the service, so a function's services see that function's ctx and share instances within the call; singletons stay singletons. `inject`'s type only accepts a ctx that has what `C` asks for (a query can't get a `ForgeService<MutationCtx>`). The cost is an instance of each request-scoped class per call.
- **The engine compiles decorators itself.** Bun applies the tsconfig of the directory the process runs in, not the one next to the file, so `forge/tsconfig.json`'s `experimentalDecorators` would be ignored from the CLI or the engine image. `loadProject` registers a `Bun.plugin` for the `forge/` directory: a file that contains a decorator is built on its own with `Bun.build` (the flags forced, extending `forge/tsconfig.json`, every import external, inline source map, so stack traces keep their lines); other files load unchanged. Bun's transpiler alone moved lines, which is why it is `Bun.build`. The templates set both flags in `forge/tsconfig.json` (and `experimentalDecorators` in a full-stack app's root tsconfig, which type-checks `forge/` through `api.ts`) for editors and `tsc`.
- **The whole of Nest is in the runtime** (user decision: CORS, WebSocket gateways, microservices, GraphQL and Express-style writes "fully supported", with bunest as the reference, and every package in the runtime rather than optional). `@nestjs/websockets`, `@nestjs/microservices`, `@nestjs/platform-socket.io` (with `socket.io` and `engine.io`), `@nestjs/graphql`, `graphql`, `graphql-yoga`, `graphql-ws`, `cors` and the clients Nest's transports load (`ioredis`, `nats`, `mqtt`, `kafkajs`, `amqplib` and `amqp-connection-manager`, `@grpc/grpc-js` and `@grpc/proto-loader`) are dependencies, so no transport needs an install. A packed backend's `node_modules` measures 122 MB, about 32 MB of it the transport clients and Socket.IO. Bundling them into the runtime was rejected: users' resolvers and gateways need the same `graphql` and Nest classes their types name. They load only for projects that import them. The companions are `/nest/websockets`, `/nest/graphql` and `/nest/microservices`; they import the package by its own name, because a relative import made the build put `nest.ts` in a shared chunk, which loses its `export *` of `@nestjs/common` (a CommonJS package whose names Bun can't list).
- **The engine holds gateway sockets; the runtime has the gateways.** The server upgrades WebSockets under `/http/*` (the `/rpc` origin check and rate limit apply) and sends their events to the function runtime as messages that need no answer (`{ t: "ws", op: "open" | "message" | "close" }`); the runtime sends to or closes a socket the same way. A socket stays with the worker that took its open, and when a worker stops or crashes its sockets are closed so clients reconnect. The runtime gives a project's `nest.ts` what it needs through a `Symbol.for` global (identity, an `ActionCtx`, send, close), because the project's copy of the package is not the engine's, and `nest.ts` registers where socket events go the same way. `ForgeWsAdapter` speaks `@nestjs/platform-ws`'s protocol (JSON `{ event, data }`); `websockets: "socket.io"` swaps in `ForgeIoAdapter`, Nest's `IoAdapter` with an engine.io server whose `wsEngine` hands over the engine's sockets, and whose long-polling requests come through the HTTP adapter. The caller is resolved once from the upgrade request.
- **Every gateway socket is held by worker 0.** With `RUNTIME_WORKERS > 1`, `wsEvent` pins opens to the first worker and the server sends Engine.IO polling requests (`?EIO=`) there too, so `server.clients`, Socket.IO rooms and a polling session's state are in one place. Gateway handlers don't spread across workers; HTTP routes and GraphQL queries do. Events crossing workers go through `createPubSub`, the engine's: a publish is a `{ t: "relay" }` message that the server sends to every worker. Several engine servers (the Redis bus) don't share sockets or pubsub events; the database is how to reach everyone there.
- **Responses stream when they are written.** Nest's `res` has Express's and Node's API. Until a handler writes or flushes, the response is one body; after, it is a stream. The engine passes a stream through when the Response is marked with `Symbol.for("archlast-forge.stream")` or is `text/event-stream` (so plain HTTP actions can stream SSE too). Inline it is the Response's own body; from a child process the result goes first and the bytes follow as `{ t: "chunk" }` messages. A client that leaves cancels the stream: inline the Response's body is cancelled; from a child process the server sends `{ t: "cancel", id }` and the child cancels its reader, so `req` and `res` get `"close"` in both.
- **GraphQL is our driver on Yoga, not Apollo or bunest's.** Nest's drivers pick an integration by `httpAdapter.getType()`, and ours is neither Express nor Fastify. `ForgeGraphQLDriver` takes the schema `@nestjs/graphql` builds, serves it with Yoga (which runs on Web requests, the form the engine already has) on GET and POST at `path`, and runs subscriptions with `graphql-ws`'s `makeServer` on `onSocket(path)`.
- **Microservices listen inside the function runtime.** `nest(http, { microservices })` calls `connectMicroservice()` for each and `startAllMicroservices()` after `init()`. Their handlers get an anonymous `ActionCtx` (a message has no caller) through the engine's `Ctx`, which shadows Nest's in `/nest/microservices` (Nest's is `TransportCtx`). Only the first runtime process (`ARCHLAST_WORKER` 0) connects them, so a port is bound once with `RUNTIME_WORKERS > 1`.
- **Still out:** `listen()`, static assets, views, versioning other than URI, `@Ip()`. One Nest app per process (`nest()` once), which is one per deployment.

## Observability

- **Built into the engine and its dashboard** (user request: "a builtin observable system dashboard + the reactive dashboard system we have", after Traceway and NestJS Observe). One dashboard at `/_dashboard`: the observability pages (Observe, Performance) next to the BaaS ones (Backend, Admin). Nothing to install, `TELEMETRY=off` to turn it off; then the dashboard says so instead of failing, and Users, Jobs and Logs open on the views that don't need it.
- **Traceway is ported, not forked.** Traceway (MIT) is Go, Svelte and ClickHouse; the engine is one Bun process on SQLite or Postgres. Its exception fingerprint and endpoint impact score (Apdex and its floors) are ported to TypeScript in `telemetry/traceway.ts`, with the notice in `packages/runtime/THIRD_PARTY_NOTICES.md` (shipped in the tarball). Changes, marked in the file: only the app's own stack frames are hashed when there are any (dependency frames move with every upgrade), message-only errors have their variable parts taken out, and Apdex T depends on the kind of request.
- **NestJS Observe is matched, not copied.** It is proprietary: its feature set and page structure (overview, requests, errors grouped into issues, users, jobs, spans, hotspots, map, runtime, releases, SLOs, alerts) were the reference, in our own design and code. None of its code, artwork, logo or text is used.
- **A store of its own.** On SQLite, `DATA_DIR/telemetry.db`: SQLite has one writer, and telemetry in `app.db` would queue behind the app's writes (and hold them up). On Postgres, `_otel_*` tables in the app's database, so every server shares them. The store, its queries, compaction and alert checks run on a Bun Worker thread, so a 30-day chart never delays a request; the server sends it batches once a second.
- **Every request counted, detail sampled.** Per-minute rollups per operation with log-scale histograms (8% buckets) make counts exact and percentiles accurate to a few percent at any traffic. Spans are recorded for up to `TELEMETRY_DETAIL_PER_SECOND` (200) requests a second, then for a share that keeps that rate, weighted 1/share in span statistics; the rest run untraced in the function runtime. Recording every span cost about 17% of throughput on uncached calls at saturation; with the detail rate, throughput with telemetry on is within the noise of off (about 4,300 vs 4,100 calls a second on one core; 14,500 vs 15,000 cached). Kept traces are tail-sampled after they finish: errors and slow requests (over 4×T) have their own budget, `TELEMETRY_TRACES_PER_SECOND` (25) each, with weight 1/probability so counts read from kept traces stay unbiased. A caller's sampled `traceparent` forces detail, as OpenTelemetry's parent-based sampler does.
- **Spans** come from the function runtime through `AsyncLocalStorage`: each function (nested calls included), each database statement (a wrapper on the transaction), each outbound `fetch` (which carries `traceparent` on), Nest methods and `trace.span()`. Own time is a span's duration minus the union of its children's; Hotspots groups it by code unit (forge module, Nest class, database, host).
- **Nest classes are timed by our decorators.** `Injectable`, `Controller`, `Resolver` and `WebSocketGateway` from `@archlast/forge-runtime/nest` wrap the class's methods (keeping Reflect metadata), so only the user's classes are spans, not Nest's or libraries'.
- **Releases** are named by the platform's commit variable (`FORGE_RELEASE`, `GIT_COMMIT`, `GITHUB_SHA`, …) or a hash of `forge/`, and judged on the 30 minutes before and after, cut at the minute, with at least 20 requests a side.
- **OTLP ingest without an SDK.** `/otlp/v1/{traces,logs,metrics}` take protobuf (a hand-written decoder for the OTLP v1 messages; `protobufjs` is only a test dependency) or JSON, gzip or deflate. Ingest keys are stored hashed, can pin a service name, and are not needed in dev. Cumulative metrics become per-minute deltas, resetting only when a value drops. An engine's own export pointed back at it (same `OTEL_SERVICE_NAME`, marked by an `x-forge-service` header) is ignored with one warning, because those requests are recorded already.
- **Alerts** are checked every minute in the worker and posted to Slack-compatible webhooks (`text`). A window with no requests keeps a rule's state: no data proves neither a problem nor a recovery. Deleting an SLO deletes its burn-rate rules.
- **The latest runtime sample per process is one grouped join** (2026-11-02). It was a subquery per row (`time = (SELECT MAX(time) … WHERE instance = s.instance)`) with no index on the instance: quadratic, 89 s over a dev machine's month of samples (19k rows; every restart in dev is new processes). The telemetry thread answers one question at a time on synchronous SQLite, so every other dashboard call queued behind it, and Bun's idle timeout (75 s) closed the connection: the 502 through a proxy. Now 0.1 s. The dashboard also stopped polling while an answer is still on the way (`useObs`, `useAsync`), so ticks don't pile up behind a slow store.
- **One dashboard for a main app and its microservices** (user request: "main app will only have the dashboard but microservices telemetry and metrics and observe data will share single dashboard (even the schemas and stuff)"). A microservice (`DASHBOARD_URL`) keeps no store: its recorder's batches go as JSON to the main app's `POST /_telemetry` (`telemetry/forward.ts`, a minute of batches held while the main app is away), which writes them into its store unchanged. Not OTLP: the engine's own batches carry rollups, runtime samples and releases that OTLP has no place for, and the store would only have to rebuild them. Data, schema and functions go the other way: the dashboard adds `?target=<name>` and the main app forwards the admin call to the service in `MICROSERVICES` with `DASHBOARD_TOKEN` and the signed-in user's email and role (`x-forge-actor`, `x-forge-role`), so the service enforces roles as its own dashboard would. A service accepts the token only when it has `DASHBOARD_URL` (a main app doesn't accept it as an admin credential), and a main app refuses telemetry under its own name. A new token rather than `FORGE_RPC_TOKEN`: the transport may be TCP or NATS, and a credential for calling routers shouldn't also be one for the admin API.
- **Nodes are server processes** (`host:pid`; in a container or pod the host is its name), with the function-runtime processes they run (`/wN`). The server sends its first sample a second after it starts, so a replica a scaler adds shows at once. Per-node requests come from the minute rollups' `instance`, which compaction folds into `*` after two days. The live-nodes alert counts distinct (service, instance) servers that sampled in the window.
- **Messages to the app are requests** (after NestJS Observe's SDK, which reports `rpc`, `grpc`, `ws` and `graphql` operations): a microservice transport's message (Forge RPC included) is kind `rpc` by pattern, a gateway message `ws` as `Gateway:event`. An interceptor that `timeClass` puts on every controller and gateway calls the telemetry bridge's `entry` in `runtime-core.ts`, which records it like a scheduler job (a trace record sent to the server), at most `TELEMETRY_DETAIL_PER_SECOND` (this process's share) in detail and the rest only counted, as the server does for HTTP. Forge RPC passes the caller's `traceparent` on `ForgeRpcContext`, so a call joins the caller's trace. GraphQL stays one `http` request per POST (per-operation naming would mean a Yoga plugin), and gateway connects and disconnects aren't requests (Observe doesn't report them either).
- **The Services page is the Nest classes** (Observe's "Services"): Hotspots over `nest` spans only (`obs.hotspots { type: "nest" }`), sortable. What was the Services page (the reporting services) is Microservices.
- **Not done:** session replay, on-call schedules and paging, AI or LLM call tracing, status pages, assigning or commenting on issues, retention per signal, sampling decisions shared across services, and GC or event-loop utilization metrics (Bun exposes neither). The Docker end-to-end run (`bun run e2e`) was not repeated for this work, because Docker was unavailable where it was built.

## Many users on one server

From a hospital-scale load test of an app on the engine (300 signed-in staff, every function behind an authorization check). Findings were checked against the code and profiles first; the measurements are in `benchmarks/hospital/README.md`.

- **A query can declare `access`, and then its result is shared.** The engine can't tell a check from a use of `ctx.auth`, so it cached any query that touched it once per user: 300 users meant 300 runs of the same query, and 300 re-runs after each change. A query may now say which part is the check (`access`, run for every caller on every serve and push) and which is the data (the handler, run once for everyone who passes, with `ctx.auth` made unavailable so the result can't depend on the caller). It is opt-in because only the author knows. Rejected: guessing from behaviour (a result that happens to match for two callers proves nothing), and a key by role (the engine would have to know what a role is).
- **The check is watched like any read.** What `access` read, and the caller's own session and user rows, are topics: a write to one evicts the kept check and wakes a subscription, so a deactivated user or an ended session is refused on the very next call and cut off live. A refusal is never kept. A check is kept only for a caller that could be pinned to topics (the direct session path); with Better Auth plugins or secondary storage it runs every time.
- **The server keeps who is calling.** Resolving the caller was a round trip to the function runtime on every authenticated call, which capped a cached authenticated query at about a quarter of an anonymous one. The server now keeps the identity per credential until a write to the session or user it came from, or the session's end or refresh, whichever is first. Not a time-to-live alone: that would let a ban wait out the timer. Anonymous requests skip the lookup.
- **Queued queries start a few per turn, not all at once.** Against SQLite a query never waits for I/O, so a burst ran as one long run of microtasks: nothing was sent and no message read until the last query was done. The server, hearing nothing, took the backlog for a hang and killed the process, failing every call in it. The process now starts as many as fit a 4 ms slice at the pace queries have been taking (a cheap query batches as before, a heavy one goes alone). Mutations are not queued: the one writer runs them in turn, and mutations that start together are committed together (group commit), which one start per turn halved. Rejected: one query per turn (measured 15% slower at 10% writes).
- **Overload is refused early.** A query that would wait longer than a function may run is refused at once with the retryable `503`, from the pace the process has shown over the last two seconds (not trusted until it has five answers, and not once stale, so a burst after quiet gets in); a queued query that has waited that long is refused by the process instead of being run for a caller who has gone. Mutations, actions and HTTP routes are not queued this way, so none of them holds a place.
- **A slow run no longer multiplies.** Callers waiting on a run that a write overlapped each started their own run; now one starts it and the rest join, and under steady writes that was the difference between one run and one per waiting caller. A run that a write overlaps still can't be cached or shared. That is correct, and it is why a query over data that is written constantly gains little from any cache.
- **Calls go to the process with the fewest waiting**, not round-robin, so a long call holds up only what is queued behind it. Queue depth is in the Runtime page's in-flight figure, `/metrics`, and a warning at about two seconds of work waiting.
- **A result crosses to the server as its JSON text, and its topics as one string.** The server answers with the JSON and never needs the object unless something reads `value`, which then parses from the text (once; `lazyValue`). The object tree and a long array of topic strings were most of what a large result cost to move. Standalone, a round trip took 0.51 ms with the tree against 0.08 ms without for 34 KB of JSON, and 4.4 ms against 0.7 ms for 273 KB; 5,000 topics took 2.5 ms as an array and 0.3 ms as one string (beside 550 KB of JSON, 3.1 ms against 1.0 ms in all). With a busy sender the tree also made a 550 KB result arrive 1.8 s late on average against 1.2 s as JSON alone. A shared (Redis) cache entry loses its second copy of the data too, and entries from an older server (with both) are still read. Rejected: compressing (the cost is serialization, not bytes on the wire), and a separate channel for results (the pipe is the only one between the processes that survives a restart).
- **Results the pipe hasn't taken yet hold the queue back.** A busy runtime process can only write to the pipe between its own turns, about 4 MB a second, which a 150 ms query returning 550 KB roughly equals. Past that the backlog grew in the pipe, where nothing could refuse a call and answers reached the server seconds after they were made. Large results (64 KB and up) are sent as messages of their own and `process.send` reports each one, and no queued query starts while more than 4 MB are unreported (or none was written for 5 s, which means the pipe is not draining). Measured on the 200-user census burst, four rounds each: the first tenth of the answers at 2.5–5.3 s instead of about 11 s, the median served call at 7.6–10.0 s instead of 11.2–11.6 s, the same number served (mean 101 against 99). 1 MB and 2 MB windows served fewer (mean 87 and 87) for no better median; 4 MB stays. Small results never reach the limit, so the common case is unchanged. A call that waited past its deadline is dropped on every turn and by a timer, whatever the process is doing.
- **The process sampler reads the heap with `process.memoryUsage()`.** `bun:jsc`'s `heapStats()` walks the heap synchronously: 36 ms at 27 MB of live objects, 180 ms at 109 MB, 490 ms at 281 MB, in the server and in every runtime process every 10 s. `memoryUsage()` gives the same figures in 0.02 ms (its `heapUsed` can include garbage not yet collected, as Node's does). The observability stack was measured as a whole and is not what held the extreme burst back: with telemetry and the sampler both off, tail latency in the stress scenario and the burst were unchanged within noise.
- **`RUNTIME_WORKERS=auto`, opt-in, and a pool that resizes while running** (user request: workers from the cores, a dashboard control, no dropped work). `auto` is `floor(cores × RUNTIME_WORKERS_RATIO)`, at least 1, ratio 0.5 by default; cores are `availableParallelism()` capped by the cgroup v2 `cpu.max` quota. The default stays 1 (the next entry), and the environment still wins over the dashboard (settings), so `auto` is what to set, in either place. In `process` mode, saving `RUNTIME_WORKERS` or `RUNTIME_WORKERS_RATIO` calls `FunctionRuntime.resize()`: new processes are added beside the others; removed ones (the last; worker 0 never goes, it has the scheduler, backups and sockets) leave the pool, finish their calls and stop, and a crash of a retiring process isn't respawned. Worker 0 hears the size (`{ t: "pool" }`): SQLite's read cache is valid only while one process writes, so it is dropped before a second process starts, and a fresh one is made once the pool is back to one. Inline ↔ process needs a restart. Measured (`benchmarks/workers`, 4 cores, 16 clients, 4 ms of CPU per call): 185 calls/s inline, 221 one process, 348 two, 599 four; 1 → 3 → 1 under load, no failed call.
- **`RUNTIME_WORKERS` still defaults to 1.** More processes help queries that compute and hurt light ones (each call crosses to a process and back: about twice the CPU of running inline), so a default would be a loss for as many apps as it helps. The warning says when to raise it.

## Backups, built-in storage and settings

Asked for together: "a backup system for the entire baas … schedule backups, download them and restore, snapshots of the data and functions and files", "an in process s3 engine … so that we still have object storage if we're in dev mode and did not opt for an s3 storage", and "all the things that are configurable for the baas should be configurable in the dashboard … put it in the settings module", with no breaking changes. Three choices were put to the user and are marked.

- **A backup is one `.tar.gz`** (`server/backup/`): `manifest.json` first, then the documents as `export` JSON Lines, the scheduled jobs and migration states, `_env` and `_settings` with their values, the `forge/` source (no `node_modules`, `data/`, dot files or files over 10 MB) and every object a `_storage` row names. Plain tar so `tar tzf` reads it, written and read as streams by a small ustar/PAX implementation of our own: `Bun.Archive` holds every entry in memory, and a backup with its files can be larger than that. Dashboard accounts, sessions, the audit log and telemetry are left out: they are the deployment's, not the app's.
- **The snapshot is one read transaction** (SQLite's reader snapshot, Postgres `repeatable read read only`), rows read raw and paged by `_id`, so a backup never holds half a mutation and writes carry on. Files are read afterwards; one deleted meanwhile is counted as missing, not an error.
- **Where backups go** (user's choice: next to the files, plus a bucket of their own): `BACKUP_S3_*` (a bucket of their own, recommended off-machine) wins, then `BACKUP_DIR`, then the files' bucket under `_backups/` with `STORAGE=s3`, then `DATA_DIR/backups`. The list is the `_backups` table; archives in the store that it doesn't know about are listed as "found" so a fresh database can restore from a bucket. A folder is per server, so with replicas use a bucket.
- **Restore brings back data and files, not code** (user's choice). Code ships with git and the image, and in production it is baked into the image, so writing `forge/` back would be wrong there and destructive in dev. The source is in the archive, and the dashboard marks backups made with code other than what runs (a hash of the same file set). Environment and settings are restored only when asked: restoring into another deployment would replace its keys.
- **A restore is all or nothing for data**: a safety backup first (its failure stops everything), files next (written back under their keys; files added since stay), then every schema table truncated and refilled, validated by the current schema, with jobs and migrations (and config if chosen) in one transaction. It publishes no per-document topics (`Executor.rewrite`); it publishes `_forge:reset` once, and every server drops its query cache and re-runs its subscriptions, so other servers on the bus see it too. Tables the backup has and the schema doesn't are refused before anything is written.
- **Scheduled backups run on every server and happen once**: worker 0 of each server checks `BACKUP_SCHEDULE` (cron, UTC) every 30 s and claims the slot by inserting a row whose id is the slot time; only the insert that lands runs. A missed slot runs once on return. `BACKUP_KEEP` prunes scheduled ones only; manual, uploaded and safety backups stay until deleted.
- **Built-in storage, not an S3 server** (user's choice: on in dev without S3, opt-in in production with `STORAGE=local`, so a deployment without storage stays one). Files live in `DATA_DIR/storage/objects` (types in `meta/`) and the engine serves `/_storage/<key>` with URLs it signs itself (HMAC over method, key and expiry with a key derived from `BETTER_AUTH_SECRET`; the host is not signed, so they work through any address). It implements the `Storage` interface `ctx.storage` already used, so functions are unchanged; speaking the S3 wire protocol (SigV4, XML listings, multipart) would only serve tools nothing here uses. Uploads stream to a temp file and are renamed in place. Responses carry `Content-Security-Policy: sandbox` and `nosniff`, because files are served from the app's own origin and an uploaded HTML page must not run as the app. `REPLICAS > 1` refuses it.
- **Bigger bodies only where uploads go.** With the built-in storage or the dashboard on, Bun's body limit is raised to `MAX_UPLOAD_MB` and every other body (`/rpc`, `/http`, `/api/auth`, `/otlp`, `/_cli`, the admin API) is read through `readBytes`/`readText`, which keep `MAX_REQUEST_BYTES` (413 `PAYLOAD_TOO_LARGE`), declared lengths and chunked bodies alike. Without either, Bun's limit is what it was.
- **Settings live in `_settings`, under the environment.** `server/settings.ts` lists every variable the engine reads with its group, type, default and doc. The server reads `_settings` itself at startup (before the runtime, which owns the database, exists: workers and limits depend on it), and the process environment wins over every stored value, so an existing deployment means exactly what it did. Values are checked when saved (type, then a full `loadConfig` with them); a stored set that stops being valid later is ignored at startup with the reason shown, rather than keeping the engine down. Environment-only: `DATA_DIR`/`DATABASE_URL` (where the settings are), `PORT`/`HOST` (port mapping), `REDIS_URL` (connected before serving), `REPLICAS`, and `BETTER_AUTH_URL`/`BETTER_AUTH_SECRET`/`ADMIN_KEY`/`DASHBOARD` (a wrong value locks you out). Owner only; audited without values.
- **Applying is a restart, not hot reconfiguration.** Most settings are read once into objects (the cache, the limiter, Bun.serve, the runtime pool); making each live was many small risks. The CLI's `serve()` restarts the server in place (`startServer({ restart })`, `stop({ keepApp })`) from the dashboard's **Restart now**; an embedder without it is told to restart the process. Backup settings are read per use and apply at once.
- **The dashboard is bundled in production mode everywhere**, dev included (`development: false`): minified (434 KB of JS instead of 1.7 MB) and on React's production build. The cost is that edits to the dashboard's own source need a restart in this repo.

## SQLite durability

User request: "is the archlast forge's durability caveat bad for production…? if not can we fix that part and still retain insane speeds?", then "optimize the inserts even with full… go back up to 12k". Measured with `benchmarks/load/convex-vs-forge.md` (section 7) on a btrfs-on-LUKS disk where an fsync takes about 3.5 ms.

- **SQLite syncs every commit by default** (`SQLITE_SYNCHRONOUS=FULL`; `NORMAL` is the opt-out). The engine ran `synchronous = NORMAL` in WAL mode, which never syncs at commit: an answered write survived a crash of the engine but not a power cut or an operating-system crash, and the code's own comment ("a reply always means committed") and the docs said nothing about it. A fast default that loses acknowledged writes is the wrong default for a database; a faster one is one setting away. Postgres (`synchronous_commit = on`) and MongoDB (majority, journaled) already waited for the disk.
- **The fsync is not run by `COMMIT`.** `PRAGMA synchronous = FULL` syncs inside `COMMIT`, on the thread that runs the functions, so every commit stops everything for the disk's sync time: inserts went from 12,673 to 6,472 a second (64 clients; toggles 24,373 to 13,186) when the disk synced in about 3.5 ms. Now the writer's connection runs `synchronous = NORMAL` and `WalSyncer` (`db/sqlite.ts`) fsyncs the `-wal` file through the asynchronous `fs.fsync`, which Bun runs on its thread pool (a 1 ms timer kept ticking through 300 fsyncs, largest gap 1.1 ms). A write is answered once an fsync that **began after its commit** has finished, which is the promise FULL makes; the writer carries on with the next batch meanwhile. Syncs run one at a time and the commits that arrive during one share the next (group commit on top of group commit).
- **What was tried and dropped.** A Worker thread that did the fsync lost replies intermittently (after a few rounds the worker had answered and the main thread never saw it, hanging `ops.test.ts` on close), and it cost a message protocol, a keep-alive timer and a "ready" handshake; the async `fs.fsync` needs none of them. Two syncs in flight were slower than one (2.0–2.3k against 2.6–2.9k inserts a second), because the kernel serializes them. `fdatasync` and a larger checkpoint threshold changed nothing. A writer connection in a Worker was rejected before any of this: a function's transaction issues statements one at a time and awaits each, so every statement would be a message round trip.
- **What decides the speed is the disk's fsync time, not the code.** With 64 clients a closed loop cannot do more than about 64 divided by the time a write waits for its sync. On the test disk (btrfs on LUKS) a bare 4 KiB fsync took 1.0 ms at some times of the day and 6 ms at others, and insert throughput followed it (see section 7 of `benchmarks/load/convex-vs-forge.md` for the runs and the probes). A server whose disk syncs in 0.1–0.5 ms pays far less. A write that arrives alone always waits for its own sync, which nothing can hide.
- **What it does not promise.** A reader can see a commit during the millisecond or two before its fsync has finished, and answer a query with it; a power cut in that window loses a row that a read had shown (Postgres makes a commit visible only after its WAL flush). Topics for live queries and the answer to the writer are sent after the sync, so subscribers hear about a write only once it is on disk. If an fsync fails, the writes waiting on it are rejected with an error, though they were committed: the caller can't tell whether they will survive.
- **Telemetry stays `NORMAL`.** Its store takes batches every second, and a lost second of metrics after a power cut costs nothing.
- **The syncer exists only for FULL and a file database.** A pending `fs.fsync` keeps the process alive like any other pending request, so a script that awaits one write does not exit under it.

## ACID across the engine

User request: "ensure that our baas is fully acid compliant (not the sqlite, the entire baas itself)", and that performance stay as it was. Checked with `packages/runtime/test/acid.test.ts`, which runs the same atomicity, consistency, isolation and durability cases on SQLite (file and memory), Postgres and MongoDB. It found three gaps, all fixed, and records what is outside any transaction on purpose.

- **MongoDB mutations were snapshot isolation, not serializable, though the docs said serializable.** 40 concurrent "claim this name" mutations all succeeded, and both of two on-call doctors went off call. MongoDB detects two writers of one document, not a read of what another writes. A transaction that scans (query, search, count, stats), or reads by id a document it does not write, now also writes one shared document (`_serial_guard`, `mongodb.ts`), so two such transactions conflict and the later one is retried like a Postgres serialization failure. Why that is enough: a snapshot-isolation anomaly needs a transaction with a read of something a concurrent one wrote, and one that wrote nothing it read (a blind insert, or a read-modify-write of the same documents, whose write conflicts anyway) cannot be part of the cycle; every transaction that can be takes the guard. Scans take it before they run, so a conflict costs as little as possible; by-id reads are judged when the function ends. `test/acid.test.ts` checks that blind inserts and read-modify-write never touch it, which keeps the benchmarked mutations on their fast paths.
- **On MongoDB, a mutation aborted for a conflict runs again one at a time within its process** (`Db.serializeRetries`, `Executor.retrying`). Forty contenders otherwise abort each other round after round and spend their ten attempts. Not on Postgres: a first version did it for every database and the toggle benchmark's 99th percentile went from 0.3 s to 1.5 s at the same throughput, because retried transactions stopped sharing commits. So Postgres keeps its ten attempts: under extreme contention (200 concurrent increments of one document) some mutations are answered with the conflict instead of succeeding, which is a failure the caller sees, not a lost update, and the tests assert the count is exactly the increments that were answered.
- **Better Auth's adapter had `transaction: false`**, so a sign-up wrote a user, an account and a session in three transactions and a failure between them left a user who could not sign in. The adapter now provides `transaction`, which runs the whole flow in one write transaction of the store (its calls read their own writes); Better Auth resets what it queued for after the commit when the store runs the flow again.
- **`import --replace` cleared the tables in one transaction and loaded rows in batches of 500 in others**, so a failure left the tables empty or half loaded. It is one transaction now (and publishes one reset, like a restore). On MongoDB a very large import is bounded by its 60-second transaction limit.
- **Not transactions, by design:** actions (at most once, each `runMutation` its own transaction), the object behind a `_storage` row (uploaded by the client, deleted after the commit that removes the row), the message that tells other servers about a commit (sent once, not stored), and other servers' caches until that message arrives.
- **Read of a commit that is not yet durable on SQLite.** For about one sync interval a reader can see a commit that a power cut would revert. Making readers wait for it would put a sync into every read that overlaps a write; it is documented instead (`transactions.mdx`). Anything a reader then writes is answered only after the sync that covers both.
- **Not claimed:** durability against a power cut is argued from the design, not tested, and MongoDB and Postgres durability is whatever their configuration says (MongoDB's default is majority-acknowledged and journaled).
